# zhang22 / zhao2020 分块测时失真排查

## 1. 本轮先确认的问题

用户反馈的问题不是单纯“某些段里混入了别的逻辑”，而是更严重的现象：

- 设置了较大的常量权重后，`pipeline timing` 测出来的 `avg_ns` 放大倍数并不对等
- 一些理论上很重的纯计算段，实测时间只有几百纳秒

本轮排查对象：

- 源文件：`/home/chove/Desktop/ScratchDAG/源文件/zhang22/zhang22.c`
- 分块文件：`/home/chove/Desktop/ScratchDAG/中间结果/zhang22/pipeline/blocks/level2/effective_line_merge/segments.json`
- 测时文件：`/home/chove/Desktop/ScratchDAG/中间结果/zhang22/pipeline/timing/level2/effective_line_merge/timing.json`


## 2. 已确认的两个根因

### 根因 A：`effective_line_merge` 的段本来就不等于“单个 Cx 的纯计算段”

最明显的是 `MU:main#001@132-168`，它对应源码第 132-168 行，包含：

- `pthread_mutex_lock`
- `sched_setaffinity`
- `init_matrices`
- `clock_gettime`
- 多个 `sem_init`
- 多个 `pthread_create`
- 最后才到 `busy_wait_seconds(C7)`

所以该段的 `avg_ns` 不能用来验证 `C7` 的线性比例。

同类问题还出现在：

- 含 `sem_wait` 的段
- 含 `sem_post` 的段
- 含 `pthread_join` 的段

这些段的测时本质上是“同步等待 + 框架逻辑 + 少量计算”的合成值，不适合拿来做常量倍率验证。


### 根因 B：`busy_wait_seconds()` 在 `-O2` 下被优化空了

这是本轮最关键的新发现。

当前 `pipeline timing` 编译命令见 `pipeline/timing.py`：

```c
gcc -O2 -g -std=c11 -pthread ...
```

而 `zhang22.c` 里的 `busy_wait_seconds()` 只是反复做矩阵乘法并写入全局数组 `mat_c`，但程序后续并不读取这些结果。

经直接查看 timing 产物中的可执行文件反汇编，已经确认：

```asm
0000000000001b40 <busy_wait_seconds>:
    1b40: c3    retq
```

也就是说：

- `busy_wait_seconds()` 被 GCC 优化成了空函数
- 所有 `Cx` 权重在 `pipeline timing` 阶段实际上几乎都没有真实计算成本
- 因此当前测出来的段时间，主要来自锁、信号量、线程创建、`join`、调度等待，而不是 `Cx`

这也解释了为什么会出现如下明显违背预期的结果：

- `C1 = 350`，但 `MU:worker_c2#001@98-100` 的 `avg_ns = 166`
- `C4 = 220`，但 `MU:worker_c1#001@113-115` 的 `avg_ns = 203`
- `C10 = 140`，但 `MU:main#004@177-180` 的时间主要受 `pthread_join` 影响，`min_ns = 325`，波动极大


## 3. 对当前实验结论的影响

这意味着当前 `zhang22` 上关于“权重是否按预期放大”的判断，不能直接信任。

更具体地说：

- 现在的 `avg_ns` 不是单纯由 `Cx` 决定
- 它更多反映的是同步等待和线程时序
- 用这份 `timing.json` 喂给 `zhao2020`，算法拿到的节点权重已经偏离了原本想表达的计算量

因此，如果继续在现有口径下只调 `C1..C14`，很可能是在错误反馈上调参。


## 4. 当前不应该做什么

在修复测量口径前，不建议继续做下面这些事：

- 继续盲目放大 `C1..C14`
- 试图从当前 `avg_ns` 图上直接验证常量比例
- 用当前 `timing.json` 的权重去判断 `zhang22` 是否天然适合 `zhao2020`


## 5. 下一步建议

### 第一步：先修复“纯计算不会被编译器消掉”

优先方案：

- 设计一个新的实验用 C 程序，放在 `test实验` 目录下
- 让计算代码具备可观察副作用，避免 `-O2` 下被优化成空函数

可选做法：

- 把结果累加到 `volatile` 全局变量
- 或在计算结束后读取结果并写到 `stderr` / `stdout`
- 或给计算核心加 `asm volatile("" ::: "memory")` 之类的屏障

其中最稳妥的是：

- 使用 `volatile double g_sink`
- 每轮计算后做 `g_sink += accum`


### 第二步：实验 DAG 要刻意满足 zhao2020 的优势条件

如果目标是“让 `prio(zhao2020)` 明显优于 FIFO，而且 FIFO 特别差”，新程序结构要满足：

- 关键路径节点必须早释放，但容易在 FIFO 下被填充任务抢占
- 关键路径不能由 `main` 单线程长期串行主导
- 关键路径上的释放点要对后续 makespan 真正敏感
- 需要限制在严格两核或固定少核环境下运行

换句话说，新实验不该再像当前 `zhang22` 这样：

- `main` 拿最高优先级后自己一路串行推进大量关键段
- worker 更像陪跑


### 第三步：分块规则也要配合实验目的

如果目标是“验证权重比例”，就不能让一个 segment 同时包含：

- 同步原语
- 线程创建
- `join`
- 真实计算

更合理的实验设计是：

- 一个计算块只做计算
- `post/wait/join/create` 单独成段
- 关键路径和填充路径都由多个纯计算块构成


## 6. 下一轮实验设计约束

下一轮我建议直接按下面约束设计新 DAG：

1. 新实验目录放在：
   `test实验/2026-03-17_zhang22_zhao2020_测时失真排查/`
2. 新源码单独命名，不复用 `zhang22.c`
3. 纯计算函数必须抗优化
4. 同步段与计算段分离
5. 先做“常量倍率验证”，确认 `C=1:10:100` 大致能反映到 `avg_ns`
6. 再把这个程序接到 `zhao2020` runtime compare


## 7. 当前结论一句话总结

当前“权重放大倍数不对等”的首要原因，不是你常量调得不对，而是：

- 一部分段混入了大量非计算逻辑
- 更关键的是 `busy_wait_seconds()` 已经在 `-O2` 下被优化成空函数

所以接下来应该先修实验载体和测量口径，再谈怎么构造一个对 `zhao2020` 特别友好的 DAG。
