# 适合 zhao2020、且 FIFO 明显吃亏的新 DAG 设计草案

## 1. 设计目标

新实验程序需要同时满足两件事：

- `pipeline timing` 能测到接近真实比例的纯计算权重
- 在固定少核条件下，`prio(zhao2020)` 明显优于 `baseline(FIFO)`


## 2. 结构原则

### 原则 A：关键路径必须由 worker 主导，不要由 `main` 串行主导

如果还是像 `zhang22` 一样让 `main` 自己连跑很多关键段，那么即使设了优先级，也很难把 FIFO 拉差。

更合理的是：

- `main` 只负责创建线程、发起第一批 release、最后汇总
- 真正的关键路径放到 worker 链上


### 原则 B：两核下要有“重填充任务先占坑”的机会

FIFO 想变差，必须让它有机会先把两个核都塞给不关键但很重的任务。

所以建议结构上包含：

- 一条关键链 `K1 -> K2 -> K3 -> K4`
- 两到三个填充任务 `F1/F2/F3`
- `F*` 在时间上更早 ready
- `K1` 也 ready，但 FIFO 容易先跑 `F*`

这样：

- FIFO 可能把核心时间片先给 `F1/F2`
- `K1` 延后，导致整个关键链后续节点都晚释放
- zhao2020 则可通过更高优先级尽快推进 `K1..K4`


### 原则 C：关键路径节点之间的依赖要真实敏感

不要只做“很多独立重任务 + 最后 join”。

更好的结构是：

- `K1` 完成后才释放 `K2`
- `K2` 完成后才释放 `K3`
- `K3` 完成后才释放 `K4`

这样任何一个关键节点被拖慢，都会直接拖长 makespan。


### 原则 D：同步段和计算段严格分开

每个计算段只保留：

- 一次纯计算调用

不要把下面内容和计算混在一个 segment：

- `pthread_create`
- `pthread_join`
- `sem_wait`
- `sem_post`
- `mutex lock/unlock`

否则 `avg_ns` 还是会失真。


## 3. 建议的初版 DAG

建议先做一个两核、四关键段、三个填充段的程序。

逻辑示意：

```text
main
 ├─ release F1
 ├─ release F2
 ├─ release K1
 └─ wait all

F1: heavy filler
F2: heavy filler
F3: heavy filler, released by F1

K1 -> K2 -> K3 -> K4
```

进一步约束：

- `F1/F2` 的单段时长大于 `K1`
- 但 `K1+K2+K3+K4` 的总长度决定 makespan
- `F3` 作为额外干扰项，防止 FIFO 偶然表现太好


## 4. 一组可先尝试的权重关系

先不要用特别夸张的数，先保证倍率可测。

建议第一版：

- `K1 = 20`
- `K2 = 20`
- `K3 = 20`
- `K4 = 20`
- `F1 = 60`
- `F2 = 60`
- `F3 = 60`

两核下的直觉：

- 如果 FIFO 先跑 `F1 + F2`，则 `K1` 被明显延后
- 而 `K1` 一旦延后，后面的 `K2/K3/K4` 都被整体平移
- zhao2020 只要能优先推进 `K1`，总时间就会显著更短


## 5. 实现层面的硬约束

### 5.1 纯计算函数要抗优化

建议固定写法：

```c
static volatile double g_sink = 0.0;
```

计算函数结束时：

```c
g_sink += local_sum;
```

这样 `-O2` 不会把核心循环直接删掉。


### 5.2 固定两核

源码里直接绑定：

```c
CPU_SET(0, &cpu_set);
CPU_SET(1, &cpu_set);
```

不保留 `2,3`。


### 5.3 线程 release 顺序要服务于“FIFO 容易犯错”

建议让 `F1/F2` 先创建并先 ready，`K1` 虽然也 ready，但在无优先级区分时容易排到后面。


## 6. 推荐的推进顺序

下一步不要直接上完整 runtime compare，先分两段做：

1. 先写一个最小实验程序，只验证 `K` 和 `F` 段的 `avg_ns` 是否大致符合权重比例
2. 比例稳定后，再接入 `pipeline schedule + instrument + runtime compare`
