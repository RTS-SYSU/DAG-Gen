# zhang1 五算法 runtime vs 手动测时校验（ws=100, r=10）

## 1. 实验目的

- 验证 `runtime_compare` 工具在 `work_scale=100` 下对 5 个算法的测时是否与程序体内手动计时一致。
- 手动测时：在 `main()` 体内注入 `clock_gettime(CLOCK_MONOTONIC_RAW)` 计时。
- 对象：`zhang1` 的 cpf / heft / zhao2020 / wcet_first / t_level。

## 2. 实验配置

- `work_scale = 100`
- `repeats = 10`
- `cpu_set = [0, 1]`
- `cores_per_task = 2`

原始均值偏差很大，原因是两种方法都存在系统级异常值（单次运行 6-8 秒，正常值约 2 秒）。

## 4. 异常值分析

每组 10 次运行中，均有 1-3 次出现 6-8 秒的异常高值（正常值约 2 秒）。这是系统级干扰（后台进程、调度器抖动等），两种测时方法都受到同样影响。

示例（cpf prio，runtime_compare）：
```
[7.557, 2.144, 1.920, 2.247, 7.864, 2.028, 2.384, 2.142, 7.797, 1.824]
```

## 6. 结论

### 6.1 两种测时方法的一致性

去掉系统级异常值后，大部分对比偏差在 1-4% 之间，说明：

- `runtime_compare`（wrap_main + prog_timer）和程序体内手动测时的口径基本一致
- 两者使用相同的时钟源（`CLOCK_MONOTONIC_RAW`），测量范围也几乎相同
- 偏差主要来自不同时间段运行时的系统状态差异，而非测时方法本身

### 6.2 系统干扰问题

- ws=100 下单次运行约 2 秒，但偶尔出现 6-8 秒的异常值
- 异常值在 baseline 和 prio 中都会出现，不是某种版本特有的
- 建议后续实验增加 repeats（如 20-50 次）并使用中位数或 trimmed mean 作为主指标

### 6.3 各算法 baseline vs prio 效果

由于异常值干扰，本轮数据不适合直接用于评估算法效果。建议：

1. 增加 repeats 到 50-200 次
2. 使用中位数作为主指标
3. 或者降低 work_scale 减少单次运行时间，降低被干扰的概率
