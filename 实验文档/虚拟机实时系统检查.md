## 4. RT 带宽与 cgroup 限制

### 4.1 全局 RT 节流

```text
/proc/sys/kernel/sched_rt_runtime_us = 950000
/proc/sys/kernel/sched_rt_period_us  = 1000000
```

含义：每 1 秒周期内，全系统所有 `SCHED_FIFO/RR` 线程合计最多占用 950ms CPU 时间，仍保留 5% 给 CFS。

### 4.2 cgroup RT 配额

本机内核配置为：

```text
# CONFIG_RT_GROUP_SCHED is not set
```

复查 `/sys/fs/cgroup/cpu`、`/sys/fs/cgroup/cpu,cpuacct`、`user.slice`、`system.slice` 后，没有发现 `cpu.rt_runtime_us` / `cpu.rt_period_us` 文件。

### 4.3 当前进程所在 cgroup

```text
cpu,cpuacct:/user.slice
0::/user.slice/user-1000.slice/session-2.scope
```

### 4.4 结论

- 虚拟机保留了全局 RT 节流 `950000 / 1000000`
- 但 **没有** `RT_GROUP_SCHED`，也没有 `user.slice` 级 RT 预算
- 因此这里不会出现 rk3588 上那种“用户会话整组 RT 线程先被 cgroup 限流”的额外惩罚

这仍然是 VM 与 RK3588 的重要差异，但它已经不足以单独解释全部实验反转现象。

## 6. 本次新增的详细系统级测试

这次不是只查配置项，而是补做了 IRQ、亲和性、cpuset、工具可用性和一个同核竞争微基准。

### 6.1 IRQ 线程现状

`ps -eLo pid,tid,cls,rtprio,pri,psr,comm` 复查结果显示：

- 大量 `irq/*` 线程本身就是 `SCHED_FIFO`
- 常见优先级是 **`rtprio=50`**
- `migration/*` 线程是 **`rtprio=99`**
- `rcu_preempt` / `rcuc/*` 是 **`rtprio=1`**

这点很重要，因为它说明：

> 即使在这台虚拟机里，用户态 `SCHED_FIFO 80/90/99` 线程理论上也会压过大部分 `irq/*` 线程。

换句话说，“FIFO 可能压住 IRQ 线程”并不是板子独有机制，虚拟机也成立；只是虚拟机里的设备链路和中断复杂度低得多，所以副作用更不容易放大。

### 6.2 热点 IRQ 与 CPU 亲和性

从 `/proc/interrupts` 和 `/proc/irq/*/smp_affinity_list` 看，当前虚拟机中断分布非常集中：

| IRQ | 设备 | 当前热点 CPU | `smp_affinity_list` |
|-----|------|-------------|---------------------|
| 19 | `ens33` | CPU7 | `7` |
| 17 | `ehci_hcd:usb1, ioc0` | CPU1 / CPU4 | `1` |
| 16 | `vmwgfx, snd_ens1371` | CPU3 / CPU5 | `5` |
| 18 | `uhci_hcd:usb2` | CPU5 / CPU6 | `6` |

说明：

- VM 里的关键设备 IRQ 数量不多
- 它们通常被固定到单个 vCPU
- 真实板端那种“多设备、多驱动、多簇协同”的复杂度在这里明显更低

### 6.3 cpuset / cgroup 约束

本次复查得到：

```text
Cpus_allowed_list: 0-127
Mems_allowed_list: 0
/sys/fs/cgroup/cpuset/cpuset.cpus = 0-7
```

结论：

- 当前 shell 没有被额外收缩到某几个 CPU
- 顶层 cpuset 允许使用 `0-7`
- 没看到类似“只准跑在小核”或“被 systemd slice 卡死在某一簇”的现象

这也意味着虚拟机里没有出现板端常见的 cpuset / cluster 级偏置。

### 6.4 RT 相关附加参数

本次还确认了两项常被忽略的参数：

```text
/proc/sys/kernel/sched_rr_timeslice_ms = 100
/proc/sys/kernel/sched_autogroup_enabled = 1
```

其中：

- `sched_rr_timeslice_ms` 只影响 `SCHED_RR`，对 `SCHED_FIFO` 不是直接变量
- `sched_autogroup_enabled=1` 会影响普通 CFS 任务的交互分组行为，但不会改变前面确认的 RT 类可抢占性

### 6.6 同核竞争微基准

为了确认“VM 里 FIFO 是否真的更容易赢”，本次加做了一个固定工作量测试：

- 计算任务和干扰任务都绑到 **CPU7**
- 干扰任务是同核 CFS busy loop
- 被测任务分别用 `CFS`、`FIFO 10`、`FIFO 50`、`FIFO 80`
- 被测任务执行同一段约 3000 万次迭代的纯计算

结果如下：

| 模式 | 墙钟时间 |
|------|---------|
| CFS | **3.948s** |
| FIFO 10 | **2.000s** |
| FIFO 50 | **2.076s** |
| FIFO 80 | **2.236s** |

解读：

- 在这个“单核 + 纯 CPU + 简单干扰”的 VM 微基准里，`FIFO` 明显优于 `CFS`
- 但也不是优先级越高越好；`FIFO 10` 反而比 `FIFO 80` 更快
- 这和前面的判断一致：**FIFO 的优势在“只缺 CPU”的场景里最容易显现，而优先级过高又会开始带出额外副作用**

## 7. 对 VM / RK3588 结果相反的重新判断

之前文档把重点放在 `RT_GROUP_SCHED + user.slice 90%`。这次复测后，结论需要收敛成下面这句：

> **虚拟机里 FIFO 比 CFS 好、而 RK3588 上 CFS 比 FIFO 好，更像是“真实板端系统协同成本把纯调度优势盖过去了”，不是单纯谁的策略更高级。**

### 7.1 虚拟机为什么更容易让 FIFO 看起来更强

- PREEMPT_RT 内核，用户态 RT 线程更容易直接体现抢占优势
- 没有 `user.slice` 级 RT 配额，不会先被 cgroup 额外限流
- 没有可观测的真实 `cpufreq` / governor / big.LITTLE 路径
- 真实设备中断、驱动链路、DMA、总线争用都比板端简单得多

因此虚拟机更接近“干净环境下比拼调度策略本身”。

### 7.2 RK3588 上为什么可能反过来是 CFS 更好

按优先级排序，更可能是下面几类原因叠加：

1. **FIFO 压住了关键 IRQ 线程、kthread 或应用辅助线程**  
   板端是真实 SoC，有网卡、存储、定时器、驱动等中断和内核线程；应用主线程设成高优先级 `SCHED_FIFO` 后，可能把本来给自己“喂数据”的线程也压住。

2. **DVFS + big.LITTLE + 负载均衡更照顾 CFS 的运行形态**  
   RK3588 是异构多核平台，CFS 更容易配合调频和落核；FIFO 如果落在小核或把相关线程拆散，整体反而更差。

3. **RT 节流确实仍然会放大 FIFO 的抖动**  
   板端同时有全局 `sched_rt_runtime_us=950000` 和 `user.slice/cpu.rt_runtime_us=900000`，FIFO 线程长期跑满时会被周期性打断。

4. **程序自身的线程拓扑被 FIFO 放大了问题**  
   例如主线程设成 FIFO，但真正干活的 worker 仍是 CFS，或者主线程 post/lock/wakeup 链路长，最后就会出现“主线程很凶，但整条 pipeline 更慢”。

### 7.3 当前更稳妥的判断

虚拟机结果更像在回答：

> 在一个中断少、环境更干净、RT 限制更少的环境里，`SCHED_FIFO` 能否直接压过 CFS？

RK3588 结果更像在回答：

> 在真实 SoC、真实中断、调频、异构核和多线程协作同时存在时，哪种方式让整条链路更顺？

所以“VM 上 FIFO 好，板上 CFS 好”并不矛盾。

## 8. 这份虚拟机检查文档能支持的结论

本次复测可以确认：

- 虚拟机仍然是 `PREEMPT_RT`
- `SCHED_FIFO` 仍可直接使用
- 全局 RT 节流仍为 `950000 / 1000000`
- 没有 `RT_GROUP_SCHED`，没有 `user.slice` RT 配额
- 没有标准 `cpufreq` 接口，无法从虚拟机侧直接对比 governor / 实时频率
- 虚拟机内也存在大量 `FF 50` 的 `irq/*` 线程，但热点 IRQ 数量和设备复杂度远低于真机
- 在“单核纯计算 + 同核干扰”微基准中，`FIFO` 确实显著优于 `CFS`

因此，这份文档最多只能支持下面的判断：

> **虚拟机环境对 FIFO 更友好，且更容易显露“调度策略本身”的效果。**

它 **不能** 单独证明：

> rk3588 上 CFS 更好只是因为 `user.slice` 90% 配额。

板端结论仍应结合 IRQ 线程、绑核、频率、迁核和多线程依赖关系一起看。

## 9. 下一轮板端对比建议

如果要继续定位“为什么板上 CFS 更好”，优先做下面 8 个对比：

1. 检查 `sched_rt_runtime_us` 与 `sched_rt_period_us`
2. 检查各 `policy*/scaling_governor` 与 `scaling_cur_freq`
3. 用 `ps -eLo pid,tid,cls,rtprio,pri,psr,pcpu,comm` 看应用线程落核
4. 用 `ps -eLo ... | grep -E 'irq/|your_app'` 看 IRQ 线程优先级
5. 用 `pidstat -wt -p <pid> 1` 看切换和抖动
6. 在 RK3588 上先固定 `performance` 再比较 FIFO/CFS
7. 把程序和关键线程绑到同一组大核再比较
8. 列出所有关键线程，确认是否存在“主线程 FIFO、worker 仍是 CFS”的拓扑失配
