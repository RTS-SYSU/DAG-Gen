## 4. RT 带宽配额（关键！影响实验结果）

### 4.1 全局 RT 节流

```text
/proc/sys/kernel/sched_rt_runtime_us = 950000
/proc/sys/kernel/sched_rt_period_us  = 1000000
```

含义：每 1 秒周期内，全系统所有 `SCHED_FIFO/RR` 线程合计最多占 **950ms** CPU 时间，剩余 **50ms** 强制留给 CFS。

### 4.2 cgroup 层 RT 配额

本机内核配置为：

```text
# CONFIG_RT_GROUP_SCHED is not set
```

因此以下 RT 配额文件都**不存在**：

| cgroup 路径 | `cpu.rt_runtime_us` | `cpu.rt_period_us` | 含义 |
|-------------|---------------------|--------------------|------|
| `/sys/fs/cgroup/cpu/` | **不存在** | **不存在** | 无顶层 RT 配额文件 |
| `/sys/fs/cgroup/cpu/user.slice/` | **不存在** | **不存在** | 无 `user.slice` RT 预算 |
| `/sys/fs/cgroup/cpu/system.slice/` | **不存在** | **不存在** | 无 `system.slice` RT 预算 |

补充说明：`/sys/fs/cgroup/cpu` 实际是指向 `/sys/fs/cgroup/cpu,cpuacct` 的符号链接，目录中只有 `cpu.cfs_quota_us` 等 CFS 配额文件，没有 RT 配额文件。

### 4.3 当前进程所在 cgroup

```text
cpu,cpuacct:/user.slice
0::/user.slice/user-1000.slice/session-4.scope
```

### 4.4 RT 配额对实验的影响

**这台虚拟机和 rk3588 最大的差异，不是“能不能用 SCHED_FIFO”，而是“有没有 cgroup 级 RT 限流”。**

- 你的实验程序虽然也运行在 `user.slice` 下
- 但本机 **没有** `user.slice/cpu.rt_runtime_us` 这种 90% RT 配额
- 因此不会出现 rk3588 上那种“RT 线程跑到 900ms 后整组被 cgroup 节流”的现象
- 本机仅保留 **全局** `sched_rt_runtime_us = 950000` 的 95% 节流
- 所以虚拟机上的 FIFO / 算法版本，相比 rk3588，更不容易因为 `user.slice` 配额被额外惩罚

### 4.5 永久化服务

```text
rt-cgroup-user-slice.service: not found
```

本机没有发现类似 rk3588 上用于写入 `user.slice` RT 配额的 systemd 服务。

## 6. 总结 & 对实验的影响

### 本机是实时内核

- 抢占模型为 **`PREEMPT_RT`**
- `/sys/kernel/realtime = 1`
- uname 中明确包含 `PREEMPT_RT`
- 当前用户可直接运行 `SCHED_FIFO`

### 影响实验结果的关键参数

| 参数 | 当前值 | 对实验的影响 |
|------|--------|-------------|
| `CONFIG_PREEMPT_RT` | **y** | 完整实时补丁，RT 抢占能力强 |
| `CONFIG_RT_GROUP_SCHED` | **not set** | **没有 cgroup 层 RT 时间配额** |
| `sched_rt_runtime_us`（全局） | **950000** | 全局每秒最多 950ms 给 RT，仍有 **5% 节流** |
| `CONFIG_HZ` | **250** | tick 基准约 4ms |
| `CONFIG_HIGH_RES_TIMERS` | **y** | 定时精度优于普通低精度 tick |
| cpufreq governor | **不可见** | 无法直接分析来宾中的动态调频行为 |

### 与 rk3588 的关键差异

| 项目 | 虚拟机（本机） | rk3588 |
|------|---------------|--------|
| 内核抢占模型 | **`PREEMPT_RT`** | `PREEMPT_VOLUNTARY` |
| `/sys/kernel/realtime` | `1` | 不存在 |
| `RT_GROUP_SCHED` | **n** | **y** |
| `user.slice` RT 配额 | **无** | **950000**（与顶层一致，已与虚拟机侧「无额外 10%」对齐） |
| 全局 `sched_rt_runtime_us` | 950000（95%） | 950000（95%） |
| cpufreq / governor | 来宾中不可见 | 可直接读取 |
| 平台特性 | VMware 虚拟化 | 物理开发板 |

### 对实验现象的直接解释

- 在这台虚拟机上，`SCHED_FIFO` 是真的生效的
- 同时又**没有** `user.slice` 级别的 RT 限流
- 因此虚拟机上的 FIFO / 算法实验结果，通常会比 rk3588 更容易体现“优先级调度本身”的效果
- rk3588 上若曾出现 “CFS 反而最好”，除 DAG/插桩因素外，常见原因是 `RT_GROUP_SCHED` 下 **`user.slice` RT 配额低于顶层**（例如曾为 900000）；现已改为 **950000** 与顶层对齐后，应对照重跑实验再下结论

### 如需取消当前虚拟机上的全局 RT 节流

```bash
# 取消全局限制（实验时临时执行，存在卡死风险）
echo -1 | sudo tee /proc/sys/kernel/sched_rt_runtime_us

# 恢复默认
echo 950000 | sudo tee /proc/sys/kernel/sched_rt_runtime_us
```

⚠️ **警告**：取消全局 RT 节流后，若 `SCHED_FIFO` 程序存在死循环或优先级设置不当，可能导致系统长时间失去响应。
