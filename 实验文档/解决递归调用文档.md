# 解决递归/多级调用导致的 DAG 建图混乱问题

## 1. 问题背景

当前 `Code2DAG` 在生成 DAG 图时，已经对部分函数调用做了"实例化"处理，目的是避免：

- 同一个函数被多次调用时，多个调用边都指向同一个函数名节点；
- 从而导致调用关系塌缩、上下文丢失、图结构混乱。

目前已经对 `busy_wait_seconds` 这类函数做过特殊处理，将其视为"函数实例"而不是单纯函数名。

但是，当某个函数实例内部继续调用其他函数时，现有的一层实例命名机制就不够用了。

---

## 2. 当前问题本质

如果建图时只记录函数名，例如：

- `busy_wait_seconds`
- `clock_gettime`

那么会出现下面的问题：

1. `main` 多次调用 `busy_wait_seconds` 时，会有多条边指向同一个 `busy_wait_seconds` 节点；
2. `busy_wait_seconds` 内部如果再调用 `clock_gettime`，所有内部调用也会汇聚到同一个 `clock_gettime` 节点；
3. 无法区分"这个 `clock_gettime` 属于哪个 `busy_wait_seconds` 实例"；
4. 一旦出现多层调用，图结构会被压扁，边关系错误。

因此，问题的核心并不是"某个函数要不要实例化"，而是：

**节点标识必须携带完整调用上下文。**

---

## 3. 现有一级命名机制

目前已有的思路是：

- 用"调用者 + 函数名 + 数字"的形式表示函数实例；
- 数字表示"该函数在该调用者下第几次被调用"。

例如：

- `main/busy_wait_seconds#1`
- `main/busy_wait_seconds#2`

这个方案可以解决"同一个调用者多次调用同一个函数"的问题。

但是它只能解决一层上下文。

例如当：

- `main` 调用 `busy_wait_seconds`
- `busy_wait_seconds` 再调用 `clock_gettime`

如果仍然只保留一级调用者信息，那么 `clock_gettime` 仍然无法唯一归属于某个 `busy_wait_seconds` 实例。

---

## 4. 目标：升级为多级嵌套调用实例命名

新的节点命名机制应改为"完整调用路径实例化"。

### 命名规则

采用如下嵌套结构：

- `调用者/函数名#数字`
- 如果继续嵌套，则在上一级实例路径后继续追加：
  - `/函数名#数字`

例如：

- `main/busy_wait_seconds#2`
- `main/busy_wait_seconds#2/clock_gettime#1`

这里的含义是：

- `main` 中第 2 次调用了 `busy_wait_seconds`
- 在这个 `busy_wait_seconds` 实例内部，第 1 次调用了 `clock_gettime`

因此，节点的唯一标识不再只是"函数名"，也不再只是"一级调用者 + 函数名"，而是：

**完整调用路径 + 当前层局部序号**

---

## 5. 不只是函数实例，函数内部普通节点也必须实例化

后续升级时，不能只给"函数调用名"加多级前缀，还必须把函数体内部的普通节点也挂在实例路径下面。

例如，不能只区分：

- `main/worker_c2#1`
- `main/worker_c2#2`

还必须同时区分它们各自函数体内部的节点：

- `main/worker_c2#1/pthread_mutex_lock1`
- `main/worker_c2#1/sem_wait4`
- `main/worker_c2#1/busy_wait_seconds#2`
- `main/worker_c2#2/pthread_mutex_lock1`

如果只实例化函数名，而函数体内部节点仍然沿用模板名，那么：

- 两个不同函数实例内部的 `pthread_mutex_lock1`
- `sem_wait4`
- `pthread_mutex_unlock7`

仍然会撞名，图还是会乱。

因此，后续应统一采用：

**函数实例路径 + 该实例内部节点名**

作为普通节点 ID 的生成规则。

---

## 6. 线程也必须实例化

除了普通函数调用，线程创建也必须进入同一套实例化体系。

原因：

- `main` 中可能多次 `pthread_create` 同一个线程变量；
- 线程可能创建后被 `join`，然后再次创建；
- 线程入口函数也可能被多次创建；
- 如果只记录线程变量名或线程函数名，也会发生塌缩。

因此，线程至少需要区分两类实例：

1. **线程句柄实例**
2. **线程入口函数实例**

例如：

- `main/thread_c2#1`
- `main/worker_c2#1`

其中：

- `main/thread_c2#1` 表示 `main` 下第 1 次创建的 `thread_c2` 句柄实例
- `main/worker_c2#1` 表示与之对应的线程入口函数实例

如果 `worker_c2` 内部又调用 `busy_wait_seconds`，则继续展开为：

- `main/worker_c2#1/busy_wait_seconds#1`
- `main/worker_c2#1/busy_wait_seconds#2`

这样线程内部的调用也可以和主线程中的同名调用区分开。

---

## 7. 正确的实例化原则

未来真正的实现不应再是"全局给函数加 `@instanceN` 后缀"，而应该改为：

### 原则 1：保留函数模板

先保留每个函数的静态定义信息，例如：

- 函数体内有哪些调用
- 调用顺序是什么
- 哪些是 `pthread_create`
- 哪些是 `pthread_join`
- 哪些是 `sem_wait` / `sem_post`
- 哪些是普通函数调用
- 哪些是函数体内部普通节点

这一层只是"模板"，不带实例编号。

### 原则 2：从 `main` 出发递归展开实例图

真正生成 DAG 时：

- 从 `main` 开始；
- 按调用顺序扫描；
- 每遇到一次调用，就基于"当前父实例路径"分配一个新的子实例；
- 子实例继续递归展开；
- 从而得到一张真正的"实例图"。

也就是说：

- 不是先把函数表 clone 一遍再画图；
- 而是先保留模板，再按调用路径逐步展开成图。

### 原则 3：实例化发生在"展开层"，不是"函数表层"

函数模板应该保持静态定义；
真正的节点唯一化应该在"从入口函数递归生成实例图"的过程中完成。

---

## 8. 推荐的数据结构方向

后续实现时，建议至少具备以下几类数据结构。

### 8.1 函数模板

用于保存函数的静态调用序列。

建议字段：

- `name`
- `ops`：顺序操作列表

### 8.2 操作模板

每一条操作记录一个静态事件，例如：

- 普通函数调用
- 普通外部调用
- `pthread_create`
- `pthread_join`
- `pthread_mutex_lock`
- `pthread_mutex_unlock`
- `sem_wait`
- `sem_post`
- 条件/循环节点
- `return`

建议字段：

- `kind`
- `name`
- `callee`
- `handle`
- `line`
- `raw_node`
- `extern`

### 8.3 实例展开帧（Frame）

表示"当前正在展开哪个函数实例"。

建议字段：

- `function_name`
- `instance_path`
- `child_call_counters`
- `handle_counters`
- `prev_node`

其中：

- `child_call_counters` 用于记录"当前父实例下，某个子函数已经被调用了几次"
- `handle_counters` 用于记录"当前父实例下，某个线程句柄已经创建了几次"

### 8.4 线程实例信息

用于绑定 create / join / 线程尾节点。

建议字段：

- `handle_name`
- `handle_key`
- `handle_instance_id`
- `task_function`
- `task_instance_path`
- `create_node_id`
- `join_node_id`
- `tail_node_id`
- `state`

其中 `state` 建议至少支持：

- `created`
- `running`
- `joined`
- `detached`
- `orphaned`
- `unresolved`

### 8.5 最终实例图

建议维护：

- `nodes`
- `edges`
- `tail_by_instance`
- `exit_nodes_by_instance`
- `live_threads`

其中：

- `tail_by_instance`：记录每个函数实例的主尾节点
- `exit_nodes_by_instance`：记录每个函数实例所有可能出口
- `live_threads`：记录当前还活跃、尚未 join 的线程实例

### 8.6 节点元数据

后续不要再依赖"字符串长什么样"来判断节点类型，建议为每个节点显式维护元信息，例如：

- `node_id`
- `kind`
- `template_name`
- `owner_instance`
- `display_name`

---

## 9. 节点命名与展示建议

后续最好区分下面几层含义：

### 9.1 唯一 ID

用于程序内部判断唯一性，例如：

- `main/worker_c2#1/busy_wait_seconds#2`
- `main/worker_c2#1/pthread_mutex_lock1`

### 9.2 模板名

用于回溯它来源于哪个静态模板节点，例如：

- `busy_wait_seconds`
- `pthread_mutex_lock1`

### 9.3 展示名

用于图上显示，可根据需要缩短：

- `busy_wait_seconds#2`
- `clock_gettime#1`

---

## 10. 普通函数调用的展开规则

假设当前实例路径为 `P`，当在 `P` 中遇到一次对子函数 `foo` 的调用时：

1. 令 `counter[(P, foo)] += 1`
2. 得到当前调用序号 `k`
3. 生成子实例路径：`P/foo#k`
4. 建立边：`P` 当前线性前驱节点 -> `P/foo#k`
5. 递归展开 `foo` 的函数体
6. 得到 `foo` 实例的出口信息
7. 将父路径中的后续边接到该实例出口之后

---

## 11. 编号规则必须固定为"父实例下的静态顺序"

后续必须明确：

- `#数字` 的含义不是全局第几次出现；
- 也不是运行时执行顺序；
- 而是"在当前父实例模板中，按静态扫描顺序，第几次遇到该调用"。

建议固定采用：**按父实例内的静态调用顺序编号。**

---

## 12. pthread_create 的展开规则

当父实例 `P` 中遇到 `pthread_create(&thread_x, ..., worker_x, ...)`，建议处理为：

1. 生成 create 节点（例如 `P/pthread_create17`）
2. 在 `P` 下为 `thread_x` 分配句柄实例编号：`P/thread_x#k`
3. 在 `P` 下为线程入口函数 `worker_x` 分配函数实例编号：`P/worker_x#k`
4. 建立绑定：`handle_instance -> task_instance`
5. 建立图边：`create_node -> task_instance`、`create_node -> 创建者的后继节点`
6. 递归展开线程入口函数实例
7. 保存线程实例出口节点，供后续 `join` 使用

---

## 13. pthread_join 的展开规则

当父实例 `P` 中遇到 `pthread_join(thread_x, NULL)`，建议处理为：

1. 从 join 节点解析出 handle 表达式
2. 将该表达式规范化为统一的 `handle_key`
3. 在活跃线程表中找到匹配的线程实例
4. 再找到其绑定的线程任务实例
5. 再找到该任务实例的尾节点或统一出口节点
6. 增加补边：`tail_or_exit -> join_node`
7. 将该线程实例标记为已 `joined`

---

## 14. handle 绑定必须使用"规范化表达式"

线程绑定不能只处理简单变量名 `thread_c0`，还要考虑 `&thread_c0`、`threads[i]`、`ctx->thr`、`*p` 等形式。建议使用 `sym:thread_c0`、`sym:threads[i]`、`mem:ctx->thr`、`deref:p` 这类规范化 key。

---

## 15. `tail` 不能简单假设为单值

推荐为每个函数实例添加统一虚拟出口节点，例如 `main/worker_c2#1/__exit__`，将所有真实出口先连到 `__exit__`，然后父路径或 `join` 统一接到这个虚拟出口。

---

## 16. 分支、循环、递归都必须提前定义处理策略

### 16.1 分支与循环

升级到实例图后，分支节点是否也挂在实例路径下、分支合流点如何表示、循环节点如何处理，都需要明确。

### 16.2 递归

必须提前定义最大递归展开深度，超限时截断为虚拟节点或回边。

---

## 17. 源码解析不能只依赖单行简单正则

建议统一为基于函数区域扫描 + handle 规范化 + 出现顺序配对。

---

## 18. 需要避免的错误实现方式

- 全局函数名 + `@instanceN`
- 只在 create/join 上修补
- 实例化发生在函数表层而非展开层
- 只实例化函数名，不实例化函数内部节点
- 继续用字符串形状判断语义

---

## 19. 线程生命周期异常情况也要纳入设计

需要考虑 create 后未 join、detached thread、handle 被覆盖前尚未 join、join 绑定失败、线程内部再 create 子线程、create 与 join 不在同一个函数实例中等场景。

---

# 第二部分：下游影响分析

## 20. 当前系统中存在两套独立的"节点名空间"

这是理解影响范围的前提。

### 20.1 调用点节点名（dag.dot / internal_meta / circle.txt）

这是本次要改动的核心。

当前格式：

- `worker_c2/sem_wait4`
- `main/pthread_mutex_lock1`
- `busy_wait_seconds@instance5`
- `init_matrices`

改动后格式（举例）：

- `main/worker_c2#1/sem_wait4`
- `main/pthread_mutex_lock1`
- `main/worker_c2#1/busy_wait_seconds#2`
- `main/init_matrices#1`

### 20.2 段级节点名（seg_id）

这是 pipeline blocks/timing/schedule/instrument 阶段使用的。

当前格式：

- `SEG:worker_c2#1@115-116`
- `MU:main#7@150-184`
- `THR:worker_c2@112-126`

**段级 `seg_id` 由 `level2/segment_dag_level2.py` 独立生成**，它的输入是调用点节点名 + 行号，但输出的 `seg_id` 是一套完全独立的标识符。

关键结论：**调度、测时、插桩主要消费 `seg_id`，不直接消费 `dag.dot` 节点名。**

## 22. 需要适配但风险可控的环节

### 22.1 `core/func_ranges.py` — `@instance` 后缀剥离

当前代码：

```python
_INSTANCE_SUFFIX_RE = re.compile(r"@instance\d+$")

def normalize_func_name(name: str) -> str:
    """busy_wait_seconds@instance1 -> busy_wait_seconds."""
    return _INSTANCE_SUFFIX_RE.sub("", name)
```

影响：

- 如果未来不再使用 `@instanceN` 格式，而改用 `#N` 或多级路径
- 这个正则就匹配不到了
- 但这个函数只在映射源码行时使用

适配方案：

- 如果改用 `main/busy_wait_seconds#2` 形式，需要新增逻辑：取路径最后一段，再去掉 `#数字` 后缀
- 或者直接用节点元数据中的 `template_name` 字段

风险：**低，改一个正则即可。**

### 22.2 `tools/extract_func_ranges.py` — 同上

与 `core/func_ranges.py` 相同的 `@instance\d+$` 正则，同样适配。

风险：**低。**

### 22.3 `generation/thread_map.py` — join 节点正则

当前代码：

```python
if not re.search(r"(^|/)pthread_join(\d+)?$", join_node):
    return []
```

影响：

- 新命名下 join 节点可能变成 `main/pthread_join43` 或 `main/worker_c2#1/pthread_join5`
- 这个正则仍然能匹配（`(^|/)pthread_join(\d+)?$` 匹配末段即可）

风险：**无。** 该正则已经兼容多级路径。

### 22.4 `generation/exporters.py` — `_parse_node_name()`

当前代码：

```python
def _parse_node_name(self, node_name: str) -> Optional[Dict]:
    # 格式: "main/while/pthread_mutex_lock5"
    match = re.search(r'(\d+)$', node_name)
    if not match:
        return None
    seq_num = int(match.group(1))
    api_with_seq = node_name.split('/')[-1]
    api_name = api_with_seq[:-len(match.group(1))]
    parts = node_name.rsplit('/', 1)
    prefix = parts[0] if len(parts) > 1 else ''
    return {
        'full': node_name,
        'prefix': prefix,
        'api': api_name,
        'seq': seq_num
    }
```

影响：

- 新命名下节点如 `main/worker_c2#1/pthread_mutex_lock5`
- `split('/')[-1]` 取到 `pthread_mutex_lock5`，仍然正确
- `rsplit('/', 1)[0]` 取到 `main/worker_c2#1`，语义上变成了"实例路径"而非单层"函数名"
- **prefix 的语义变了**，但如果只用 prefix 做分组，仍然有效

但如果节点名包含 `#` 且尾部数字正则碰上了 `#1` 中的 `1`：

- 例如 `main/busy_wait_seconds#2`
- `(\d+)$` 匹配到 `2`
- `split('/')[-1]` 得 `busy_wait_seconds#2`
- `api_name` 变成 `busy_wait_seconds#`

**这会出错。**

适配方案：

- 解析时先区分"内部节点名"（如 `pthread_mutex_lock5`）和"函数实例名"（如 `busy_wait_seconds#2`）
- 或者在实例名和内部节点名之间用不同的分隔符

风险：**中等，需要明确区分 `#` 和尾部序号的关系。**

## 23. 必须重点改造的环节（高风险）

### 23.1 `level2/segment_dag_level2.py` — `_owner_from_dot_node()`

当前代码：

```python
def _owner_from_dot_node(node: str) -> str:
    """Best-effort owner function name for a legacy dag.dot node."""
    # Common format: "<fn>/<api><seq>"
    if "/" in node:
        return node.split("/", 1)[0]
    return node
```

影响（严重）：

当前假设：`/` 前面的第一段就是"拥有者函数名"。

- 旧命名：`worker_c2/sem_wait4` → owner = `worker_c2` ✅
- 新命名：`main/worker_c2#1/sem_wait4` → owner = `main` ❌

这会导致 **post/wait 节点的行号映射到错误的函数**，进而导致：

- 信号量依赖边建错或缺失
- 段 DAG 中 sem 边丢失
- 分块结果错误

适配方案：

- 改为取 `倒数第二段` 或更准确的"直接父函数实例"
- 或者在 `mycalls_meta_internal.json` 中显式记录 owner 函数名，不再从节点名推断

**风险：高。这是最关键的断裂点之一。**

### 23.2 `level2/segment_dag_level2.py` — `_fallback_edges_from_dot()`

当前代码：

```python

    # 只保留 src 含 '/' 且 dst 不含 '/' 的边
    for raw in dot_path.read_text(...).splitlines():
        m = _DOT_EDGE_RE.match(raw)
        ...
        src_node, dst_node = m.group(1), m.group(2)
        if "/" not in src_node:
            continue
        if "/" in dst_node:
            continue
        src_fn = _owner_from_dot_node(src_node)
        dst_fn = dst_node
```

影响（严重）：

当前假设：

- `src` 含 `/` = 调用点节点（callsite）
- `dst` 不含 `/` = 被调函数节点（callee）

新命名下：

- callee 也可能变成 `main/worker_c2#1` 这种含 `/` 的形式
- 那么 `if "/" in dst_node: continue` 会把所有 callee 边都过滤掉
- 结果：**回退边全部丢失**

适配方案：

- 不再用 `/` 有无来区分 callsite vs callee
- 改为用节点元数据中的 `kind` 字段

**风险：高。**

### 23.3 `level2/segment_dag_level2.py` — `circle.txt` 中的 post/wait 节点名匹配

- `node_owner_line` 查找失败
- **信号量依赖边丢失**

适配方案：

- `circle.txt` 和 `dag.dot` 必须同步更新
- 两者的节点名来自同一个生成源

**风险：中高。只要确保同步即可，但漏了就很难排查。**

## 25. 核心矛盾：`/` 的含义发生了根本性变化

**这是整个影响分析中最核心的一个结论。**

当前系统中，`/` 的含义是固定的：

- `函数名/调用点名+序号`
- 第一段 = 拥有者函数 = 所属线程

改动后，`/` 的含义变成了：

- `调用路径层级分隔符`
- 第一段 = 根调用者（通常都是 `main`）
- 中间各段 = 调用链上的各级实例
- 最后一段 = 当前节点

也就是说：

| | 旧含义 | 新含义 |
|--|--------|--------|
| 第一个 `/` 之前 | 直接拥有者函数名 | 根入口（`main`） |
| 最后一个 `/` 之后 | 调用点名 + 序号 | 当前节点名 |
| 总层级数 | 固定 1-2 层 | 可能 N 层 |
| 无 `/` 的节点 | 独立函数名/callee | 不一定存在 |

这意味着：

- 所有用 `split("/", 1)[0]` 提取"线程/拥有者"的代码都需要改
- 所有用 `"/" in node` 判断"是不是调用点"的代码都需要改
- 所有用 `"/" not in node` 判断"是不是独立函数"的代码都需要改

## 30. 当前 `instfunctions` 实现的根本性缺陷

### 30.1 全局计数器而非按调用者计数

当前 `instfunctions`（`generation/legacy.py`）使用一个**全局** `seen` 字典跨所有函数统计调用次数：

```python
seen = defaultdict(int)

for fn, finfo in functions.items():
    for call in mycalls:
        if call in clones:
            seen[call] += 1
            idx = seen[call]
            if idx > 1:
                inst_list = clones[call]
                inst_idx = min(idx - 2, len(inst_list) - 1)
                target = inst_list[inst_idx]
```

这意味着如果 `main` 调用了 `foo` 两次，`bar` 也调用了 `foo` 一次，那么实例分配取决于**字典遍历顺序**（`sorted(functions.keys())`），而不是按每个调用者独立编号。

具体问题：

- `main` 第 1 次调用 `foo` → 保留原名 `foo`
- `main` 第 2 次调用 `foo` → 变成 `foo@instance1`
- `bar` 第 1 次调用 `foo` → 变成 `foo@instance2`（全局第 3 次）

但语义上 `bar` 的 `foo` 应该是该调用者下的第 1 次，与 `main` 无关。

### 30.2 实例数量夹顶

当一个函数的实际调用次数超过 `cnt - 1` 时，代码会把多余的调用全部映射到最后一个实例：

```python
inst_idx = min(idx - 2, len(inst_list) - 1)
```

这导致多个不同调用点共享同一个实例节点，DAG 中这些调用边会汇聚到同一个节点，产生虚假的依赖关系。

### 30.3 深拷贝的浪费

`copy.deepcopy(functions[fn])` 复制了整个函数的 `mycalls`、`mycalls_meta`、`myinfo` 等，但实际上这些实例的函数体内容完全相同——只是调用者不同。升级后应改为"保留模板 + 按路径展开"的方式，避免无谓的深拷贝。

### 30.4 `@instance` 后缀与路径分隔符 `/` 的语义冲突

当前 `@instanceN` 后缀不含 `/`，因此不会与路径分隔符冲突。但如果实例化后的函数内部又有调用点（如 `foo@instance1/bar7`），`/` 的语义已经混乱——`foo@instance1` 应该是调用者，但下游代码用 `split("/", 1)[0]` 取到的却是 `foo@instance1`（含 `@` 符号），这个值在 `functions` 字典里可能找不到对应条目（如果 `@instance` 后缀是后加的）。

## 31. `mycalls` 序列就是事实上的"函数模板"

### 31.1 当前模板的隐含结构

文档第 8 节提出了"函数模板"的概念，但实际上当前代码中 **`functions[fn]["mycalls"]` 就是事实上的模板**：

- 它是一个**有序列表**，记录了函数体内所有调用的目标名
- `full_call_graph` 通过 `while idx < len(callers)` 按顺序扫描它来画边
- `mycalls_meta` 提供每个调用点的元信息（文件、行号、是否 extern）
- `myinfo` 记录 `pthread_create`/`pthread_join` 的句柄绑定和 `tail` 节点

因此，升级时的"函数模板"不需要从零设计——可以基于现有的 `mycalls` + `mycalls_meta` + `myinfo` 结构进行规范化抽取。

### 31.2 模板中的控制流前缀

当前 `mycalls` 中的条目可能携带控制流前缀：

- `while/pthread_mutex_lock5`
- `if/sem_wait3`
- `switch1/case_handler`

这些前缀是在 RTL 解析阶段通过状态机（`state_2`、`state_4`、`state_6`）加上去的。它们会出现在模板的调用列表中，也会传递到 DOT 节点名中。

升级时必须决定：**控制流前缀是模板的一部分，还是展开时动态添加的？**

建议：将控制流前缀作为操作模板的一个字段（如 `control_flow_context`），而不是拼在节点名字符串中。

---

## 32. 控制流前缀与多级路径的交互

### 32.1 当前的控制流命名

RTL 解析阶段会根据控制流状态给调用点加前缀：

```python
if add_condition_prefix:
    if state_2 == 1:
        target = "while/" + target
    elif state_4 == 1:
        target = "if/" + target
    elif state_6 == 1:
        target = "switch" + str(switch_count) + "/" + target
```

这意味着当前一个调用点的完整名可能是 `main/while/pthread_mutex_lock5`（已经有两级 `/`）。

### 32.2 多级实例化后的路径爆炸

如果升级为完整调用路径实例化，且保留控制流前缀，一个节点的 ID 可能变成：

```
main/worker_c2#1/while/helper#2/if/busy_wait_seconds#1/clock_gettime#1
```

这会导致：

1. **`/` 的层级含义不确定**——有些 `/` 分隔的是调用实例层级，有些分隔的是控制流上下文
2. **下游解析更加困难**——无法通过 `/` 计数或位置判断语义
3. **DOT 渲染标签过长**——节点显示文本难以阅读

### 32.3 建议方案

将控制流上下文从路径分隔符中剥离出来：

- 方案 A：用不同的分隔符，如 `main/worker_c2#1/{while}pthread_mutex_lock5`
- 方案 B：完全移除路径中的控制流前缀，改为存储在节点元数据的 `control_flow` 字段中
- 方案 C：只在 `display_name` 中保留控制流信息，`node_id` 中不体现

**推荐方案 B**：路径中只保留调用层级，控制流信息放在元数据中。这样 `/` 的语义就是纯粹的"调用层级分隔"，解析逻辑更清晰。

## 33. 外部函数节点的命名统一

### 33.1 当前的双轨命名

RTL 解析阶段对被调函数有两种处理方式：

```python
if origin_target not in functions:
    target = function_name + "/" + target + str(count)
```

- **项目内函数**（在 `functions` 字典中）：保留原名（如 `busy_wait_seconds`），后续由 `instfunctions` 添加 `@instance` 后缀
- **外部函数**（不在 `functions` 字典中）：直接生成 `调用者/函数名+序号` 格式（如 `main/pthread_mutex_lock5`）

这两种命名方式在升级后必须统一到同一套路径规则中。

### 33.2 统一方案

升级后，所有节点（包括外部函数调用点）都应遵循：

```
实例路径/节点名
```

例如：
- 外部调用：`main/worker_c2#1/pthread_mutex_lock5`（`pthread_mutex_lock5` 是该实例内部的调用点名）
- 项目内调用：`main/worker_c2#1/busy_wait_seconds#2`（`busy_wait_seconds#2` 是子函数实例）

区别在于：
- 外部调用的节点是**叶节点**（不会再递归展开）
- 项目内调用的节点是**可展开实例**（会继续递归生成子节点）

这个区别应通过元数据的 `kind` 字段表达（`callsite` vs `function_instance`），而非节点名格式。

## 34. `full_call_graph` 的根本性重构

### 34.1 当前架构：按函数独立绘图

当前 `full_call_graph` 的核心循环是：

```python
for func in sorted(functions.keys()):
    callers = functions[func].get("mycalls", [])
    pre = func  # 每个函数的"上一节点"初始化为函数名自身
    while idx < len(callers):
        # 画 pre -> caller 的边
        # 处理 pthread_create 的分叉
        # 处理 if/while/switch 的虚线框
        pre = caller
```

这种"逐函数、逐调用点"的画图方式在多级实例化后**完全不适用**，因为：

1. 同一个函数模板可能被展开为多个实例，每个实例的边应该独立
2. 父实例到子实例的入口/出口边需要跨越函数边界
3. 线程 fork/join 的边需要在全局实例图上建立

### 34.2 新架构：递归展开器

升级后应改为单一入口的递归展开：

```
expand_instance(template_db, parent_path, function_name, graph) -> exit_nodes
    1. 为该函数实例创建入口节点
    2. 遍历 template_db[function_name].ops
    3. 对每个操作：
       - 外部调用 → 创建叶节点，连边
       - 项目内调用 → 递归 expand_instance，连入口/出口边
       - pthread_create → 启动并行分支
       - pthread_join → 连接线程出口
    4. 创建 __exit__ 虚拟出口节点
    5. 返回出口信息
```

这要求 **`functions` 字典在展开过程中保持不变**（作为模板），展开结果写入独立的实例图数据结构。

### 34.3 `conditions_call_graph` 同步问题

文件中还有一个平行的 `conditions_call_graph` 函数，它也画调用图，但只画控制流结构。升级时如果只改 `full_call_graph` 而忘记同步 `conditions_call_graph`，会导致两者产出不一致。

建议：将两者合并为一个统一的展开器，通过参数控制输出粒度。

## 35. 线程绑定解析链的完整追踪

### 35.1 当前的线程信息流

从源码到最终 DAG，线程信息经过以下环节：

```
RTL 解析（legacy.py 主循环）
  ↓ _resolve_symbol_from_reg_history() → 寄存器回溯找线程入口函数
  ↓ 失败时 → create_targets_from_source() → 源码正则解析
  ↓
myinfo 字典写入：
  myinfo[create_node_name] = thread_entry_function
  myinfo[join_node_name] = handle_variable
  myinfo["tail"] = last_node_name
  ↓
instfunctions()
  ↓ 克隆函数时 myinfo 被 deepcopy，但键名没有更新
  ↓
_fixup_create_join_bindings_from_source()
  ↓ 从 C 源码重新解析 create/join 参数，修补缺失的绑定
  ↓
build_join_binding_map()
  ↓ 构建 handle→entry、entry→tail、handle→join 的全局映射
  ↓
append_join_edges()
  ↓ 在 DOT 中添加 tail→join 的边
```

### 35.2 升级后的断裂风险

在多级实例化后，这条链上有多个断裂点：

1. **`myinfo` 的键**：当前用的是 `create_node_name`（如 `main/pthread_create17`），升级后变成 `main/worker_c2#1/pthread_create17`——但 `instfunctions` 的深拷贝不会更新这些键
2. **`build_join_binding_map` 的全局性**：当前假设每个 handle 只绑定一个 entry，但多实例后同一个 handle 变量可能在不同实例中绑定不同的 entry
3. **`tail` 节点的唯一性**：`myinfo["tail"]` 记录的是模板中的最后一个节点名，克隆后所有实例共享同一个 tail 名——与文档第 15 节的 `__exit__` 方案冲突

### 35.3 建议

将线程绑定信息从 `myinfo` 中独立出来，改为在展开阶段动态构建：

- 展开时遇到 `pthread_create` → 记录 `(parent_instance, handle_key, entry_instance)` 三元组
- 展开时遇到 `pthread_join` → 在活跃线程表中查找并连接
- 不再依赖 `myinfo` 的全局映射

## 36. join 边的双路径问题

### 36.1 当前存在两套 join 边实现

1. **`generation/thread_map.py` 的 `resolve_join_edges`**：在 `full_call_graph` 中原本被调用，但已被**整段注释**（`legacy.py` 第 872-875 行附近）
2. **`legacy.py` 的 `append_join_edges`**：当前实际使用的路径，在所有函数画完后统一追加 `tail → join` 边

这两套实现的差异：

- `resolve_join_edges` 是在画每个函数时，遇到 join 节点就立刻画边
- `append_join_edges` 是在全部函数画完后，根据 `build_join_binding_map` 的结果批量追加

### 36.2 升级建议

递归展开模式下，join 边应在展开 `pthread_join` 操作时就建立：

1. 从活跃线程表中找到对应的线程实例
2. 获取该实例的 `__exit__` 节点
3. 立即建立 `__exit__ → join_node` 的边
4. 标记该线程为 `joined`

不再需要后置的 `append_join_edges`，因为所有信息在展开时已经可用。

## 37. `circle.txt` 的生成与消费的完整追踪

### 37.1 生成侧

`circle.txt` 由 `generation/exporters.py` 中的 `export_circle_txt` 生成。它使用 `_parse_node_name` 解析每个节点的 API 类型和序号，然后按 `sem_post`/`sem_wait`/`pthread_mutex_lock`/`pthread_mutex_unlock` 分类输出。

### 37.2 消费侧

- **`level2/segment_dag_level2.py` 的 `_parse_circle_sem_pairs`**：读取"信号量"区块，提取 `(post_node, wait_node)` 对
- **`pipeline/collector.py`**：也有类似的信号量解析逻辑
- **`visualization/viewer.py` 的 `_parse_semaphore_pairs`**：在可视化中用于画信号量依赖边

### 37.3 同步风险

升级后，`export_circle_txt` 输出的节点名格式变了（如 `main/worker_c2#1/sem_post9`），但三个消费侧都是用字符串匹配 `"sem_post" in node` 来判断类型——这个逻辑不会出错。

真正的风险在于：`_parse_circle_sem_pairs` 拿到节点名后，会去 `node_owner_line` 字典中查找：

```python
post = node_owner_line.get(post_node)
```

如果 `node_owner_line` 是从 `mycalls_meta_internal.json` 构建的，而 `circle.txt` 是从 `mycalls_meta`（可能是不同的数据源）生成的，两者的节点名必须**完全一致**。

**最安全的做法**：让 `circle.txt` 和 `mycalls_meta_internal.json` 从同一个数据源生成，而不是各自独立解析。

## 38. `scheduler.py` 权重对齐的隐含风险

### 38.1 当前的对齐机制

`scheduler.py` 的 `load_time_result_weights` 直接使用 `time_result.json` 的顶层 key 作为节点权重：

```python
for k, v in data.items():
    out[str(k)] = int(v.get("total_ns", 0) or 0)
```

然后在 `longest_path_dag` 和 `compute_cpc_priorities` 中，用这些 key 与 DOT 解析出的节点名做匹配。

### 38.2 升级后的对齐问题

`time_result.json` 的 key 来自 `time_analysis.py` 的插桩标签 `time_account("{key_str}", ...)`。这里的 `key_str` 就是 `site.raw_key`，即 `mycalls_meta_internal.json` 中的节点名。

升级后，这些 key 变成了多级路径格式。只要 `time_result.json`、`dag.dot`、`mycalls_meta_internal.json` 三者使用同一套节点名，对齐就不会出问题。

但如果中间经过了 `filter_dot.py` 处理（它会修改 DOT 中的节点名），就可能导致 DOT 节点名与 `time_result.json` 的 key 不一致。

### 38.3 建议

将 `filter_dot.py` 的节点名清洗逻辑改为只修改 `display_name`（DOT 的 `label` 属性），而不修改节点的唯一 ID。或者在 `dag_meta.json` 中记录原始 ID 到清洗后名称的映射。

## 39. `source_only.py` 的平行命名体系

### 39.1 独立的命名逻辑

`source_only.py` 有自己的一套独立命名逻辑：

```python
if raw_target in defined:
    pending_target = raw_target
else:
    call_counter[current_fn] = call_counter.get(current_fn, 0) + 1
    pending_target = f"{current_fn}/{raw_target}{call_counter[current_fn]}"
```

这与 `legacy.py` 的命名逻辑**不一致**：

- `source_only.py`：用 `call_counter[current_fn]` 按**当前函数**计数（局部计数器）
- `legacy.py`：用全局 `count` 变量（全局计数器），且对已定义函数不加前缀

### 39.2 升级建议

升级后 `source_only.py` 也需要采用统一的实例路径命名。由于 `source_only.py` 生成的是简化版 DAG（只含指定源文件的调用边），可以复用核心展开器，但限制展开范围为指定源文件内的函数。

## 40. Level1 create-to-entry 映射的顺序依赖

### 40.1 当前的脆弱假设

`level1/segment_dag.py` 的 `_build_create_node_to_entry_fn` 依赖 `mycalls` 的相邻元素关系：

```python
if _CREATE_NODE_RE.search(node):
    entry = callers[i + 1] if i + 1 < len(callers) else None
    if isinstance(entry, str) and entry in functions_full:
        mapping[node] = entry
```

这意味着：`pthread_create` 节点的下一个 `mycalls` 条目必须是线程入口函数名。

### 40.2 升级后的风险

在 `legacy.py` 的解析阶段，`pthread_create` 后面确实会追加 `resolved_target`（线程入口函数名）。但升级为多级实例后：

1. `mycalls` 中的线程入口函数名会变成实例名（如 `worker_c2#1`），在 `functions_full` 中可能找不到
2. 如果模板中保留原名 `worker_c2`，但展开后产生 `main/worker_c2#1`，Level1 的查找逻辑需要适配

### 40.3 建议

不再依赖 `mycalls` 的相邻元素推断 create→entry 映射，而是在模板的操作结构中显式记录：

```python
Op(kind="pthread_create", handle="thread_c2", entry_function="worker_c2", ...)
```

## 41. `filter_dot.py` 对节点名的破坏性修改

### 41.1 当前的清洗逻辑

`filter_dot.py` 的 `simplify_node` 会对每个节点名的每一段执行 `clean_symbol`：

```python
def simplify_node(node: str) -> str:
    parts = [clean_symbol(p) for p in node.split("/")]
    return "/".join(parts)
```

`clean_symbol` 会：
- 去掉 `_thunk.` 前缀
- 去掉 `.isra.0`、`.part.0` 等后缀
- 去掉 C++ 函数签名中的括号和参数

### 41.2 多级路径下的风险

如果节点名是 `main/worker_c2#1/busy_wait_seconds#2`，`clean_symbol` 对 `worker_c2#1` 的处理取决于正则：

```python
SUFFIX_RE = re.compile(r"\.\d+$")
```

`#1` 不会被这个正则匹配（因为用的是 `.` 不是 `#`），所以不会被误删。但如果 `clean_symbol` 的正则未来被扩展，或者某些 C++ 模板名中包含 `#`，就可能出问题。

### 41.3 建议

`filter_dot.py` 应该在展开器生成 DOT 之后运行，且只修改 DOT 节点的 `label` 属性，不修改节点 ID。节点 ID 应保持为原始的实例路径，label 可以是清洗后的短名称。

## 42. DOT 渲染与显示策略的深入考量

### 42.1 节点标签长度问题

多级路径作为节点 ID 在 DOT 中会导致极长的标签。例如：

```
"main/worker_c2#1/helper_func#3/inner_call#1/pthread_mutex_lock5"
```

Graphviz 渲染这样的长标签会使节点框非常宽，图整体布局被拉伸。

### 42.2 分层显示建议

建议在 DOT 输出时，节点使用完整路径作为 ID（确保唯一性），但 `label` 使用短名称：

```dot
"main/worker_c2#1/pthread_mutex_lock5" [label="pthread_mutex_lock5"];
```

或者使用分层的 `display_name`：

```dot
"main/worker_c2#1/pthread_mutex_lock5" [label="worker_c2#1\npthread_mutex_lock5"];
```

### 42.3 子图聚合

可以利用 DOT 的 `subgraph cluster_` 语法，将同一个函数实例内的所有节点包含在一个子图中：

```dot
subgraph cluster_main_worker_c2_1 {
    label="worker_c2#1";
    "main/worker_c2#1/pthread_mutex_lock5";
    "main/worker_c2#1/sem_wait4";
    "main/worker_c2#1/busy_wait_seconds#2";
}
```

这样可视化效果更好，也能清晰展示调用层级关系。但需要注意 Graphviz 对嵌套 cluster 的布局支持有限，深层嵌套可能导致布局问题。

## 43. `myinfo` 字典的键值不对称性

### 43.1 当前结构

`myinfo` 是一个混合用途的字典，同时存储了多种信息：

```python
myinfo = {
    "main/pthread_create17": "worker_c2",      # create节点 → 线程入口函数名
    "main/pthread_join43":   "thread_c2",       # join节点 → 句柄变量名
    "tail":                  "main/sem_post9",  # 函数最后一个节点
    "thread_c2":             "worker_c2",       # 句柄变量 → 线程入口函数名
}
```

**键**既可能是节点名（带 `/` 前缀），也可能是句柄变量名（纯字符串），还有固定的 `"tail"` 键。

**值**既可能是函数名，也可能是变量名，也可能是节点名。

### 43.2 升级后的混乱

多级实例化后，节点名变成长路径，但句柄变量名和函数名仍然是短字符串。`myinfo` 中的键和值的格式差异更大：

```python
myinfo = {
    "main/worker_c2#1/pthread_create17": "helper_func",   # 长路径 → 短名
    "main/worker_c2#1/pthread_join5":    "thread_h1",     # 长路径 → 短名
    "tail":                              "main/worker_c2#1/sem_post9",  # 固定键 → 长路径
    "thread_h1":                         "helper_func",   # 短名 → 短名
}
```

### 43.3 建议

将 `myinfo` 拆分为多个专用数据结构：

- `create_bindings`: `Dict[str, CreateInfo]`（create 节点 → 线程信息）
- `join_bindings`: `Dict[str, str]`（join 节点 → 句柄变量）
- `handle_to_entry`: `Dict[str, str]`（句柄变量 → 入口函数）
- `tail_node`: `Optional[str]`（尾节点名）

这与文档第 8.4 节的建议一致，但这里强调的是**必须先拆解 `myinfo`**，否则后续的展开逻辑无法正确消费。

## 44. `conditions_call_graph` 与 `full_call_graph` 的同步

### 44.1 当前的平行实现

`legacy.py` 中有两个独立的图生成函数：

- `full_call_graph`：生成完整的 DAG（包含所有调用边和线程边）
- `conditions_call_graph`：只生成控制流结构（`if`/`while`/`switch` 虚线框 + 内部调用）

两者共享 `functions` 字典，但各自维护独立的边绘制逻辑。

### 44.2 升级时的同步需求

如果只升级 `full_call_graph` 而不升级 `conditions_call_graph`，会导致：

1. 两种视图使用不同的节点名格式
2. 用户在 GUI 中切换视图时看到不一致的图
3. 如果有下游工具同时消费两种 DOT 文件，会产生节点名不匹配

### 44.3 建议

将两者统一为一个核心展开器，通过配置参数控制输出内容：

```python
def expand_instance_graph(
    template_db,
    root_function="main",
    include_conditions=True,      # 是否包含 if/while/switch 虚线框
    include_thread_edges=True,    # 是否包含 create/join 边
    include_extern_calls=True,    # 是否包含外部函数调用点
    ...
)
```

## 46. 向后兼容与迁移

### 46.1 现有中间结果的处理

`中间结果/` 目录下存储了大量已生成的 `dag.dot`、`mycalls_meta_internal.json`、`circle.txt` 等文件，使用的是旧格式节点名。

升级后的代码需要：

1. 能**识别**旧格式并给出明确提示（如"检测到旧格式，请重新运行生成阶段"）
2. 或者能**自动转换**旧格式到新格式（但这增加了复杂度，不推荐）
3. 至少不能**静默失败**——如果旧格式数据导致节点名不匹配，应抛出有意义的异常

### 46.2 格式版本标记

建议在所有生成的 JSON 文件中添加版本标记：

```json
{
  "__format_version__": "2.0",
  "__generator__": "Code2DAG",
  ...
}
```

下游消费时检查版本号，如果版本不匹配则提前报错。

### 46.3 配置文件迁移

`配置文件/` 目录下的配置可能引用了旧的函数名或节点名。需要确认配置文件中是否包含节点名相关的硬编码。

## 47. 递归展开的边界条件

### 47.1 直接递归

```c
void foo() {
    foo();  // 直接递归
}
```

展开时会产生无限递归。必须设置最大展开深度（如 `MAX_RECURSION_DEPTH = 3`），超限时生成一个虚拟截断节点：

```
main/foo#1/foo#1/foo#1/__recursion_limit__
```

### 47.2 间接递归

```c
void foo() { bar(); }
void bar() { foo(); }
```

需要在展开栈中维护一个"已在展开中"的函数集合，检测到回边时截断。

### 47.3 条件递归

```c
void foo(int n) {
    if (n > 0) foo(n - 1);
}
```

当前系统不做条件分析，因此**必须假设所有调用都会发生**，用深度限制兜底。

### 47.4 多路径递归

```c
void foo() {
    if (cond) foo();  // 路径 A
    else bar();
    foo();             // 路径 B
}
```

同一函数中可能有多个递归调用点，每个都需要独立编号和独立的深度检查。

### 47.5 建议的递归处理策略

```python
def expand_instance(templates, parent_path, func_name, graph, expanding_stack, depth=0):
    if depth > MAX_RECURSION_DEPTH:
        node_id = f"{parent_path}/__recursion_limit__"
        graph.add_node(node_id, kind="recursion_limit", template=func_name)
        return [node_id]

    if func_name in expanding_stack:
        node_id = f"{parent_path}/__cycle__{func_name}__"
        graph.add_node(node_id, kind="cycle_back_edge", template=func_name)
        return [node_id]

    expanding_stack.add(func_name)
    # ... 正常展开 ...
    expanding_stack.remove(func_name)
```

## 48. 性能考量

### 48.1 节点数膨胀

多级实例化会显著增加节点数。假设：

- `main` 调用 `worker` 4 次
- 每个 `worker` 调用 `helper` 3 次
- 每个 `helper` 内有 5 个调用点

则总节点数约为：`1(main) + 4(worker) + 4×3(helper) + 4×3×5(调用点) = 1 + 4 + 12 + 60 = 77`

相比旧方案的 `1 + 1 + 1 + 5 = 8` 个节点（所有实例共享同一节点），增长了约 10 倍。

对于更深的调用链或更多的调用次数，增长会更快。

### 48.2 DOT 渲染性能

Graphviz 对超过 500 个节点的图渲染会明显变慢，超过 2000 个节点可能需要数分钟。

建议：
- 提供"折叠深度"参数，允许用户控制展开层数
- 超过阈值时自动切换为分层视图（每层一个独立的 DOT 文件）
- 在 `dag_meta.json` 中记录完整的实例图，但 DOT 可以是折叠后的摘要视图

### 48.3 JSON 文件大小

`mycalls_meta_internal.json` 的 key 从短名（`sem_wait4`）变成长路径（`main/worker_c2#1/sem_wait4`），文件大小会增长。对于大型项目，这可能影响 JSON 的加载速度。

建议：使用紧凑的 JSON 输出（去掉不必要的缩进），或者考虑在 `dag_meta.json` 中使用整数 ID 索引代替长字符串。

## 49. 被文档遗漏的下游消费点

### 49.1 `pipeline/collector.py` 中的互斥正则

```python
_MU_LOCK_RE = re.compile(r"(^|/)pthread_mutex_lock(\d+)?$")
_MU_UNLOCK_RE = re.compile(r"(^|/)pthread_mutex_unlock(\d+)?$")
```

这些正则与 Level2 的正则格式一致，在新命名下仍然能匹配（因为用了 `(^|/)` 前缀匹配）。但它们的结果会与 `node_owner_line` 查找联动——如果 owner 推断出错，这里也会跟着错。

风险：**中等。** 本身正则没问题，但依赖的上游数据可能出问题。

### 49.2 `scheduler.py` 中的节点名完全匹配

`apply_priorities_to_dot` 通过正则逐行匹配 DOT 文件中的节点名，将优先级写入节点属性。匹配方式是**精确字符串比较**：

```python
for m in _NODE_STMT_RE.finditer(line):
    name = m.group("name")
    if name in priorities:
        ...
```

只要 DOT 中的节点名与 `priorities` 字典的 key 格式一致就没问题。但如果有任何中间环节修改了节点名（如 `filter_dot.py`），就会断裂。

风险：**中等。** 需确保优先级写入在 DOT 过滤之后，或者优先级字典也做同步过滤。

### 49.3 `source_binder.py` 中的 C 文件扩展名硬编码

```python
_SRC_LOC_RE = re.compile(r'"(?P<src>[^"\n]+\.c)":(?P<line>\d+):')
```

只匹配 `.c` 文件，不支持 `.cpp`、`.cc` 等。如果升级后要支持 C++ 项目，这个正则需要扩展。

风险：**低（当前项目只用 C）。** 但作为升级项目应考虑扩展性。

### 49.4 `generation/renderer.py` 中的 `_is_excluded` 整名匹配

```python
def _is_excluded(self, name: str) -> bool:
    return bool(self._exclude_regex and self._exclude_regex.match(name))
```

使用 `match`（从字符串开头匹配）而非 `search`。如果排除规则是 `__stack_chk_fail`，新命名下的 `main/worker_c2#1/__stack_chk_fail3` **不会被匹配**（因为开头是 `main`）。

风险：**中等。** 需改为 `search` 或对路径最后一段做匹配。

## 51. 第三部分总结

### 51.1 比文档前两部分更深层的发现

1. **`instfunctions` 的全局计数器是一个已有的 bug**（第 30 节），升级时应一并修复而非延续
2. **控制流前缀（`while/`、`if/`）会与多级路径产生语义冲突**（第 32 节），必须从路径中剥离
3. **`myinfo` 字典的混合用途是下游逻辑脆弱性的根源**（第 43 节），必须在升级中拆解
4. **`full_call_graph` 不是可以"修补"的——它需要从根本上重写**（第 34 节）
5. **存在至少 4 个平行的命名体系**（`legacy.py`、`source_only.py`、`filter_dot.py`、`Level1 seg_id`），升级必须统一前三者
6. **join 边存在两套实现**（第 36 节），升级应合并为一套
7. **`circle.txt` 的生成和消费链涉及 3 个独立模块**（第 37 节），必须确保三者同步

### 51.2 核心设计决策清单

在开始编码前，必须先确定以下设计决策：

| 编号 | 决策点 | 选项 |
|------|--------|------|
| D-1 | 控制流前缀是否保留在路径中 | A: 保留 / B: 移到元数据 / C: 完全去除 |
| D-2 | 最大递归展开深度 | 建议 3-5 层 |
| D-3 | `__exit__` 虚拟节点是否始终生成 | A: 始终生成 / B: 仅多出口时生成 |
| D-4 | DOT 节点 label 策略 | A: 完整路径 / B: 最后两段 / C: 只显示最后一段 |
| D-5 | 旧格式兼容 | A: 自动检测降级 / B: 强制报错要求重新生成 |
| D-6 | `dag_meta.json` 是否强制要求 | A: 下游必须有 meta 才能运行 / B: 无 meta 时回退到字符串解析 |
| D-7 | 节点数膨胀超限处理 | A: 警告但继续 / B: 自动折叠深层 / C: 报错终止 |
