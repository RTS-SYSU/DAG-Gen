# 权值调整实验

## 实验目标

通过调整权重常量，改变各 DAG 节点的执行时间，从而影响 4 个调度算法（heft、t_level、wcet_first、zhao2020）生成的优先级排序，最终使这 4 个算法的实际运行时间（avg_s）优于 CFS 和 FIFO 两个对照组。

- cpf 和 lpf 不参与本实验比较
- DAG 拓扑结构保持不变
- 绑核 6、7（2 核）
- 目标运行时间：ws=100 下约 2~3 秒

## 实验流程

改 zhang2.c 的 C1~C15 → 重跑 pipeline run_all → 重跑 runtime_compare

## DAG 结构分析

zhang2 的 DAG 拓扑（4 线程：main + worker_c0 + worker_c1 + worker_c2）：

```
main#001 (C8) ──┬──→ main#002 (C9) → main#003 (C10) ──┬──→ main#004 (C11) → main#005 (C12) ──┬──→ main#006 (C13) → main#007 (C14) → main#008 (C15)
                ├──→ worker_c0#001 (C7) ───────────────┘                                       │
                ├──→ worker_c1#001 (C4) → worker_c1#002 (C5) ─────────────────────────────────→┘ (→ main#006)
                └──→ worker_c2#001 (C1) ──→ worker_c2#002 (C2) ──→ worker_c2#003 (C3) ──────────→ main#008
                                           ↑(from main#003)        ↑(from main#005)
```

跨线程依赖边：
- main#001 → worker_c0, worker_c1, worker_c2（fork）
- worker_c0 → main#004（join）
- main#003 → worker_c2#002, worker_c1#002（触发）
- main#005 → worker_c2#003（触发）
- worker_c1#002 → main#006（join）
- worker_c2#003 → main#008（join）

### 基线权重问题诊断

原始权重：C8=40, C9=80, C10=100, C11=2000, C12=120, C13=1000, C14=1000, C15=2

- 主链总计算量 = 4342，worker 分支最重的也只有 ~1040
- C11=2000 远大于任何 worker 分支，worker 总能在 main 等它之前完成
- 调度顺序无关紧要，所有算法表现趋同

## 第一轮权重调整方案

### 设计思路

制造**调度决策点**——多个就绪任务竞争 2 个核心，且选错会导致关键路径被阻塞：

1. 让 worker 分支上有重任务（C5=400, C3=300, C2=200），使 worker 不再是"轻量附属"
2. 降低主链中间段的权重（C11: 2000→100），避免主链独占时间
3. 在 fork 后制造 3 任务竞争 2 核的局面

### 具体权重

| 常量 | 原值 | 新值 | 对应节点 | 调整理由 |
|------|------|------|---------|---------|
| C1 | 20.0 | 15.0 | worker_c2#001 | 轻，快速进入等待触发状态 |
| C2 | 20.0 | 200.0 | worker_c2#002 | **大幅增加**，被 main#003 触发后的关键任务 |
| C3 | 1000.0 | 300.0 | worker_c2#003 | 调整为中重，被 main#005 触发，main#008 等它 |
| C4 | 20.0 | 15.0 | worker_c1#001 | 轻，快速进入等待触发状态 |
| C5 | 1000.0 | 400.0 | worker_c1#002 | **最重的 worker 任务**，main#006 等它完成 |
| C6 | 20.0 | 20.0 | (未使用) | 保持不变 |
| C7 | 80.0 | 50.0 | worker_c0#001 | 中等，main#004 等它 |
| C8 | 40.0 | 30.0 | main#001 | 轻，初始化+fork |
| C9 | 80.0 | 40.0 | main#002 | 轻 |
| C10 | 100.0 | 50.0 | main#003 | 中等，完成后触发 worker_c1#002 和 worker_c2#002 |
| C11 | 2000.0 | 100.0 | main#004 | **大幅降低**，不再独占时间 |
| C12 | 120.0 | 50.0 | main#005 | 中等，完成后触发 worker_c2#003 |
| C13 | 1000.0 | 80.0 | main#006 | 中等，等 worker_c1#002 后执行 |
| C14 | 1000.0 | 80.0 | main#007 | 中等 |
| C15 | 2.0 | 5.0 | main#008 | 轻，等 worker_c2#003 后执行 |

### 关键调度竞争点分析

| 竞争点 | 就绪任务 | 正确选择 | 错误选择的代价 |
|--------|---------|---------|--------------|
| main#003 完成后 | main#004(100), worker_c1#002(400), worker_c2#002(200) | 优先 worker_c1#002（关键路径最长） | main#006 多等数百单位 |
| main#005 完成后 | main#006(等worker_c1), worker_c2#003(300) | 优先 worker_c2#003（main#008 等它） | main#008 多等 |

### 时间估算（ws=100，每单位 C ≈ 0.37ms）

- 最优调度 makespan：~735 单位 ≈ **2.7s**
- CFS/FIFO 错误调度：~900+ 单位 ≈ **3.3s+**
- 预期差距：**15~25%**

### 为什么 CFS/FIFO 会选错

- **CFS**：按时间片轮转，不感知 DAG 依赖，会均匀分配 CPU 给所有就绪线程
- **FIFO（同优先级99）**：按创建顺序调度，main 线程先运行所以优先跑 main 而不是 worker

### 为什么 4 个算法能选对

- **heft**：rank_u 计算会识别出 worker_c1#002 的后继路径更长，给予更高优先级
- **zhao2020**：关键路径分析会将 worker 分支的 provider 正确排序
- **wcet_first**：worker_c1#002(400) 是最重任务，自然获得最高优先级
- **t_level**：拓扑层级会让被依赖的 worker 任务获得合理优先级

#### zhang2 Trace 分析（实际运行时间线）

通过在每个 MU 块前后插入 `clock_gettime` 时间戳，精确观测了 CFS/FIFO/heft/zhao2020 四种模式下的线程执行时间线（ws=100, taskset 6,7）。

**总时间对比**：

| 模式 | 总时间 | 与 CFS 差距 |
|------|--------|------------|
| CFS | 679ms | 基准 |
| FIFO | 746ms | +10% |
| heft | 839ms | +24% |
| zhao2020 | 758ms | +12% |

**CFS 时间线（679ms）**：
```
[  0.5ms] main BEGIN C8=30 (c2 blocked on mutex_01)
[  0.6ms] c0 BEGIN C7=50        ← main+c0 并行
[ 22ms]   c1 BEGIN C4=15        ← c1 也启动了
[ 78ms]   c1 END C4, wait(s1)   ← c1 很快完成第一段，阻塞等 sem
[ 93ms]   main END C8, release c2 → c2 BEGIN C1=15
[100ms]   c0 END C7 → main GOT mutex_07, BEGIN C9=40
[111ms]   c2 END C1, wait(s2)
[145ms]   main END C9, BEGIN C10=50
[191ms]   main END C10, post(s1,s2) → c1 BEGIN C5=400, c2 BEGIN C2=200
          ★ 竞争点开始: main(C11) + c1(C5) + c2(C2) 竞争 2 核
          CFS 轮转: 3 线程都在推进, c2 也能获得 CPU
[266ms]   main END C11, BEGIN C12=50
[304ms]   main END C12, post(s3) → main JOIN c1
          ★ main 退出竞争, c1+c2 各占 1 核
[400ms]   c2 END C2, BEGIN C3=300   ← c2(C3) 在 400ms 就启动了
[543ms]   c1 END C5 → main JOIN c1 DONE
[543ms]   main BEGIN C13=80     ← main+c2 各占 1 核
[603ms]   main END C13, BEGIN C14=80
[623ms]   c2 END C3             ← c2(C3) 只用了 223ms
[663ms]   main END C14, JOIN c2 DONE
[679ms]   main END C15 → DONE
```
CFS 的优势：在竞争窗口（191→304ms）内，CFS 时间片轮转让 3 个线程都能推进。c2 在 191ms 就开始 C2，400ms 开始 C3。c2 启动最早，所以总时间最短。

**FIFO 时间线（746ms，比 CFS 慢 12%）**：
```
FIFO: 所有线程 prio=99（同优先级），按 FIFO 顺序调度

[  0.6ms] main(99) BEGIN C8=30, c0(99) BEGIN C7=50
          ★ main+c0 先创建先运行，c1/c2 排队
[ 98ms]   main END C8, release c2 → main 尝试 lock mutex_07
          c1 BEGIN C4=15（终于获得 CPU）
[124ms]   c1 END C4, wait(s1) → c2 BEGIN C1=15
[131ms]   c0 END C7 → main GOT mutex_07, BEGIN C9=40
[146ms]   c2 END C1, wait(s2)
[183ms]   main END C9, BEGIN C10=50
[236ms]   main END C10, post(s1,s2)
          ★ 竞争点: main(99) + c1(99) + c2(99) 同优先级
          FIFO 按先就绪顺序: main 先跑（它刚 post 完还在运行）
[236ms]   main BEGIN C11=100, c1 BEGIN C5=400
          c2 排在 c1 后面，等 c1 或 main 阻塞才能跑
[327ms]   main END C11, BEGIN C12=50
[369ms]   main END C12, post(s3) → main JOIN c1（main 阻塞）
          ★ c2 终于获得 CPU: c2 BEGIN C2=200
[518ms]   c2 END C2, BEGIN C3=300   ← c2(C3) 在 518ms 才启动（CFS 是 400ms）
[556ms]   c1 END C5 → main JOIN c1 DONE
[556ms]   main BEGIN C13=80
[615ms]   main END C13, BEGIN C14=80
[675ms]   main END C14, JOIN c2...
[742ms]   c2 END C3 → DONE 746ms
```
FIFO 比 CFS 慢的原因：同优先级 FIFO 下，main 在 post(s1,s2) 后继续独占 CPU 跑 C11+C12（236→369ms），c2 被延迟 133ms 才开始 C2。CFS 下 c2 在 206ms 就开始了。c2 是最终瓶颈（C3=300 最后完成），c2 启动越晚总时间越长。

heft 比 CFS 慢的根本原因：
1. **阶段2（291→493ms）**：c1#002(95)+c2#002(93) 独占 2 核，main#004(91) 被完全饿死 202ms，这是最大的时间损失
2. **阶段3（649→835ms）**：c2#003(89) > main#006(88)/main#007(87)，c2 抢占 main，main 的 C13+C14 被拖慢
3. main 被饿死导致 post(s3) 延迟（611ms vs CFS 的 304ms），c2(C3) 启动从 400ms 推迟到 611ms

zhao2020 和 FIFO 几乎一样慢（758 vs 746ms）。原因：zhao2020 给 c2 最低优先级（86~88），c2 在竞争点被完全抢占 144ms。而且 zhao2020 给 main#006/007 很高优先级（95/94），在 c1 完成后 main 抢占 c2(86)，c2(C3) 被进一步拖慢。

**关键发现：zhang2 的同步结构严重限制了调度自由度**

1. **mutex 互斥锁强制串行**：main 持有 mutex_01 阻塞 c2，main 需要 mutex_07 等 c0 完成。这些互斥关系强制了执行顺序，优先级无法改变。

2. **sem 触发点固定**：c1 和 c2 的重任务（C5=400, C2=200, C3=300）必须等 main#003 的 sem_post 才能开始。无论优先级如何，这些任务的启动时间都是 ~190~260ms。

3. **真正的竞争窗口很短**：唯一的竞争点在 sem_post(s1,s2) 之后（~235~493ms），约 250ms 的窗口。在这个窗口内：
   - CFS：3 线程轮转，main 得到约 33% CPU，c2 也在推进
   - heft：c1(95)+c2(93) 抢占 main(91)，main 被饿死 202ms
   - zhao2020：c1(96)+main(90) 抢占 c2(87)，c2 被饿死 144ms
   - FIFO：main 同优先级先跑完 C11+C12 后才让出 CPU 给 c2

4. **最终瓶颈是 c2(C3=300)**：c2 的 C3 是最后完成的任务，它的启动时间决定了总时间。

5. **所有算法都在"帮倒忙"**：
   - heft 让 c1+c2 抢占 main → main 的 post(s3) 延迟 → c2(C3) 启动从 400ms 推迟到 611ms
   - zhao2020 让 c1+main 抢占 c2 → c2(C2) 启动从 206ms 推迟到 379ms → c2(C3) 启动从 400ms 推迟到 530ms
   - FIFO 让 main 独占 → c2 排队等待 → c2(C2) 启动从 206ms 推迟到 369ms

**根本原因总结**：zhang2 的 DAG 结构中，mutex 互斥和 sem 触发**强制了大部分执行顺序**，留给调度器的自由度极小。CFS 的时间片轮转恰好让 c2 在竞争窗口内也能推进，而所有 SCHED_FIFO 方案（无论优先级如何分配）都会导致某个线程被完全抢占，最终延迟 c2(C3) 的启动。

| 模式 | 总时间 | c2(C2)启动 | c2(C3)启动 | c2(C3)结束 | 比CFS慢 |
|------|--------|-----------|-----------|-----------|---------|
| CFS | 679ms | 206ms | 400ms | 637ms | — |
| FIFO | 746ms | 369ms | 518ms | 742ms | +10% |
| zhao2020 | 758ms | 379ms | 530ms | 754ms | +12% |
| heft | 839ms | 291ms | 611ms | 835ms | +24% |

## zhang5：新 DAG 设计

### 设计思路

zhang2 的教训：在 2 核 SCHED_FIFO 下，给 worker 更高优先级会抢占 main，导致 main 上的 sem_post 触发延迟。

zhang5 的策略：**利用 main 的 join 等待窗口**。main 链很轻，大部分时间在 join 等待。竞争发生在 worker 之间，不存在"抢占 main"的问题。

### DAG 拓扑（5 线程：main + worker_a + worker_b + worker_c + worker_d）

```
main#001(C1) ──fork all──→ main#002(C2) → join(worker_a) → main#003(C3) → join(worker_b) → main#004(C4) → join(worker_c,worker_d) → main#005(C5)
                  │
                  ├──→ worker_a#001(C6) → sem_wait(s1) → worker_a#002(C7)
                  │                        ↑ main#002 sem_post(s1)
                  │
                  ├──→ worker_b#001(C8) → sem_wait(s2) → worker_b#002(C9) → sem_wait(s3) → worker_b#003(C10)
                  │                        ↑ main#002 sem_post(s2)             ↑ main#003 sem_post(s3)
                  │
                  ├──→ worker_c#001(C11) → sem_wait(s4) → worker_c#002(C12)
                  │                         ↑ main#003 sem_post(s4)
                  │
                  └──→ worker_d#001(C13) → sem_wait(s5) → worker_d#002(C14)
                                            ↑ main#004 sem_post(s5)
```

### 权重

| 常量 | 值 | 节点 | 设计理由 |
|------|-----|------|---------|
| C1 | 0.5 | main#001 | 轻，初始化+fork |
| C2 | 0.8 | main#002 | 轻，完成后 sem_post(s1,s2) |
| C3 | 0.8 | main#003 | 轻，完成后 sem_post(s3,s4) |
| C4 | 0.8 | main#004 | 轻，完成后 sem_post(s5) |
| C5 | 0.3 | main#005 | 轻，收尾 |
| C6 | 0.4 | worker_a#001 | 轻，快速进入等待 |
| C7 | 8.0 | worker_a#002 | 重！竞争点1关键任务 |
| C8 | 0.4 | worker_b#001 | 轻，快速进入等待 |
| C9 | 5.0 | worker_b#002 | 重，竞争点1干扰 |
| C10 | 6.0 | worker_b#003 | 重！竞争点2关键任务 |
| C11 | 10.0 | worker_c#001 | 重，背景任务 |
| C12 | 5.0 | worker_c#002 | 重，竞争点2干扰 |
| C13 | 9.0 | worker_d#001 | 重，背景任务 |
| C14 | 4.0 | worker_d#002 | 中等，竞争点3 |

### 竞争点分析

| 竞争点 | 时机 | 就绪任务 | 正确选择 | 错误选择代价 |
|--------|------|---------|---------|------------|
| 1 | main join(worker_a) | worker_a#002(8.0), worker_b#002(5.0), worker_c#001(10.0), worker_d#001(9.0) | 优先 worker_a#002（main 在等它） | main join 等待延长 |
| 2 | main join(worker_b) | worker_b#003(6.0), worker_c#002(5.0), worker_d#001 可能还在跑 | 优先 worker_b#003（main 在等它） | main join 等待延长 |
| 3 | main join(worker_c,d) | worker_c#002, worker_d#002(4.0) | 优先未完成的那个 | 总时间延长 |

### 为什么这次能成功

- main 链很轻（总 3.2 单位），大部分时间在 join 等待 → 不存在"抢占 main"的问题
- 竞争发生在 worker 之间，SCHED_FIFO 按优先级选 worker
- CFS 不感知依赖，均匀分配 CPU 给所有 worker → 被 join 等待的 worker 得不到优先
- FIFO（同优先级99）按创建顺序 → 不一定选对

## 经验总结

### 核心发现：SCHED_FIFO 抢占效应

在 2 核 SCHED_FIFO 环境下，优先级调度存在一个根本性矛盾：

1. **高优先级线程完全抢占低优先级线程**：SCHED_FIFO 不是时间片轮转，高优先级线程会独占 CPU 直到主动让出（阻塞/结束）
2. **CFS 的时间片轮转反而更高效**：当多个线程都需要推进时，CFS 让所有线程都能获得 CPU，整体吞吐量更高
3. **优先级调度在"核心数 < 就绪线程数"时容易导致饿死**：2 核上 4 个就绪线程，最低优先级的 2 个完全得不到 CPU

### SEG 块切分的影响

pipeline 的 level2 分块会把 mutex 外的同步原语（sem_post、pthread_join、pthread_create）切成独立的 SEG 段，每个 SEG 段有自己的优先级。这导致：

- 一个线程在执行过程中优先级会频繁变化
- 关键路径上的 MU 块可能因为前后 SEG 段的低优先级而被抢占
- 算法计算的"理想优先级"和实际 SCHED_FIFO 行为之间存在偏差

### 什么条件下算法能赢 CFS

从 zhang5 v3 的 min_s 数据看，算法在以下条件下能赢：

1. **关键路径集中在 1 个 worker 线程上**（不跨线程切换优先级）
2. **worker 内只有 1 个 MU 块**（避免优先级在 MU 块之间降低）
3. **filler 线程数量足够多**（让 CFS 浪费更多 CPU）
4. **main 极轻**（不参与关键路径计算）

### 源码编写规范

1. **mutex 无竞争、按顺序命名**：每个 mutex 只在一个线程内 lock/unlock（自锁），不允许跨线程竞争同一把锁。mutex 按使用顺序命名 mutex_01, mutex_02, ...，不跳号
2. **同步原语放在 mutex 外面**：sem_wait/sem_post/pthread_join/pthread_create 全部放在 mutex 临界区外面，mutex 内只放计算代码
3. **跨线程同步只用 sem 和 join**：线程间的启动延迟、触发、等待完成等同步关系，统一用 sem_wait/sem_post 和 pthread_join 实现，不用 mutex 竞争
4. **消除 worker 线程的 SEG 入口段**：worker 函数体的第一条语句必须是 `pthread_mutex_lock`，lock 之前不能有任何代码（包括 `(void)arg;`）。否则 pipeline 的 "cut BEFORE lock" 规则会在入口和 lock 之间切出一个零权重 SEG 段，干扰优先级排序
5. **mutex 内可以放任意非同步代码**：`init_matrices()`、普通计算、赋值等都可以放在 mutex 临界区内，只要不放 `pthread_create/join/sem_post/sem_wait` 即可。mutex 内不会产生额外切点

```c
// ✅ 正确写法：worker 函数
static void *worker(void *arg)
{
  pthread_mutex_lock(&mutex_01);       // 第一条语句就是 lock → 不产生 SEG 入口段
  busy_wait_seconds(C1);
  pthread_mutex_unlock(&mutex_01);
  return NULL;
}

// ✅ 正确写法：main 函数（init 放进 mutex 内）
int main(void)
{
  pthread_mutex_lock(&mutex_01);
  init_matrices();                     // 非同步代码，放 mutex 内没问题
  busy_wait_seconds(C1);
  pthread_mutex_unlock(&mutex_01);
  pthread_create(...);                 // 同步原语在 mutex 外面
  pthread_join(...);
  pthread_mutex_lock(&mutex_02);
  busy_wait_seconds(C2);
  pthread_mutex_unlock(&mutex_02);
  return 0;
}

// ❌ 错误写法：lock 前有代码 → 产生 SEG 入口段
static void *worker(void *arg)
{
  (void)arg;                           // ← 这行会产生 SEG:worker#001
  pthread_mutex_lock(&mutex_01);       // ← MU:worker#002
  busy_wait_seconds(C1);
  pthread_mutex_unlock(&mutex_01);
  return NULL;
}
```

### 待解决的问题

1. **worker 多 MU 块时优先级降低**：算法给 worker 的第二个 MU 块更低优先级，导致被 filler 抢占
2. **avg vs min 的差距**：即使 min_s 能赢，avg 被方差拖累。需要更多重复次数或更大的权重差距
3. **是否需要修改插桩策略**：当前按 MU 块切换优先级，是否应该改为按线程设置固定优先级
