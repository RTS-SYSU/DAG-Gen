# ScratchDAG 约定术语

## Pipeline 完整流程

ScratchDAG 的 Pipeline 完整流程分为以下 **8 个阶段**：

> **重跑说明**：每次说"重跑完整流程"，是指从第 1 阶段开始，共完整跑完全部 8 个阶段。中间结果已存在不代表可以跳过，必须全部重新执行。

> **一键命令**：
> ```bash
> cd /home/firefly/Desktop/ScratchDAG
> python3 -m pipeline run_all --source 源文件/zhang1/zhang1.c
> ```
> 可选参数：
> - `--base-name zhang1`：指定测试用例名（默认取源文件名）
> - `--level level2`：分块级别（默认 level2）
> - `--rule effective_line_merge`：分块规则（默认 effective_line_merge）
> - `--repeats 10`：Timing 阶段重复次数（默认 10）
> - `--mode auto`：插桩模式（auto/specialized/generic，默认 auto）

### 1. **源码准备阶段**
- 输入：原始 C 源文件（如 `zhang1.c`）
- 输出：源文件本身
- 作用：准备待分析的 C 程序，通常包含关键链 + 填充任务的实验程序

### 2. **编译展开阶段**（expand 文件生成）
- 输入：C 源文件
- 输出：`.233r.expand` 文件（GCC RTL 中间表示）
- 命令：`gcc -fdump-rtl-expand <源文件>`
- 作用：生成 GCC 编译器的内部 RTL 表示，用于后续代码分析

### 3. **DAG 生成阶段**（生成dag图）
- 输入：expand 文件 + 源文件
- 输出：
  - `配置文件/{base_name}_threads.dot`：线程视图 DAG（threads-only 模式）
  - `配置文件/{base_name}.dot`：完整 DAG 视图
  - `生成dag图/dag.dot`：从完整视图复制，供 Collect 阶段前置检查
  - `生成dag图/functions_full.json`、`functions_ranges.json`、`debug/mycalls_meta_internal.json`
- 作用：基于 RTL expand 文件解析代码结构，生成任务依赖图
- 说明：pipeline 会自动执行两次 DAG 生成（threads-only + 完整视图），并确保 `dag.dot` 存在。与 GUI 工具的"生成 expand 文件"+"生成 dag 图"两步操作等价

### 4. **Collect 阶段**（收集基础信息）
- 输入：源文件
- 输出：`block_info.json`
- 命令：`pipeline collect --source <源文件>`
- 作用：分析源代码结构，建立基础元数据

### 5. **Blocks 阶段**（代码分块 + DAG 优化）
- 输入：block_info + 源文件
- 输出：`segments.json`、`dag_seg.json`、`dag_seg.dot/png`
- 命令：`pipeline blocks --level level2 --rule effective_line_merge`
- 作用：按规则分块代码段，生成优化后的 DAG 结构
- **分块规则**：以 `pthread_mutex_lock` / `pthread_mutex_unlock` 为切点，生成 MU 块
- **SEG 吸收规则**：mutex 外的同步原语通过双向吸收合并到相邻 MU 块
  - unlock 往下吸 `sem_post` / `pthread_create`（归前一个 MU 块）
  - lock 往上吸 `sem_wait` / `pthread_join`（归后一个 MU 块）
  - 两个方向各自只吸收自己类型，遇到对方类型停止（碰头机制）

### 6. **Timing 阶段**（执行时间测量）
- 输入：blocks 输出的代码段
- 输出：`timing.json`
- 命令：`pipeline timing --level level2 --rule effective_line_merge`
- 作用：测量每个代码段的实际执行时间（avg_ns）
- **探针定位**：扫描 MU 块内的 `mutex_lock` 和 `mutex_unlock`，`SEG_BEGIN` 插在 lock 之后，`SEG_END` 插在 unlock 之前，只测纯计算部分
- **纯 blocker 段**：如果残留的 SEG 段全是同步原语，自动跳过并填 `avg_ns=0`

### 7. **Schedule 阶段**（调度算法生成优先级）
- 输入：timing 结果 + DAG
- 输出：每个算法的 `schedule.json`
- 命令：`pipeline schedule --level level2 --rule effective_line_merge --algo cpf`
- 支持算法：cpf、heft、lpf、t_level、wcet_first、zhao2020
- 作用：使用调度算法为每个段分配优先级

### 8. **Instrument 阶段**（代码插桩 + 可视化 + 测时版本）
- 输入：schedule + 源代码
- 输出（v3.0 新结构）：
  - `result/CFS/CFS.c`：纯源文件（CFS 默认调度）
  - `result/FIFO/FIFO.c`：源文件 + `l1_set_thread_prio_fifo(99)`
  - `result/{algo}/{algo}.c`：各算法优先级插桩版本
  - `timing/CFS/CFS.c`、`timing/FIFO/FIFO.c`、`timing/{algo}/{algo}.c`：在 result 基础上加 `MAIN_ELAPSED_S` 测时代码
  - validation 可视化：`dag_seg_annotated.dot/png` + `dag_seg_annotated_value.dot/png`
- 命令：`pipeline instrument --level level2 --rule effective_line_merge --algo cpf`
- 作用：代码插桩、生成 8 个独立测时版本（2 个对照组 + 6 个算法组），并生成可视化图

**实验分组**（每个算法跑一次 instrument 后，CFS/FIFO 对照组同步生成）：

| 分组 | 目录名 | 说明 |
|------|--------|------|
| 对照组 | CFS | 源文件，默认 Linux CFS 调度 |
| 对照组 | FIFO | 源文件 + 开启 FIFO 实时调度（统一优先级 99） |
| 实验组 | cpf | Critical Path First |
| 实验组 | heft | Heterogeneous Earliest Finish Time |
| 实验组 | lpf | Longest Processing Time First |
| 实验组 | t_level | T-Level 拓扑层级 |
| 实验组 | wcet_first | WCET 排序 |
| 实验组 | zhao2020 | Zhao 2020 文献算法 |

## runtime_compare 完整流程

runtime_compare 是独立的测时实验工具，在 Pipeline 第 8 阶段完成后使用。

### 前提条件
- Pipeline 已完成 Instrument 阶段，`timing/` 目录下已有 8 个子目录及对应 `.c` 文件

### 流程步骤

#### 1. 启动工具
```bash
cd tools/runtime_compare
python -m runtime_compare
```
浏览器打开 `http://localhost:5000`

#### 2. 设置实验结果目录
- 在 Web UI 顶部设置 `results_root`，如 `实验结果/zhang1_exp1`

#### 3. 批量导入任务
- 点击「批量提交」，填入 `folder` 路径（如 `/path/to/中间结果/zhang1`）
- 工具自动扫描 `timing/` 下的 8 个子目录，每个生成一个独立任务入队
- 共 8 个任务：CFS、FIFO、cpf、heft、lpf、t_level、wcet_first、zhao2020

#### 4. 配置运行参数
- `WORK_SCALE`：工作量倍数（默认 100）
- `repeats`：每个任务重复运行次数（在 Web UI 可配置）
- `cores_per_task`：每任务使用核心数（建议绑定大核 4-7）

#### 5. 等待任务完成
- 每个任务独立编译、运行 N 次，输出 `runs.csv` + `summary.json`
- 消息格式：`完成: heft mean=0.953s (10 次)`

#### 6. 生成汇总
- 所有任务完成后，调用 `/api/summary_all` 接口（或在 UI 点击「生成汇总」）
- 生成 `summary_all.csv`，包含 8 个算法的 avg/min/max 对比

### 输出目录结构
```
实验结果/{batch_name}/
├── CFS/
│   ├── runs.csv          # 每次运行时间
│   └── summary.json      # 统计结果
├── FIFO/
├── cpf/
├── heft/
├── lpf/
├── t_level/
├── wcet_first/
├── zhao2020/
└── summary_all.csv       # 8 个算法汇总对比
```

### runs.csv 格式
```csv
run,time_s,wall_s
1,1.234567,1.240000
2,1.230000,1.235000
...
avg,1.232284,
min,1.230000,
max,1.234567,
```

### summary_all.csv 格式
```csv
algorithm,avg_s,min_s,max_s,median_s,n
CFS,1.500000,...
FIFO,1.200000,...
cpf,1.050000,...
...
```

## 关键术语

### 文件类型
- **`.c`**：C 源文件
- **`.233r.expand`**：GCC RTL 展开文件
- **`.dot`**：GraphViz DOT 格式图文件
- **`.png`**：渲染后的图文件
- **`.json`**：配置和结果文件

### 目录结构
- **`源文件/`**：原始实验程序
- **`配置文件/`**：编译和调试配置
- **`中间结果/`**：pipeline 处理结果
  - `pipeline/blocks/`：分块结果
  - `pipeline/timing/`：时间测量结果
  - `pipeline/schedule/`：调度结果
  - `pipeline/instrument/result/`：插桩结果（不含测时）
  - `pipeline/instrument/timing/`：测时版本（含 MAIN_ELAPSED_S）
  - `pipeline/validation/`：可视化结果

### 算法名称
- **cpf**：Critical Path First
- **heft**：Heterogeneous Earliest Finish Time
- **lpf**：Longest Processing Time First
- **t_level**：Top Level
- **wcet_first**：Worst Case Execution Time First
- **zhao2020**：Zhao 2020 算法

### 关键概念
- **DAG**：有向无环图，表示任务依赖关系
- **RTL**：Register Transfer Language，GCC 的中间表示
- **插桩**：Instrumentation，在代码中插入测量/控制代码
- **优先级调度**：使用 SCHED_FIFO + 不同优先级进行实时调度
- **MAIN_ELAPSED_S**：测时代码输出格式，由 `clock_gettime` 在 main 首尾插桩生成

### CPU 核心速率（实验环境）

**测量时间**：2026-04-01（5次测量取平均）

**各核心速率（单位：MHz）：**

| 核心 | 5次测量平均 | 最大频率 | 备注 |
|------|-------------|----------|------|
| CPU0 | 609        | 1800    | 小核 |
| CPU1 | 446        | 1800    | 小核 |
| CPU2 | 566        | 1800    | 小核 |
| CPU3 | 528        | 1800    | 小核 |
| CPU4 | 408        | 2352    | 大核 |
| CPU5 | 408        | 2352    | 大核 |
| CPU6 | 408        | 2352    | 大核 |
| CPU7 | 489        | 2352    | 大核 |

**说明**：
- 小核（CPU 0-3）：最大可达 1.8GHz
- 大核（CPU 4-7）：最大可达 2.352GHz（推荐用于高性能实验）
- 实际运行时频率会动态调整（受负载和温控影响）

**实验建议**：
- 实验任务建议绑定到**大核（4-7）**以获得更高性能
- 系统后台任务可限制在小核（0-3），减少实验干扰
- 使用 `taskset -c 6,7` 可将程序绑定到核心 6 和 7

### 源码编写规范（Pipeline DAG 解析器硬性要求）

以下是 Pipeline 能正确解析源码并生成 DAG 的**必须满足**的条件（来源：`generation/legacy.py`、`level2/segment_dag_level2.py` 代码分析）。

#### 硬性要求

1. **每段计算必须用 `pthread_mutex_lock/unlock` 包裹**
   - 这是 level2 分块（MU 块切分）的核心依据
   - 没有 mutex 临界区的程序**无法生成 dag.dot**，pipeline 会在 Collect 阶段报错
   - mutex 临界区内只放 `busy_wait_seconds(Cx)` 计算，同步原语放在 mutex 外面

2. **必须存在 `busy_wait_seconds` 函数**
   - timing 阶段靠函数名识别计算段
   - 实现统一使用：`int units = (int)(seconds * WORK_SCALE + 0.5);`

3. **每个 MU 块使用独立的权重常量**（C1, C2, C3...）
   - 不要多个块共用同一个常量
   - timing 阶段需要从源码提取常量名与 MU 块对应

4. **必须存在 `pthread_join`**
   - 用于建立线程结束的 join 补边（tail → join）

5. **能被 `gcc -fdump-rtl-expand` 正确编译**
   - DAG 生成依赖 GCC RTL expand 中间表示文件

#### 灵活部分（不是硬性要求）

- **`pthread_create` 不要求全在 main 里**：可以在任何函数中创建线程（链式创建也支持），解析器会在遇到 `pthread_create` 时记录 thread_id → task_function 映射
- **`sem_wait/sem_post` 不是必须的**：sem 用于建立跨线程依赖边（sem_post → sem_wait）。如果不用 sem，跨线程依赖就只有 fork 边（pthread_create）和 join 边（pthread_join）
- **线程数量和拓扑结构自由**：支持任意数量的线程和任意依赖关系

#### Worker 参数使用规范（新增）

- 对于 `pthread` 线程函数，若参数未使用，**禁止**在函数体开头写 `(void)arg;`
- 原因：`(void)arg;` 会被 level2 分块器识别为有效代码，从而在函数入口到首个 `pthread_mutex_lock` 之间生成前导 `SEG`
- 该前导 `SEG` 不属于空白段，无法被“空白吸收规则”消除，会增加无意义分块并干扰 DAG 简洁性与优先级生成
- 生成新的实验源码时，worker 函数应尽量让**第一条有效语句就是 `pthread_mutex_lock(...)`**，避免在首个 mutex 前放置任何无业务意义的有效代码

#### 正确写法示例

```c
// ✅ 正确：mutex 内只有计算，同步原语在外面
sem_wait(&sem_01);
pthread_mutex_lock(&mutex_01);
busy_wait_seconds(C1);
pthread_mutex_unlock(&mutex_01);
sem_post(&sem_02);
```

```c
// ❌ 错误：没有 mutex 包裹（pipeline 无法切分 MU 块）
sem_wait(&sem_01);
busy_wait_seconds(C1);
sem_post(&sem_02);
```

```c
// ❌ 错误：多个计算共用同一个常量
pthread_mutex_lock(&mutex_01);
busy_wait_seconds(C1);
pthread_mutex_unlock(&mutex_01);
pthread_mutex_lock(&mutex_02);
busy_wait_seconds(C1);    // 应该用 C2
pthread_mutex_unlock(&mutex_02);
```

#### 不符合规范的程序示例

- `experiment2.c`、`cpu4_thread10_fifo_1.c`：没有 mutex 临界区，pipeline 在 Collect 阶段报错 `missing required inputs: dag.dot`

## 调度 Trace 分析法

一种用于分析和对比不同调度策略实际执行行为的方法。通过在源码的每个 MU 块前后插入 `clock_gettime(CLOCK_MONOTONIC)` 时间戳，记录每个段的绝对开始/结束时间，然后按 begin 排序生成完整执行时间线。

### 方法流程

1. **生成 trace 源码**：基于原始 C 源文件，在每个 MU 块的 lock 前插入 `TRACE_BEGIN`，unlock 后插入 `TRACE_END`，记录段名、begin_us、end_us
2. **注入调度策略**：根据算法的 schedule.json 优先级，在对应位置插入 `l1_set_thread_prio_fifo(prio)`。CFS 版本不设优先级，FIFO 版本所有线程同优先级
3. **绑核编译运行**：`gcc -O0 -DWORK_SCALE=100`，`taskset -c 6,7` 绑核运行，收集 trace 输出
4. **生成三部分分析**：
   - **时间线图**：ASCII 双核甘特图，标注每个核上跑的段和时间点
   - **Trace 数据表**：按 begin_ms 排序的表格（段名、begin_ms、end_ms、dur_ms）
   - **Phase 分析**：按阶段描述竞争情况、线程数、CPU 份额、调度行为

### 输出位置

多轮采集时分目录保存（与第一轮数据区分）：

- `权重实验分析（第一轮）/` — 首轮 trace：`zhang2_all_traces.json`、`zhang2_*_trace.c`、`zhang2_六种调度策略时间线对比.md` 等
- `权重实验分析（第二轮）/` — 同样命名：`zhang2_all_traces.json`、`run_all_traces.py`、`README_第二轮.md`

通用命名格式：

- `<case>_<algo>_trace.c` — 带 trace 插桩的源码
- `<case>_all_traces.json` — 所有算法的原始 trace 数据
- `<case>_六种调度策略时间线对比.md` — 完整对比分析文档（按该轮 json 填写）

### 用途

- 直观对比 CFS/FIFO/算法在同一 DAG 上的实际调度差异
- 定位算法比 CFS 慢的根因（如 main 独占、sem 延迟、优先级反转）
- 指导权重调整和 DAG 结构设计
