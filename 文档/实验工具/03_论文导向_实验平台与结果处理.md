# 论文导向：实验平台、结果处理与有效性说明

本文档面向论文写作，目标不是重复工具使用说明，而是回答以下问题：

1. 本项目的实验平台如何构成。
2. baseline/prio 对比实验是如何被严格执行和记录的。
3. CPU 基准结果如何用于解释跨平台差异。
4. 结果汇总表是如何从原始运行记录构造出来的。
5. 当前实现有哪些必须在论文中说明的测量边界。

## 1. 实验平台在本项目中的位置

ScratchDAG 的主线是：

```text
程序分析
-> DAG 构建
-> 分块
-> 优先级生成
-> 优先级插桩
```

而 `tools/runtime_compare` 与 `experiment/` 所承担的是最后一段：

```text
baseline / prio 程序
-> 受控 CPU 环境下运行
-> 多次重复测量
-> 统计汇总
-> 跨平台对比
```

因此论文中可以把它定义为：

- “实验执行与结果分析平台”

而不是主算法本身。

## 2. baseline / prio 对比实验模型

当前实验工具围绕一对程序文件组织任务：

- `baseline_c`
- `prio_c`

其中通常对应：

- `baseline_c`：未做优先级调度插桩的程序
- `prio_c`：经过调度算法生成并插入优先级设置语句后的程序

对于每个任务，实验参数包括：

- `work_scale`
- `repeats`
- `cores_per_task`
- 可选 `cpu_list`
- `use_sudo`

单个任务的实验目标可以形式化为：

> 在同一组 CPU 核心、同一工作负载规模、同一重复次数下，比较 baseline 与 prio 两个程序版本的运行时间统计差异。

## 3. CPU 隔离与实验可控性

### 3.1 外部 CPU 绑定

`run_with_affinity()` 在子进程启动前调用 `os.sched_setaffinity()`，把实验进程绑定到指定 CPU 集合。  
这一步保证了外层实验执行的 CPU 隔离。

### 3.2 内部 affinity 改写

如果被测源码中本身包含：

- `CPU_ZERO(&set)`
- `CPU_SET(...)`
- `sched_setaffinity(...)`

那么 `rewrite_sched_setaffinity_cpu_set()` 会把其中硬编码的 CPU_SET 替换为当前任务分配的核心集合。  
这一步的意义在于：

- 避免程序内部的 affinity 设置覆盖实验平台的核隔离策略。

### 3.3 CPU 池调度

`CpuPool` 保证不同并发任务使用不重叠的核心集合。  
如果可用核心不足，任务会回到队列中等待，而不是抢占已有任务的核心。

### 3.4 排队模式

当 `queue_mode=true` 时，所有任务串行执行。  
这可以进一步降低不同任务之间的资源干扰，适合需要严格控制环境的实验。

在论文中，这一整套机制可以被概括为：

> “通过 CPU 亲和性绑定、源码内 affinity 改写和核心池分配三层机制，降低并发任务和程序自带绑核逻辑对实验结果的干扰。”

## 4. 编译与运行的一致性

### 4.1 编译参数

`runtime_compare` 默认使用统一的 GCC 选项：

- `-O0`
- `-g`
- `-std=c11`
- `-pthread`
- `-Wl,--wrap=main`
- `-lm`

并额外注入：

- `-DWORK_SCALE=<work_scale>`

这样可以保证：

- baseline 与 prio 仅在源码本体差异上不同
- 编译器选项与工作负载宏定义在同一任务内保持一致

### 4.2 目录隔离

工具会把 baseline/prio 各自的源码目录拷贝到任务结果目录下单独编译，避免：

- 原目录被污染
- baseline/prio 互相覆盖生成物
- 多任务共享中间文件

这也保证了论文实验的可追溯性，因为结果目录本身就包含一份用于本次实验的局部源码快照。

## 5. 结果文件与统计流程

### 5.1 原始粒度

对每一轮运行，工具会记录：

- 程序类型：`baseline` 或 `prio`
- 轮次编号 `iter`
- `time_s`
- `wall_s`
- `parsed_from_stdout`
- `cpu_set`
- `returncode`
- 原始日志文本

这些数据保存在：

- `summary.json` 的 `runs[]`
- `runs.csv`
- `run.log`

### 5.2 聚合粒度

工具再对 baseline 和 prio 分别计算：

- `min_s`
- `max_s`
- `mean_s`
- `median_s`
- `times_s`

并生成：

```text
delta_mean_s = prio_mean_s - baseline_mean_s
improvement_ratio = (baseline_mean_s - prio_mean_s) / baseline_mean_s
```

因此实验论文中的“性能提升百分比”可以直接来源于：

- `improvement_ratio * 100%`

## 6. CPU 基准结果在论文中的作用

### 6.1 为什么需要 `cpu_bench`

跨平台实验不仅要展示：

- baseline 与 prio 的时间差异

还要解释：

- 为什么虚拟机与 RK3588 的绝对时间不在一个数量级
- 为什么 RK3588 内部不同核心可能表现不同

`cpu_bench` 的作用正是提供这个解释背景。

### 6.2 当前样本体现的结论

在仓库现有样本中：

- VM 平均 MOPS 约 `17.65`
- RK3588 平均 MOPS 约 `3.00`
- VM / RK 平均倍率约 `5.89`

而在 RK3588 内部：

- top2 核心约 `5.83/5.82 MOPS`
- 低性能核心约 `1.22~1.41 MOPS`

这说明：

- RK3588 平台内部存在明显的大小核差异
- 若实验绑定到不同 CPU 集合，理论上会显著影响绝对耗时

因此论文中应把 CPU 基准结果用作：

- 平台背景说明
- 选核策略合理性说明
- 跨平台绝对时间差异的解释依据

## 7. `experiment/` 中的跨平台汇总逻辑

### 7.1 单任务结果到平台级总表

`experiment/experiment2实验总表/scripts/build_platform_config_results.py` 的处理流程可概括为：

```text
遍历 summary.json
-> 读取 baseline/prio.stats
-> 读出 mean/min/max/repeats/cpu_set
-> 计算 delta_mean_s / improvement_ratio
-> 输出 CSV
-> 输出 Markdown 表格
```

这意味着论文中的表格不是人工填写的，而是由原始任务结果自动派生出来的。

### 7.2 当前总表中的结论

从 `config_results_all.csv` 统计可得到：

- VM：6 组实验，平均提升约 `25.17%`
- RK3588：7 组实验，平均提升约 `27.98%`

从 `config_results_by_platform.md` 看，RK3588 的样本提升范围约为：

- `26.11% ~ 29.37%`

VM 的样本提升范围约为：

- `23.81% ~ 28.42%`

这说明在当前 `experiment2` 数据集中，`prio` 相比 `baseline` 的性能改进是：

- 稳定的
- 跨平台可观测的
- 在 RK3588 上略高于 VM

这类结论很适合写在论文实验结果分析小节中。

## 8. 一个必须在论文中说明的测量口径问题

这是阅读源码后最重要的发现之一。

### 8.1 工具的设计意图

`parse_internal_time_seconds(stdout)` 设计上想优先读取程序内部报告时间，特别是：

- `PROGRAM_TOTAL_NS=<...>`

如果读取成功，那么 `time_s` 应代表程序内部计时。

### 8.2 当前样本的真实行为

但 `TaskRunner` 实际只把 `stdout` 传给解析器，而现有样本中的：

- `PROGRAM_TOTAL_NS=...`

出现在 `stderr`。

于是当前样本里发生的是：

1. 内部计时解析失败。
2. 工具回退到 `wall_ns / 1e9`。
3. `summary.json` 中 `parsed_from_stdout=false`。

因此当前实验结果使用的主要是：

- 外层 wall time

而不是：

- 程序内部时间

### 8.3 对论文意味着什么

这不会让实验失效，但论文必须如实描述：

- 当前 `runtime_compare` 报告的主时间口径是任务外层 wall time
- 内部计时值虽存在，但现有实现没有正确从 `stderr` 提取

如果在论文中不说明这一点，就会把“程序内部时间”和“外层 wall time”混为一谈。

## 9. 论文中的建议写法

### 9.1 实验平台描述

建议写成：

“本文使用自研实验执行工具对 baseline 与 priority-instrumented 两个程序版本进行重复运行比较。实验工具为每个任务分配独立 CPU 核心集合，并通过进程亲和性绑定和源码内 affinity 重写两层机制降低外部干扰。每组实验记录逐次运行时间、聚合统计量以及完整日志，并将结果结构化保存为 JSON、CSV 和文本报告。”

### 9.2 CPU 平台差异说明

建议写成：

“为解释跨平台实验结果，本研究额外采用逐核轻量 CPU 基准工具估计不同在线核心的相对算力。结果显示，虚拟机平台的平均 MOPS 明显高于 RK3588 平台；同时 RK3588 内部存在显著的大核/小核差异，因此实验中的 CPU 绑定策略对绝对耗时具有重要影响。”

### 9.3 结果统计说明

建议写成：

“对于每组 `(work_scale, repeats, cpu_set)` 配置，分别计算 baseline 与 prio 版本的最小值、最大值、平均值和中位数，并采用 `improvement_ratio=(baseline_mean-prio_mean)/baseline_mean` 作为相对改进指标。”

## 10. 论文中的有效性威胁与边界

建议至少写出以下几点：

1. 当前 `runtime_compare` 的 `time_s` 在现有样本中主要是 wall time，而不是内部计时输出。
2. `cpu_bench` 是轻量相对性能估计，不是严格硬件性能计量工具。
3. RK3588 等异构平台内部存在大小核差异，选核策略可能影响实验结果。
4. 当前总表脚本仍依赖历史目录名 `mycallyplus_v1`，说明结果整理链路仍有命名迁移遗留。

## 11. 与主系统论文的衔接方式

在 ScratchDAG 的整篇论文里，这部分内容最适合放在：

- 实验平台与方法
- 实验结果统计口径
- 结果可复现性说明
- 有效性威胁

它与主系统关系可概括为：

```text
ScratchDAG 主系统
-> 生成 baseline / prio 代码
-> runtime_compare 负责执行对比实验
-> cpu_bench 提供平台解释变量
-> experiment/ 提供论文表格与结果归档
```

也就是说，这三部分不是算法核心，但构成了论文实验部分的“证据链基础设施”。
