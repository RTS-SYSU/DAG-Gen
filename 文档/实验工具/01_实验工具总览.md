# 实验工具总览

## 1. 范围与角色划分

这三部分内容在项目中承担的角色不同：

| 路径 | 角色 |
| --- | --- |
| `tools/cpu_bench/` | CPU 基准测试工具 |
| `tools/runtime_compare/` | baseline/prio 对比实验执行与结果采集工具 |
| `experiment/` | 已完成实验的结果沉淀与跨平台汇总目录 |

因此它们不是并列的三个“独立工具”，而是一个完整实验闭环中的不同阶段：

```text
cpu_bench
-> 了解平台 CPU 性能与核异构特征

runtime_compare
-> 在指定 CPU 集合上编译、运行 baseline/prio 程序
-> 生成 summary.json / runs.csv / run.log / run_results.txt

experiment
-> 保存多轮实验结果
-> 汇总为 CSV / Markdown 表格
-> 支撑论文与报告展示
```

## 2. `tools/cpu_bench/` 的职责

主文件：

- `tools/cpu_bench/cpu_bench.py`

这是一个非常轻量的逐核基准程序。其思路是：

1. 读取 `/sys/devices/system/cpu/online` 获取在线 CPU 列表。
2. 依次把当前进程绑定到单个 CPU。
3. 执行简单位运算循环 `_bench_loop()`。
4. 在至少 `min_ms=200` ms 的窗口内累计迭代次数。
5. 以 `MOPS`（百万次操作/秒）输出每个核心的估计吞吐量。
6. 保存 `.txt` 和 `.json` 报告。

它不是严格的微架构 benchmark，而是一个“足够便宜、足够稳定、足够能区分大核/小核”的相对性能估计工具。

## 3. `tools/runtime_compare/` 的职责

主入口：

- `tools/runtime_compare/main.py`

支持三种模式：

- `--cli`
- `--web`
- `--gui`（代码中标记为待实现）

当前可用主线是 CLI 和 Web。

这个工具的目标是比较一对程序：

- `baseline_c`
- `prio_c`

在给定：

- `work_scale`
- `repeats`
- `cores_per_task`
- 可选 `cpu_list`

的条件下，二者在同一组 CPU 核心上的运行时间差异。

## 4. `runtime_compare` 的核心对象

### 4.1 `Task`

定义位置：

- `tools/runtime_compare/core/task.py`

关键字段：

- `baseline_c`
- `prio_c`
- `work_scale`
- `repeats`
- `cores_per_task`
- `cpu_list`
- `cpu_set`
- `status`
- `phase`
- `out_dir`

这说明工具是围绕“实验任务”而不是“单次命令”组织的。

### 4.2 `CpuPool`

定义位置：

- `tools/runtime_compare/core/cpu_pool.py`

职责：

- 管理在线 CPU 集合
- 给任务分配互不重叠的核心组
- 支持按 `preferred cpu_list` 优先分配

其本质是一个实验资源管理器，确保并发任务不会抢占同一组 CPU。

### 4.3 `TaskRunner`

定义位置：

- `tools/runtime_compare/core/task_runner.py`

职责：

- 从任务队列取任务
- 获取 CPU 组
- 复制 baseline/prio 的源码目录
- 编译二者
- 运行二者若干次
- 汇总统计并落盘结果文件

它是整个工具的真正执行引擎。

## 5. 任务执行的实际流程

对于单个任务，`TaskRunner` 的执行流程可以概括为：

```text
获取 CPU 组
-> 创建结果目录
-> 复制 baseline/prio 源码目录
-> 尝试改写源码中的 sched_setaffinity CPU_SET
-> 分别编译 baseline 和 prio
-> 在同一 CPU 集合上重复运行 baseline / prio
-> 汇总统计
-> 写 summary.json / runs.csv / run.log / run_results.txt
```

代码中还支持：

- `queue_mode`：所有任务串行执行
- `use_sudo`：必要时通过 `sudo -n` 运行
- 结果目录可写性修复

## 6. `runtime_compare` 的 CPU 隔离机制

该工具不满足于“只在外层 taskset 一下”，而是同时做了两层 CPU 隔离：

1. 运行层  
   `run_with_affinity()` 在子进程 `preexec_fn` 中调用 `os.sched_setaffinity(0, cpu_set)`，保证程序进程和其线程被限制在指定 CPU 上。

2. 源码层  
   `rewrite_sched_setaffinity_cpu_set()` 会扫描源码中的：
   - `CPU_ZERO(&set)`
   - `CPU_SET(...)`
   - `sched_setaffinity(...)`

   然后把程序里硬编码的 `CPU_SET` 语句替换成工具分配的 `cpu_set`。

这样做的目的，是防止被测程序内部又把自己绑定回另一组核，破坏实验隔离。

## 7. 配置文件与结果目录

### 7.1 配置文件

`runtime_compare` 使用 JSON 配置描述任务列表，典型字段包括：

- `baseline_c`
- `prio_c`
- `work_scale`
- `repeats`
- `cores_per_task`
- `cpu_list`
- `use_sudo`
- 顶层的 `queue_mode`

保存位置通常是：

```text
tools/runtime_compare/配置文件/*.json
```

### 7.2 结果目录

单个任务结果默认落到：

```text
tools/runtime_compare/实验结果/<config_name>/<timestamp>_ws<work_scale>_r<repeats>/
```

典型文件：

- `summary.json`
- `runs.csv`
- `run.log`
- `run_results_*.txt`
- `baseline/`
- `prio/`

## 8. `experiment/` 的职责

`experiment/` 是更高层的实验结果仓库，用来保存：

- 虚拟机实验结果汇总
- RK3588 实验结果
- CPU 基准结果备份
- 跨平台总表和脚本

其中最关键的是：

- `experiment/experiment2实验总表/scripts/build_platform_config_results.py`

这个脚本会：

1. 遍历指定目录下的 `summary.json`
2. 抽取 `baseline/prio` 的统计值
3. 生成：
   - `config_results_vm.csv`
   - `config_results_rk3588.csv`
   - `config_results_all.csv`
   - `config_results_by_platform.md`

因此，它承担的是“实验结果后处理器”的角色。

## 9. 代码阅读后最重要的三个事实

### 9.1 `cpu_bench` 的定位是解释平台差异，而不是直接决定实验调度

它的输出不会自动反馈给 `runtime_compare` 做调度决策，但会被：

- Web 系统信息接口
- 实验总表
- 论文中的平台描述

用来解释“为什么不同 CPU 或不同平台表现不同”。

### 9.2 `runtime_compare` 其实是实验 orchestration 系统

它不只是“跑两个程序并计时”，而是完整地做了：

- 资源分配
- 编译管理
- 运行隔离
- 结果结构化记录
- Web/CLI 交互

### 9.3 `experiment/` 是论文证据层

论文中表格、对比数据、平台结论最终不会直接来自运行时代码，而是来自 `experiment/` 中的沉淀结果及其汇总表。
