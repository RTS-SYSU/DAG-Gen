# 实验结果与工具实现说明

## 1. `cpu_bench` 工具实现说明

### 1.1 核心实现

`tools/cpu_bench/cpu_bench.py` 的实现非常直接：

- `read_cpu_online()`：解析在线核列表
- `_bench_loop()`：执行固定模式的位运算循环
- `bench_cpu()`：将当前进程绑定到单个 CPU，运行循环直到超过最小时间窗
- `main()`：遍历所有在线核并保存报告

时间窗口默认为：

- `min_ms = 200`

指标为：

- `MOPS = iterations / elapsed / 1e6`

### 1.2 输出格式

输出包括：

- `cpu_bench_<timestamp>.txt`
- `cpu_bench_<timestamp>.json`

JSON 的核心字段：

- `timestamp`
- `online_cpus`
- `results_mops`
- `sorted`

### 1.3 已有结果的可读结论

从仓库里现有两个样本可以直接读出明显差异：

- 虚拟机样本 `tools/cpu_bench/cpu_bench_20260202_225553.json`
  - top2 核心：CPU 7 = 19.84 MOPS，CPU 6 = 19.50 MOPS
- RK3588 样本 `experiment/experiment2实验总表/rk3588CPU测试/cpu_bench_20260203_065917.json`
  - top2 核心：CPU 5 = 5.83 MOPS，CPU 7 = 5.82 MOPS

这表明：

- 虚拟机整体 CPU 基准值显著高于 RK3588 样本
- RK3588 样本内部存在明显高低核差异

在 `cpu_bench_compare_vm_vs_rk3588.md` 中，这种差异进一步被总结为：

- VM 所有在线核 mean MOPS = 17.65
- RK3588S 所有在线核 mean MOPS = 3.00
- VM / RK 均值倍率约 5.89

## 2. `runtime_compare` 的模式与入口

### 2.1 主入口

文件：

- `tools/runtime_compare/main.py`

职责：

- 分发 `--cli`、`--web`、`--gui`
- 自动定位项目根目录
- 初始化任务管理器

### 2.2 CLI

文件：

- `tools/runtime_compare/cli.py`

CLI 支持的核心操作有：

- `--config`
- `--add-task`
- `--list`
- `--cancel`
- `--status`
- `--wait`
- `--queue-mode`

CLI 本质上是一个“任务提交 + 轮询等待”的薄控制层，真正执行任务的仍然是 `TaskRunner`。

### 2.3 Web

文件：

- `tools/runtime_compare/ui/web/server.py`
- `tools/runtime_compare/ui/web/api.py`

Web API 提供了：

- 系统信息读取
- 系统信息保存
- 排队模式开关
- 任务添加、查询
- 配置文件导入导出
- 文件系统浏览

Web 模式适合在远程设备上执行，因为它允许在浏览器里做任务配置和状态监控。

## 3. 任务执行器 `TaskRunner`

### 3.1 结果目录命名策略

结果目录结构为：

```text
实验结果/<config_name>/<timestamp>_ws<work_scale>_r<repeats>/
```

其中：

- `config_name` 来自配置文件名
- `timestamp` 由 `now_ts_safe()` 生成
- `ws` 表示工作负载规模
- `r` 表示重复次数

这使得目录名本身就编码了关键实验参数。

### 3.2 编译策略

`compile_one()` 的关键特点：

- 只编译当前入口文件，避免 baseline/prio 同目录下出现重复 `main`
- 编译参数默认来自 `config/defaults.py`：
  - `-O0`
  - `-g`
  - `-std=c11`
  - `-pthread`
  - `-Wl,--wrap=main`
  - `-lm`
- 额外注入：
  - `-DWORK_SCALE=<task.work_scale>`

如果出现 `__wrap_main` 相关链接失败，还会自动回退，重新尝试“不带 `--wrap=main`”的编译。

### 3.3 运行与统计

每一轮实验都执行：

```text
baseline
-> prio
```

并重复 `repeats` 次。

统计输出包含：

- `min_s`
- `max_s`
- `mean_s`
- `median_s`
- `times_s`
- `delta_mean_s`
- `improvement_ratio`

其中：

```text
improvement_ratio = (baseline_mean_s - prio_mean_s) / baseline_mean_s
```

## 4. 结果文件格式

### 4.1 `summary.json`

这是最重要的单任务结果文件。样本中包含：

- 任务参数：
  - `task_id`
  - `created_at`
  - `cpu_set`
  - `cores_per_task`
  - `work_scale`
  - `repeats`
- 代码与编译信息：
  - `baseline.c_file`
  - `prio.c_file`
  - `compile_cmd`
- 统计信息：
  - `stats`
  - `times_s`
- 逐次运行信息：
  - `runs[]`
- 汇总指标：
  - `delta_mean_s`
  - `improvement_ratio`

### 4.2 `runs.csv`

逐次运行记录，列包括：

- `program`
- `iter`
- `time_s`
- `wall_s`
- `parsed_from_stdout`
- `cpu_set`

它适合：

- 画箱线图
- 做抖动分析
- 交叉验证 `summary.json`

### 4.3 `run.log`

完整运行输出日志，原样保存 baseline/prio 每轮运行的 stdout/stderr。

### 4.4 `run_results_*.txt`

更偏“人类可读报告”，内容包括：

1. 配对结果表
2. baseline/prio 统计
3. 各轮原始日志

## 5. 一个关键实现细节：时间解析口径

### 5.1 代码的预期

`tools/runtime_compare/utils/time_parse.py` 的 `parse_internal_time_seconds()` 设计上优先解析：

- `PROGRAM_TOTAL_NS=...`
- 或包含 `total time` 的输出行

### 5.2 当前样本的实际情况

但是 `TaskRunner.run_prog()` 调用解析函数时，只把：

- `stdout`

传给 `parse_internal_time_seconds(out)`。

而已有样本中的 `PROGRAM_TOTAL_NS=...` 实际出现在：

- `stderr`

因此：

- `parse_internal_time_seconds()` 返回 `None`
- 系统进入回退逻辑
- 使用 `wall_ns / 1e9` 作为 `time_s`
- 并把 `parsed_from_stdout` 记为 `false`

这与样本 `summary.json` 完全一致。

### 5.3 这意味着什么

这意味着当前 `runtime_compare` 结果里的 `time_s` 在很多现有样本中实际表示：

- 外层进程 wall time

而不是：

- 程序内部报告时间

这个事实不会让结果无效，但会改变论文中“测量口径”的描述，必须明确写出。

## 6. `experiment/` 结果沉淀与总表脚本

### 6.1 单任务结果沉淀

`experiment/experiment2虚拟机实验结果汇总/` 与 `experiment/experiment2（rk3588）实验结果/` 中的每个时间戳子目录都保留了：

- `summary.json`
- `runs.csv`
- `run.log`
- `run_results_*.txt`

这说明 `experiment/` 的内容不是手工整理表格，而是从运行时工具目录迁移或汇总得到的“原始实验证据”。

### 6.2 汇总脚本

脚本：

- `experiment/experiment2实验总表/scripts/build_platform_config_results.py`

做的事情是：

1. 遍历 VM 和 RK3588 根目录下的 `summary.json`
2. 从 `baseline/prio.stats` 提取：
   - `mean_s`
   - `min_s`
   - `max_s`
   - `repeats`
   - `cpu_set`
3. 生成 CSV 和 Markdown 表格

输出包括：

- `config_results_vm.csv`
- `config_results_rk3588.csv`
- `config_results_all.csv`
- `config_results_by_platform.md`

### 6.3 路径假设

这个脚本内部会向上寻找父目录名为：

- `mycallyplus_v1`

的项目根目录。

因此它与当前仓库已经改名为 `ScratchDAG` 的状态并不完全一致，属于一个明显的历史命名残留。

## 7. 跨平台总表里的现成结论

从 `config_results_by_platform.md` 可直接读取：

- VM 共 6 组配置，`improvement_ratio` 平均约 `0.251746`
- RK3588 共 7 组配置，`improvement_ratio` 平均约 `0.279808`

也就是说，在当前 `experiment2` 样本里：

- prio 相对 baseline 在 VM 上平均下降约 `25.17%`
- prio 相对 baseline 在 RK3588 上平均下降约 `27.98%`

这类数字非常适合直接写入论文实验结果总结。
