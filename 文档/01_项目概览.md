# 项目概览

## 1. 项目定位

`ScratchDAG` 是一个面向 C/C++ 程序的线程 DAG 构建与实验工具链。它的核心目标不是单纯“画调用图”，而是把程序逐步变成可以做时序分析和调度试验的图模型：

```text
GCC RTL .expand / C 源码
-> 调用图与线程关系
-> 执行 DAG
-> Level-1 / Level-2 分块
-> 分段测时
-> 带权 DAG
-> 调度算法
-> 优先级插桩实验
```

## 2. 当前仓库包含的能力

从代码和 README 看，仓库目前覆盖以下功能：

- 从 GCC RTL `.expand` 解析函数、调用、符号引用。
- 识别 `pthread_create` / `pthread_join`，补齐线程创建和汇合边。
- 导出 DOT、PNG、`circle.txt`、函数范围和内部元数据。
- 对互斥锁和信号量做可视化叠加分析。
- 生成 Level-1 与 Level-2 分块 DAG。
- 对调用点或代码段进行自动插桩，编译并运行程序，生成时间统计。
- 在带权 DAG 上运行 `LPF`、`CPF`、`HEFT`、`Zhao2020(CPC)` 等调度策略。
- 将调度结果转成源码优先级插桩。

## 3. 仓库的演化状态

当前代码不是一个“从零统一设计”的仓库，而是明显经历了多阶段演化：

- 早期主线：`generation/legacy.py` 驱动的单体式生成逻辑。
- 中期扩展：`time_analysis.py`、`scheduler.py`、`level1/*`、`level2/*` 形成实验工具链。
- 新架构方向：`pipeline/*` 把分块、测时、调度、插桩拆成独立 stage。
- 兼容遗留：大量模块仍把包名写成 `mycallyplus_v1`，说明仓库重命名为 `ScratchDAG` 后尚未完成统一。

这意味着理解本项目时，不能只看一个入口文件，而要把“生成链路”和“实验链路”连起来看。

## 4. 目录层面的主干

| 目录/文件 | 作用 |
| --- | --- |
| `cli.py`、`__main__.py` | 统一入口，分发到 GUI、viewer、legacy、pipeline |
| `generation/` | 调用图生成、DOT 导出、`circle.txt` 导出、源码绑定 |
| `core/` | 现代化数据模型、解析器、线程补边等基础能力 |
| `level1/` | Level-1 分块、段级测时、优先级插桩 |
| `level2/` | Level-2 分块、`post->wait` 图合成 |
| `pipeline/` | 新的模块化工作流：collect/blocks/timing/schedule/instrument |
| `time_analysis.py` | 面向调用点的自动插桩与时间分析 |
| `scheduler.py` | 长路径与 CPC 调度分析 |
| `ui/` | 统一 GUI 工作台 |
| `visualization/` | 独立 DAG 可视化查看器 |
| `中间结果/` | 所有阶段性产物的默认保存位置 |

## 5. 当前最重要的工程事实

有两个事实需要优先记住：

1. `generation/legacy.py` 仍然是最上游的“数据源制造器”。  
   `level1`、`level2`、`pipeline.collector` 都默认它已经产出了 `dag.dot`、`functions_full.json`、`functions_ranges.json`、`mycalls_meta_internal.json`、`circle.txt`。

2. `pipeline/*` 代表项目未来更清晰的组织方向，但它还没有彻底脱离旧命名和旧实现。  
   它本质上是在“复用现有 Level-1/Level-2/插桩代码”的基础上，加了一层统一 stage 封装。
