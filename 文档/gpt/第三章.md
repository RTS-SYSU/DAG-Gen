# 第三章 Execution DAG 构建的技术实现

本章面向系统研究论文写作，说明 ScratchDAG 如何从多线程程序源码及其 GCC RTL 中间表示出发，构建可供后续测时、调度和优先级插桩使用的 Execution DAG。本文不按“工具使用说明”组织，而是按“代码实现 -> 系统机制 -> 论文方法”的方式，解释系统内部的表示、分析步骤和依赖恢复逻辑。

从当前仓库实现看，Execution DAG 的上游构建主线集中在 `generation/legacy.py`。该模块负责完成 RTL 解析、调用点建模、线程生命周期依赖恢复、基础图导出以及节点元数据整理。线程补边与源码兜底绑定由 `generation/thread_map.py` 和 `generation/source_binder.py` 协同实现；同步原语的外部化表示由 `generation/exporters.py` 导出为 `circle.txt`。后续的 `level1`、`level2`、`time_analysis.py`、`scheduler.py` 与 `pipeline/*` 都建立在这些基础产物之上。因此，若论文第三章的主题是 Execution DAG Construction，其实现依据应以 `legacy` 生成链路为主，而非以调度或实验脚本为主。

## 3.1 Execution DAG 构建流程总体架构

ScratchDAG 的总体目标不是简单恢复一个静态函数调用图，而是把多线程程序转化为一个带有调用顺序、线程依赖和同步语义的执行图表示。当前代码实现对应的总体流程可以概括为：

```text
C 源码 + GCC RTL(.expand)
-> RTL 静态扫描
-> 函数与调用点抽取
-> 条件上下文与源码位置绑定
-> pthread_create / pthread_join 依赖恢复
-> 同步原语事件抽取
-> Execution DAG 导出
-> 节点元数据、函数范围与同步配置导出
```

这一流程在代码中的职责划分如下：

1. `generation/legacy.py`
   负责读取 `.expand`，识别函数、调用点、符号引用、条件前缀、线程创建/汇合事件，并输出 `dag.dot`、`functions_full.json`、`mycalls_meta_internal.json` 等核心中间结果。

2. `generation/thread_map.py`
   负责把解析阶段记录在 `myinfo` 中的线程句柄、线程入口和 join 节点映射转化为显式线程补边，特别是 `tail -> join` 类型的同步边。

3. `generation/source_binder.py`
   当 RTL 中的寄存器回溯不能稳定恢复 `pthread_create` 与 `pthread_join` 的参数绑定时，该模块回退到 C 源码层面，通过轻量级正则和函数体边界扫描，恢复 create/join 的对应关系。

4. `generation/exporters.py`
   负责扫描已经编号的同步原语调用点，生成 `circle.txt`。这个文件不是附属可视化配置，而是同步语义的外部化表示，后续 Level-2 分块和 viewer 都依赖它。

5. `core/func_ranges.py`
   负责从 C 源文件中抽取函数起止范围和有效语句边界。虽然它不直接参与 `dag.dot` 的生成，但它把 Execution DAG 节点重新映射回源码区间，是后续段级 DAG 构建的基础。

需要强调的是，当前仓库中存在“legacy 生成链路”和“pipeline 模块化链路”两套组织形式，但从真实依赖关系看，后者并未替代前者。`pipeline`、`level1`、`level2` 和 `time_analysis.py` 共同消费 `legacy` 生成的基础结果。因此论文中的系统架构图更适合画成“两层结构”：上层是 Execution DAG 生成层，下层是基于 DAG 的分块、测时与调度实验层。

## 3.2 静态程序分析实现

### 3.2.1 RTL 文件解析

ScratchDAG 的静态分析入口是 GCC 生成的 `.expand` 文件。`generation/legacy.py` 通过正则表达式直接扫描 RTL 文本，而不是构建完整 AST 或依赖外部编译器插件。该实现的核心匹配模式包括：

- 函数头：`^;; Function ...`
- 调用语句：`(call ...)`
- 符号引用：`(symbol_ref ...)`
- 源码位置：`"file.c":line:col`

这一设计体现了研究原型系统的一个重要取舍：系统只抽取 DAG 构建所需的最小语义，而不追求对 RTL 的全量语法恢复。对论文而言，可以将其表述为一种“目标导向的轻量级静态分析器”，其关注点是函数边界、调用事件和线程相关参数，而不是完整语义重建。

具体而言，`legacy.py` 对同一组 RTL 文件执行两次逻辑扫描：

1. 预读阶段
   主要用于恢复条件跳转上下文和 `pthread_join` 的参数绑定。该阶段从 `jump_insn`、`if_then_else`、`label_ref`、`code_label` 等标记中构造控制前缀线索，并通过 `preparse_pthread_join_bindings()` 预先提取 join 调用中绑定的线程句柄变量。

2. 主解析阶段
   逐行扫描所有 RTL 条目，建立函数表 `functions`，并在遇到 `call`、`symbol_ref` 与源位置信息时更新调用图与元数据。

与传统 call graph 不同，这里真正被保留下来的不是单纯的“函数 A 调函数 B”，而是“函数体中第 k 个调用事件发生在什么控制流上下文和源码位置”。这也是它能继续向 Execution DAG 扩展的原因。

### 3.2.2 函数定义识别

系统以函数名为主键维护全局字典 `functions`。当扫描到 `;; Function ...` 行时，解析器会：

1. 创建该函数的字典条目。
2. 初始化其 `files`、`calls`、`refs`、`callee_calls`、`callee_refs`、`mycalls`、`myinfo`、`mycalls_meta`、`call_src`、`call_src_full` 等字段。
3. 将当前 `.expand` 文件路径加入 `files`。

这说明 ScratchDAG 内部同时维护了两类关系：

- 集合型关系：`calls`、`refs`
  用于表示某函数“可能调用/引用了什么”，适合构建传统调用图和反向索引。

- 顺序型关系：`mycalls`
  用于表示“调用点在函数体内出现的顺序”，这是 Execution DAG 构建真正需要的结构。

因此，`functions` 不是一个普通的符号表，而是一个兼具静态调用信息和执行顺序信息的复合中间表示。

### 3.2.3 调用点提取

主解析阶段一旦匹配到 `(call ...)`，就会提取目标函数名，并结合控制前缀与编号信息生成调用节点。该过程具有三个关键特征。

第一，系统区分“被调函数语义”和“调用点实例”。  
`calls[origin_target]` 保留的是语义上的被调目标；而 `mycalls` 中保存的是已经编号、并可能带有条件前缀的节点名，例如：

- `main/pthread_create3`
- `worker/if/sem_wait7`
- `controller/switch2/pthread_mutex_lock5`

因此，同一 API 或同一被调函数的多次调用，在 DAG 中会被建模为不同节点，而不会被压扁成一个函数级点。

第二，系统把控制流局部上下文编码到节点名中。  
如果当前 RTL 状态机判断调用处于 `if`、`while` 或 `switch` 上下文，解析器会分别附加 `if/`、`while/`、`switchN/` 前缀。这样做的意义不是精确恢复 CFG，而是在 DAG 层面保留足够的局部控制语义，使后续 viewer 能单独渲染条件节点，也使相同 API 在不同控制上下文下可被区分。

第三，系统为每个调用点保留源码位置。  
当解析器识别完一个 call 之后，会将该节点暂存到 `current_func`，并在随后出现的源位置信息中把 `(file, line, col)` 绑定到 `mycalls_meta[current_func]`。从而，Execution DAG 的每个调用节点都可以回溯到具体的源文件和行列号。

### 3.2.4 符号引用解析

对于不一定构成直接调用、但能反映依赖关系的 `symbol_ref`，系统将其保存在 `refs` 字段中。`refs` 的作用主要有两点：

1. 保留被引用但未必实际构成 callsite 的符号信息。
2. 为后续寄存器回溯和线程入口恢复提供辅助线索。

在论文表述中，可以把 `symbol_ref` 解释为“RTL 层面显式暴露的符号依赖”，它并不等价于 Execution DAG 中的执行节点，但它是恢复线程参数、同步对象和被调目标的重要证据来源。

### 3.2.5 `legacy` 对 create、join、条件与同步的具体识别规则

如果第三章希望写到“实现细节”而不仅是“模块职责”，则必须明确 `legacy.py` 并不是通过统一语义分析框架识别这些事件，而是通过一组面向 RTL 文本模式的正则和状态变量完成识别。其核心规则如下。

#### 1. 普通函数与 callsite

普通函数与调用点的识别依赖以下模式：

- `function = ^;; Function ...`
- `call = ^.*\\(call.*"(?P<target>.*)".*$`
- `symbol_ref = ^.*\\(symbol_ref.*"(?P<target>.*)".*$`
- `src_re = "(?P<file>...)":(?P<line>\\d+):(?P<col>\\d+)`

即，`legacy` 首先把所有调用统一当作普通 `(call ...)` 事件处理，再在后续步骤中对 `pthread_create`、`pthread_join`、mutex、semaphore 等特殊 API 做语义增强。

#### 2. `pthread_create`

`pthread_create` 的识别并不依赖单独的“create 语句解析器”，而是在 callsite 被识别之后，通过目标名包含 `pthread_create` 触发专门分支。该分支同时使用四组线索：

- `mytaskset = (set (reg:DI 1 dx))`
- `mytask = (symbol_ref:DI ("..."))`
- `mythreadset = (set (reg:DI 5 di))`
- `mythread = (symbol_ref:DI ("..."))`

其基本含义是：

- `reg1(dx)` 对应线程入口函数；
- `reg5(di)` 对应线程句柄变量。

实现上，`legacy` 会先在局部扫描中记录 `mytaskset/mytask` 与 `mythreadset/mythread`，再在真正命中 `pthread_create` callsite 时调用 `_resolve_symbol_from_reg_history()` 回溯最近若干条 RTL 赋值，把寄存器编号解析成符号名。若 RTL 回溯失败，则退回 `generation/source_binder.py`，从 C 源码里的 `pthread_create(a1, a2, a3, a4)` 提取第三个参数作为线程入口函数。

#### 3. `pthread_join`

`pthread_join` 的识别同样是“普通 callsite + 专门增强”。主解析阶段只根据 `target` 中是否包含 `pthread_join` 判定它是 join 节点；真正困难的是恢复 join 的线程句柄变量。

为此，`legacy` 在主解析前先执行 `preparse_pthread_join_bindings()`。该函数预读全部 RTL 文本，并使用以下模式：

- `join_call_re`：定位 `pthread_join` 调用；
- `set_di_re`：定位 join 第一个参数所在的 `DI` 寄存器赋值；
- `symbol_ref_name_re`、`dbg_reg_re`、`plain_reg_re`：沿寄存器赋值链回溯真实符号名。

该阶段最终得到 `join_bindings[i] = 第 i 个 pthread_join 对应的线程句柄变量`。主解析阶段遇到 join 时，仅按出现顺序取出 `join_bindings[join_index]`，并写入 `myinfo[join_node] = join_handle`。因此，join 的“识别”和“配对”实际上分布在两个阶段完成。

#### 4. 条件语句

`legacy` 对条件语句的识别不是直接解析源代码中的 `if (...)`、`while (...)`、`switch (...)` 文本，而是通过 RTL 的跳转和标签模式间接推断控制上下文。相关模式包括：

- `condition_myjump = (jump_insn N)`
- `condition_if = (if_then_else ...)`
- `condition_jump = (label_ref N)`
- `condition_code = (code_label N)`

实现分为两个步骤：

1. 预读阶段构造 `functions_pre[func]`
   每个函数维护一串 `("jump", label)`、`("jump1", label)`、`("code", label)` 事件，用于描述当前函数的跳转-标签结构。

2. 主解析阶段运行状态机
   通过 `state_1` 到 `state_7` 的状态转移，决定当前 callsite 应附加哪一种前缀：
   - `state_2 == 1` 时加 `while/`
   - `state_4 == 1` 时加 `if/`
   - `state_6 == 1` 时加 `switchN/`

也就是说，条件上下文不是在渲染时推断出来的，而是在节点命名阶段就已经编码进 callsite 名称。

#### 5. 同步语句

对 `pthread_mutex_lock`、`pthread_mutex_unlock`、`sem_wait`、`sem_post` 等同步语句，`legacy` 主解析阶段并没有专门的独立正则。它们首先和普通函数调用一样，通过 `(call ...)` 被识别成 callsite；随后才由 `generation/exporters.py` 根据字符串包含关系做二次筛选：

- `_is_mutex_api()`：检测 `pthread_mutex_lock/unlock`
- `_is_sem_api()`：检测 `sem_wait/post`

因此，同步语句的识别是“两段式”的：

1. `legacy` 把它们保留为普通调用点节点；
2. `exporters.py`、`level2/*` 再把其中一部分解释为同步语义。

### 3.2.6 条件识别覆盖范围与限制

从代码事实看，`legacy` 对条件和循环的识别并不是完全语义化的，因此第三章需要明确其覆盖范围。

第一，当前显式支持的前缀只有三类：

- `if/`
- `while/`
- `switchN/`

第二，`for` 循环没有独立前缀。  
由于 `legacy` 是从 RTL 跳转模式恢复控制上下文，而不是从源代码关键字恢复语义，因此 `for` 通常会被编译成与 `while` 类似的跳转结构。在这种情况下，它往往被归入 `while/` 前缀，而不是被单独标记为 `for/`。因此论文若要提到 `for`，应写成“循环结构在当前实现中统一折叠到类似 `while` 的跳转模式”。

第三，`do-while`、复杂嵌套分支和部分优化后 RTL 结构并不保证被完全区分。  
代码中虽然定义了 `condition_barrier` 等变量，但并未形成完整的 barrier 驱动状态转移逻辑；条件识别主要依赖 `jump_insn / if_then_else / label_ref / code_label` 的经验式状态机，因此它更适合描述为“保守的局部控制上下文恢复”，而不是“完整 CFG 重建”。

第四，条件变量同步当前未被纳入同步语义恢复。  
`pthread_cond_wait` 和 `pthread_cond_signal` 若出现在 `.expand` 中，通常只会作为普通 callsite 保留在 `mycalls` 中，而不会在主线中形成专门的同步边或外部化配置项。

## 3.3 调用点与函数调用建模

### 3.3.1 callsite 的系统定义

在 ScratchDAG 中，callsite 不是抽象意义上的“某函数被调用”，而是函数体内部一个具有以下属性的具体调用事件：

- 所属函数；
- 控制流上下文前缀；
- 在该函数中的出现序号；
- 被调目标或同步 API；
- 源码位置 `(file, line, col)`；
- 可能附带的线程/同步语义。

也就是说，callsite 是系统内最核心的 Execution DAG 节点候选。函数本身更像是容器，真正的执行顺序由 `mycalls` 中的 callsite 序列给出。

### 3.3.2 callsite 与被调函数的关联方式

ScratchDAG 并没有将调用点和被调函数完全合并为单个节点，而是采用了一种“调用事件节点 + 被调函数语义目标”混合建模方式。

对于普通调用：

1. `calls[origin_target] = True`
   记录语义上的被调函数名。

2. `mycalls.append(target)`
   记录真正进入 Execution DAG 的调用点节点名，其中 `target` 已经被编号，并可能带有条件前缀。

这样做的好处是：

- `calls` 便于计算反向调用关系和函数级摘要。
- `mycalls` 便于构造顺序边、线程边和源码映射。

对 `pthread_create`，建模方式更进一步。系统会先把 create 调用本身作为一个 callsite 节点加入 `mycalls`，再把解析出的线程入口函数名作为下一个节点加入 `mycalls`。因此，在 DOT 渲染时可以直接输出：

```text
create_callsite -> thread_entry
```

这意味着线程创建事件不是抽象注释，而是以显式节点和边参与图构建。

### 3.3.3 源码位置记录机制

系统对 callsite 的源位置记录采用“延迟绑定”策略。原因在于 RTL 中 `(call ...)` 与源位置标记不一定以统一格式在同一字段中出现，因此实现上采取如下办法：

1. 识别 call 之后，将该节点名记录到 `current_func`。
2. 设置 `function_source = 1`，表示下一个可用的 `"file:line:col"` 片段应绑定给当前 callsite。
3. 若匹配到 `const_loc` 风格的源位置，就将其写入：
   - `mycalls_meta[target]["file"]`
   - `mycalls_meta[target]["line"]`
   - `mycalls_meta[target]["col"]`

此后 `mark_extern_by_selected()` 会根据用户选中的目标源码文件，把同文件调用标记为内部调用 `extern=0`，把其他文件调用标记为外部调用 `extern=1`，并最终导出 `mycalls_meta_internal.json`。这一步非常关键，因为 Level-1、Level-2 和调用点级插桩都主要依赖“内部调用点”的位置信息。

### 3.3.4 调用节点实例化

Execution DAG 在函数级别上可能存在“同一被调函数被多个 callsite 复用”的情况。为减少后续图中的共享节点歧义，`legacy.py` 在解析完成后调用 `instfunctions()` 对多次被调用的函数进行实例化克隆：

- 第一次调用保留原函数名；
- 后续调用被改写为 `foo@instance1`、`foo@instance2` 等。

这一过程并不改变源码中的真实函数定义，而是对图表示进行“调用实例展开”。它的意义在于增强 DAG 表示的单次调用语义，弱化纯函数级图中的共享汇聚，从而更接近任务图建模。

需要指出的是，这一实例化并不能从理论上消除所有环，但它显著降低了多父节点共享函数导致的图收缩现象，是当前实现中从调用图向执行图过渡的重要工程机制。

## 3.4 线程生命周期依赖恢复

### 3.4.1 `pthread_create` 识别与线程入口恢复

ScratchDAG 对线程创建的识别以 `pthread_create` callsite 为触发点。`legacy.py` 在解析到该调用时，额外执行两类恢复逻辑。

第一类是寄存器回溯。  
按照当前实现假设，`pthread_create` 的：

- `reg1(dx)` 承载线程入口函数；
- `reg5(di)` 承载线程句柄变量。

`_resolve_symbol_from_reg_history()` 会向前回溯若干条 RTL 赋值语句，直到找到把目标寄存器绑定到 `symbol_ref` 的赋值，从而恢复：

- 线程入口函数 `reg_task`
- 线程句柄变量 `reg_handle`

第二类是源码兜底绑定。  
如果寄存器历史中无法稳定恢复入口函数，系统调用 `create_targets_from_source()`，从对应的 C 源函数体中扫描 `pthread_create` 调用，并提取其第三个参数作为线程入口函数。这一实现由 `generation/source_binder.py` 完成，支持函数体边界提取、句柄归一化以及轻量正则匹配。

恢复线程入口后，解析器会：

1. 将 `pthread_create` 本身作为 callsite 节点加入 `mycalls`；
2. 将线程入口函数加入 `mycalls`；
3. 在 `myinfo` 中写入：
   - `myinfo[thread_handle] = task_function`
   - `myinfo["tail"] = task_function`
4. 将该任务函数推入 `__create_queue__`，用于后续 join 配对兜底。

因此，线程创建事件在系统内并不是一条简单的注释信息，而是：

- 一个显式 callsite；
- 一个从创建点指向线程入口的执行边；
- 一个后续 join 恢复所需的绑定状态。

### 3.4.2 `pthread_join` 识别与线程结束恢复

`pthread_join` 的难点不在于识别 API 本身，而在于恢复“它等待的是哪个线程”。当前实现采用预读 + 运行期写入的组合策略。

预读阶段中，`preparse_pthread_join_bindings()` 会扫描所有 RTL，定位 `pthread_join` 调用，并向前回溯对应的 `DI` 寄存器赋值链，尝试找出 join 的第一个参数，也即线程句柄变量。其返回结果是一个按出现顺序排列的 `join_bindings` 列表。

主解析阶段遇到 `pthread_join` 时：

1. 取出当前 `join_index` 对应的句柄变量；
2. 生成该 join callsite 节点；
3. 在 `myinfo` 中写入：
   - `myinfo[join_node] = join_handle`

此时系统尚未直接知道 join 对应的线程尾节点，但已经建立了“join 节点 -> 线程句柄”的映射。

### 3.4.3 线程尾节点与 join 补边

线程结束事件并不是通过显式 `pthread_exit` 节点恢复，而是通过每个线程函数当前的 `tail` 字段近似表示。解析器在处理 callsite 时持续更新 `myinfo["tail"]`，使其总是指向该函数当前已知的最后一个执行节点。对线程入口函数而言，这个 `tail` 被视为线程生命周期在图中的结束位置。

解析完成后，`build_join_binding_map()` 会综合所有函数的 `myinfo` 构建四层映射：

- `handle_to_thread`
- `thread_to_tail`
- `handle_to_joins`
- `tail_to_joins`

随后 `append_join_edges()` 把 `tail -> join` 边显式写入 DOT。若 `myinfo` 中映射不完整，`generation/thread_map.py` 还提供 `resolve_join_edges()` 和 `bind_from_source()` 作为兜底机制。源码绑定使用线程句柄表达式的归一化表示，例如：

- `&thread` -> `sym:thread`
- `threads[i]` -> `sym:threads[i]`
- `ctx->thr` -> `mem:ctx->thr`
- `*p` -> `deref:p`

这种设计的研究意义在于：系统并不依赖运行时 trace，也不需要完整别名分析，而是通过 RTL 证据和轻量源码绑定恢复出足够精确的线程生命周期依赖。

### 3.4.4 线程生命周期依赖的图语义

在最终 Execution DAG 中，线程生命周期依赖至少体现为两类边：

1. `create_callsite -> thread_entry`
   表示新线程的起始执行不能早于创建事件。

2. `thread_tail -> join_callsite`
   表示 join 同步必须等待线程主体结束。

这两类边共同把原本分散在调用图中的线程事件转化为显式的执行先后约束，使后续分块、测时和调度算法能够直接在图上操作并发依赖。

## 3.5 同步依赖关系恢复

### 3.5.1 同步原语的检测范围

当前代码中，对同步原语的显式建模重点集中在以下四类 API：

- `pthread_mutex_lock`
- `pthread_mutex_unlock`
- `sem_wait`
- `sem_post`

这些同步事件首先在 `legacy.py` 中以普通 callsite 的形式被识别、编号并放入 `mycalls`；随后 `generation/exporters.py` 进一步扫描这些节点，导出 `circle.txt` 作为同步语义的外部化表示。

需要如实指出的是，`pthread_cond_wait` 和 `pthread_cond_signal` 目前并没有像 mutex 和 semaphore 一样形成主线上的专门依赖恢复逻辑。它们在当前实现中至多被保留为普通调用点节点，但不会在 `legacy` 主链路中进一步转化为显式同步边。因此，如果论文需要讨论条件变量，应把它表述为“框架可扩展到其他同步原语，但当前实现重点支持 mutex 与 semaphore”。

### 3.5.2 `circle.txt` 作为同步语义载体

`generation/exporters.py` 中的 `CircleTxtExporter` 会扫描 `functions[func]["mycalls"]`，识别所有带编号的同步调用节点，并为其提取：

- 节点名；
- 原语类型；
- 变量名或对象名；
- 稳定编号；
- 源码行号；
- 源文件名。

对每个同步对象，导出文件按两大区段组织：

- `互斥量`
- `信号量`

`circle.txt` 的核心作用不是给用户看，而是把“同步原语事件及其配对线索”从解析阶段稳定地传递给后续模块。viewer 用它做可视化；Level-2 和 pipeline collector 用它恢复 `sem_post -> sem_wait` 依赖；研究上则可以把它解释为静态同步事件的外部化标注文件。

### 3.5.3 互斥量依赖的恢复方式

在当前仓库中，mutex 语义主要有两层用途。

第一层是可视化与区间识别。  
`circle.txt` 会记录 `pthread_mutex_lock` 与 `pthread_mutex_unlock` 的调用节点、变量名和位置。Level-2 构图时，`segment_dag_level2.py` 会基于 `mycalls_meta_internal.json` 中的有序调用点序列，用栈式匹配恢复每个函数内的 `lock/unlock` 区间。

第二层是段边界约束。  
在 Level-2 中，一旦恢复出某个临界区 `[lock_line, unlock_line]`，系统会删除位于临界区内部的切线，从而避免把同一临界区错误地切成多个段。这说明当前实现并没有直接在函数级 Execution DAG 上添加“lock -> unlock”顺序边，而是将 mutex 语义用于约束后续段级 DAG 的构造粒度。

从论文角度看，可以把这种设计解释为：ScratchDAG 在基础 Execution DAG 上先保留同步 callsite 作为事件节点，再把互斥约束主要投影到段级图构造阶段，以获得更适合调度分析的执行单元。

### 3.5.4 信号量依赖的恢复方式

信号量依赖恢复比 mutex 更接近显式边建模。`level2/merge_post_wait_dag.py` 会读取：

- `dag.dot`
- `circle.txt`

然后根据 `circle.txt` 中同编号的 `sem_post` 与 `sem_wait` 记录，显式增补：

```text
sem_post_node -> sem_wait_node
```

这一边在输出中被标记为 `sem_dep`。之后 `segment_dag_level2.py` 再把 callsite 级的 `post/wait` 节点映射回段 ID，使信号量同步依赖继续存在于段级 DAG 中。

因此，当前代码的同步依赖恢复具有以下特征：

- mutex：主要用于识别临界区并控制切分边界；
- semaphore：被进一步提升为显式执行顺序边；
- condition variable：尚未进入主线显式恢复逻辑。

## 3.6 Execution DAG 数据结构

### 3.6.1 以 `functions` 字典为核心的中间表示

尽管仓库中存在 `core/model.py` 和 `generation/model.py` 中的 dataclass 实现，但 Execution DAG 主线仍以 `legacy.py` 中的 `functions: dict` 为核心数据结构。每个函数条目至少包含：

- `files`
  该函数出现在哪些 RTL 文件中。

- `calls`
  语义级直接调用集合。

- `refs`
  符号引用集合。

- `callee_calls`、`callee_refs`
  反向索引，供后续遍历和分析使用。

- `mycalls`
  按源码出现顺序组织的调用点节点列表，是构建顺序边的核心。

- `myinfo`
  线程绑定、尾节点、join 配对和临时队列等附加状态。

- `mycalls_meta`
  调用点的 `(file, line, col, extern)` 元数据。

- `call_src`、`call_src_full`
  节点到源文件的映射，用于调试和追踪。

从研究方法上看，这相当于一个“函数容器 + 调用点流 + 线程状态”的复合表示。相比传统邻接表，它更适合表达执行顺序和跨阶段溯源。

### 3.6.2 节点结构

当前 Execution DAG 的节点可以分为三类：

1. 函数节点
   例如 `worker_fn`、`worker_fn@instance1`。它们代表线程入口或被调用函数实例。

2. 普通调用点节点
   例如 `main/printf7`、`worker/if/read_sensor3`。这类节点表示函数体中按顺序出现的具体调用事件。

3. 同步调用点节点
   例如 `main/pthread_create2`、`thread0/pthread_join9`、`worker/sem_post4`、`ctrl/pthread_mutex_lock5`。它们既是普通 callsite，也是线程与同步依赖恢复的锚点。

因此，ScratchDAG 的节点并不是单一粒度，而是函数实体与调用事件混合共存。这种设计牺牲了表示的纯粹性，但显著增强了对执行语义的表达能力。

### 3.6.3 边结构

在当前主线实现中，Execution DAG 的边主要来自三类约束。

1. 顺序边
   由 `mycalls` 中的相邻关系诱导。例如同一函数中的前一调用点连接到后一调用点。

2. 线程边
   由 `pthread_create` 与 `pthread_join` 恢复而来，具体包括：
   - create 节点到线程入口节点；
   - 线程尾节点到 join 节点。

3. 同步边
   在基础 `legacy` 输出中，同步原语首先表现为节点；在后续 Level-2 合成时，`sem_post -> sem_wait` 会被提升为显式 `sem_dep` 边。

其中 `dag.dot` 主要保存节点和边的图结构；`functions_full.json`、`mycalls_meta_internal.json` 和 `circle.txt` 保存补充元数据。

### 3.6.4 元数据结构

节点元数据主要保存在 `mycalls_meta` 中，其字段包括：

- `file`
- `line`
- `col`
- `extern`

这组元数据具有三个作用：

1. 把图节点映射回源码位置；
2. 区分内部调用点和外部调用点；
3. 为调用点级和段级插桩提供精确位置。

除此之外，`myinfo` 也是一种重要的结构化元数据。它不直接描述源码位置，而是描述节点之间隐藏的生命周期关系，例如：

- `tail`
- `thread_handle -> task_function`
- `join_node -> thread_handle`
- `__create_queue__`

这说明 ScratchDAG 的 Execution DAG 并不是“边一旦建完就结束”的静态结构，而是依靠附属元数据在多阶段中持续被解释和增强。

## 3.7 Execution DAG 构建算法

综合上述实现，可以把当前系统的构图算法概括为如下步骤。

### 步骤 1：提取函数与调用点节点

系统扫描 `.expand`，按函数头建立 `functions` 表。随后对每个 `(call ...)`：

1. 提取目标函数名；
2. 根据当前控制前缀状态附加 `if/while/switchN`；
3. 根据函数内出现次序追加编号；
4. 将节点名加入 `mycalls`；
5. 将语义被调目标加入 `calls`；
6. 将紧随其后的源位置写入 `mycalls_meta`。

至此，系统得到的是“按函数组织的调用点流”，而不是最终图。

### 步骤 2：恢复顺序执行依赖

当 `full_call_graph()` 遍历每个函数的 `mycalls` 时，会按顺序输出从前驱节点到后继节点的边。对条件节点，系统额外使用虚线样式或特殊连接方式保留局部控制语义，但总体仍遵循“函数体内调用事件的顺序投影”这一原则。

因此，Execution DAG 的基础骨架是由函数内的 callsite 顺序关系构成的。这一点与普通静态调用图不同：它不只关心“谁调用谁”，还关心“在同一执行路径上先发生什么、后发生什么”。

### 步骤 3：添加线程依赖

在线程创建点，系统通过寄存器回溯和源码兜底绑定恢复线程入口函数，并建立：

```text
create_callsite -> thread_entry
```

在线程汇合点，系统通过 join 句柄绑定与线程尾节点恢复，建立：

```text
thread_tail -> join_callsite
```

这一步把跨线程的生命周期先后关系嵌入原始图中，使图不再局限于单线程顺序。

### 步骤 4：添加同步依赖

在 `legacy` 主链路中，同步原语首先被保留为普通调用点节点，并导出到 `circle.txt`。之后：

- mutex 区间被用于限制段级切分；
- semaphore 对被提升为显式 `sem_post -> sem_wait` 边。

因此，从全系统角度看，Execution DAG 的同步依赖恢复是“节点保留 + 外部化表示 + 后续边增强”的分阶段过程，而不是在单个解析器中一次完成。

### 步骤 5：导出与验证

解析完成后，系统导出 DOT 与 JSON，并通过以下机制弱化非 DAG 风险：

1. `instfunctions()` 对多次调用函数做实例化展开；
2. 线程边总是按 create/join 的前后语义方向添加；
3. 信号量边按 `post -> wait` 的同步方向添加；
4. 后续 `scheduler.py` 和 `pipeline/algo/*` 会在调度前执行拓扑排序或显式环检测。

需要严格说明的是，当前 `legacy` 实现并不能形式化保证“任意输入程序必然得到严格 DAG”。递归、自环或复杂控制流仍可能在图中留下环结构。因此，对论文而言，更准确的表述不是“系统总能保证无环”，而是“系统采用 DAG-oriented 的节点展开和依赖恢复策略，并在后续调度阶段执行显式环检测与拒绝”。这比简单宣称“保证 DAG”更符合当前代码事实。

## 3.8 输出结果与数据产物

Execution DAG 构建完成后，ScratchDAG 会在 `中间结果/<base>/生成dag图/` 及相关目录下输出一组基础文件。它们共同构成后续分析阶段的统一输入接口。

### 3.8.1 图结构文件

- `dag.dot`
  Execution DAG 的 Graphviz 表示，是最直接的图结构输出。

- 可选 PNG
  若后续 viewer 或 Graphviz 渲染被调用，可生成配套图像文件。

这些文件主要服务于：

- 图结构调试；
- 可视化查看；
- Level-2 的信号量边合成。

### 3.8.2 节点与函数元数据

- `functions_full.json`
  导出完整 `functions` 字典，是最关键的调试与下游消费文件。Level-1 和 Level-2 都依赖它来恢复函数、调用点和线程关系。

- `debug/mycalls_meta.json`
  保存全部调用点元数据。

- `debug/mycalls_meta_internal.json`
  只保留内部调用点，供分块和插桩阶段使用。

- `functions_ranges.json`
  保存从源码中提取的函数范围、首条有效语句与末条有效语句，供段级 DAG 构造使用。

- `call_src_full.json`
  记录带编号节点到源文件的映射，便于调试和溯源。

### 3.8.3 同步语义文件

- `circle.txt`
  保存互斥量与信号量的调用节点、对象编号、源码位置等信息。该文件会被：
  - `visualization/viewer.py` 消费，用于同步原语高亮与线程图展示；
  - `level2/merge_post_wait_dag.py` 与 `level2/segment_dag_level2.py` 消费，用于恢复 `sem_dep`；
  - `pipeline/collector.py` 消费，用于生成 `sem_pairs.json` 和 `mutex_intervals.json` 等派生信息。

### 3.8.4 对后续阶段的作用

从系统设计角度，这些输出文件形成了一个稳定的阶段接口：

1. `legacy` 负责从源码和 RTL 构建 Execution DAG 及其元数据。
2. `level1`、`level2` 将节点级表示提升为段级表示。
3. `time_analysis.py` 和 `level1/time_analysis_level1.py` 把节点或段映射回源码并注入测时代码。
4. `scheduler.py` 与 `pipeline/algo/*` 在带权 DAG 上执行关键路径和优先级计算。
5. `pipeline/instrument.py` 或 `level1/instrument_prio_level1.py` 将调度结果重新回写源码。

因此，第三章在论文中的合理收束方式应当是：ScratchDAG 的 Execution DAG 构建并不是一个孤立的静态分析器，而是整个实验平台的统一上游表示层。`dag.dot`、`functions_full.json`、`mycalls_meta_internal.json` 与 `circle.txt` 共同定义了后续所有阶段的输入契约。

## 3.9 本章小结

综合当前代码实现，ScratchDAG 的 Execution DAG 构建机制可以概括为以下几点。

第一，系统以 `.expand` 为主分析输入，以轻量正则扫描提取函数、callsite、符号引用与源码位置，而不是依赖完整编译器前端。  

第二，系统真正的核心表示不是函数级调用集合，而是按函数组织的 callsite 顺序流 `mycalls` 及其元数据 `mycalls_meta`。这使得调用图能够进一步演化为执行图。  

第三，线程生命周期依赖通过 RTL 寄存器回溯、源码兜底绑定以及 `myinfo` 中的生命周期状态恢复出来，并在 DOT 中显式添加 `create -> entry` 与 `tail -> join` 约束。  

第四，同步原语并非一次性全部转成边，而是先作为调用点节点保留，再通过 `circle.txt` 把同步语义外部化；在当前实现中，mutex 主要约束段边界，semaphore 则进一步被提升为显式依赖边。  

第五，系统是“面向 DAG 的执行图构建器”，但严格无环性仍依赖实例化展开与后续调度前验证，而不是由解析阶段在理论上完全保证。  

基于这些机制，ScratchDAG 能够把多线程程序从源码和 RTL 层面的静态信息逐步转化为后续测时、调度与优先级实验可直接消费的 Execution DAG。这一表示层正是后续章节讨论分块、带权建模和调度实验的前提。
