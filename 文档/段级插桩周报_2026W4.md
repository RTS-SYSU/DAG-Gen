## 0. 名词与目标

### 0.1 名词

Level-1：  
指“段级（segment-level）”的分析与插桩流程。  
它不做 CFG 级别的热点/条件细分。  
只在函数内部按 pthread create/join 进行切割。  

Stage-1：  
只处理 cut points = pthread_create*、pthread_join*。  
不处理 if/while/switch 条件节点。  
不处理热点段（热路径/热语句）。  

标准 DAG：  
legacy 基于 RTL `.expand` 生成的调用 DAG（节点是函数或内部调用点）。  
其中 create/join 作为特殊节点参与线程边建模。  

段（segment）：  
在源 C 文件的某个函数内，按行号范围定义的一个代码片段。  
Stage-1 的段只有三种：  
- compute 段：多个连续语句行的区间。  
- create 段：pthread_create 的单行。  
- join 段：pthread_join 的单行。  

段级 DAG：  
节点是 seg_id。  
边分三类：intra / create / join。  
用于后续测时、LPF、插桩位置映射。  

LPF：  
这里指“Longest Path First”思想的优先级分配策略。  
以 DAG 中“到 sink 的最长路径”作为优先级依据。  
本实现采用“最长路径发现顺序分层”的策略。  

baseline/prio：  
同一工程的两份副本：  
- baseline：不插入优先级。  
- prio：按 schedule 在 compute 段起始插入 `l1_set_thread_prio_fifo(prio)`。  

run_experiments.sh：  
自动编译 baseline/prio，运行两次，记录总时间到文本文件。  
支持 WORK_SCALE 覆盖。  
结果文件自动去重命名，不覆盖旧文件。  

### 0.2 总目标

目标 1：  
从标准 DAG 出发，得到“段级 DAG（create/join 切割）”。  

目标 2：  
在不修改原始源文件的前提下，对段级 DAG 中的段进行测时。  
输出每段的 total_ns。  

目标 3：  
基于段级 DAG + 段耗时，计算 LPF 段优先级表。  

目标 4：  
自动生成 baseline/prio 两份工程副本。  
prio 副本插入优先级切换调用。  
测量两者“程序总耗时”。  

目标 5：  
将流程集成到 GUI：一键执行并产出可对比文件。

## 1. 目录结构与 base_name 规则（数据落盘的“合同”）

### 1.1 base_name（<base>）推导

规则：  
优先用源 `.c` 文件名 stem 作为 `<base>`。  
例如：`cpu4_thread10_fifo.c` → `<base>=cpu4_thread10_fifo`。  

若缺失源文件，仅有 `.233r.expand`：  
用 expand 去掉后缀后的前缀作为 `<base>`。  
例如：`foo.c.233r.expand` → `<base>=foo`（再按 legacy 的分割逻辑处理）。  

### 1.2 Level-1 统一目录

统一根：  
`mycallyplus_v1/中间结果/<base>/level1/`

Stage-1：  
- `stage1/segments_stage1.json`  
- `stage1/dag_stage1_seg.json`  
- `stage1/dag_stage1_seg.dot`  
- （可选）`stage1/dag_stage1_seg.png`（由 dot 渲染）  

测时：  
- `timing/<project>/time_result_seg.json`  
- `timing/<project>/trace/trace.<tid>.csv`  
- `timing/<project>/time_analysis_level1.log`  

调度：  
- `schedule/lpf_segment/schedule_seg.json`  
- （可选）`schedule/lpf_segment_entry/schedule_seg.json`  

实验：  
- `experiments/lpf_segment_<timestamp>/<project>/baseline/project/...`  
- `experiments/lpf_segment_<timestamp>/<project>/prio/project/...`  
- `experiments/lpf_segment_<timestamp>/<project>/compare.json`  
- `experiments/lpf_segment_<timestamp>/<project>/<project>/run_experiments.sh`（自动脚本）  
- `experiments/lpf_segment_<timestamp>/<project>/<project>/experiment/run_results_*.txt`  

注：  
这里 `<project>` 通常是源文件的 stem（例如 cpu4_thread10_fifo）。  
但对“源文件位于中文目录/多层目录”的情况，工程副本目录名会采用 `source_c.parent.name`。  
脚本与路径必须用该目录名。  

### 1.3 生成 DAG 的目录（legacy 合同）

标准 DAG 产物根：  
`mycallyplus_v1/中间结果/<base>/生成dag图/`

重要文件：  
- `functions_full.json`  
- `functions_ranges.json`  
- `debug/mycalls_meta_internal.json`  
- `call_src_full.json`（辅助，可选）

## 2. Step-0：标准 DAG 与元数据导出（legacy）

本步骤由 `mycallyplus_v1/generation/legacy.py` 完成。  
目的不是直接测时或插桩。  
目的在于生成 Stage-1 所需的“函数范围 + 内部调用点行号 + create/join 结构信息”。  

### 2.1 输入

必须输入：  
- RTL：`*.233r.expand`（gcc RTL 展开文件）  

可选输入（强烈建议）：  
- 源文件：`--source-file <path/to/foo.c>`  
  用于生成 `functions_ranges.json`，这是切段与插桩映射的关键。  

### 2.2 输出与含义

#### 2.2.1 functions_full.json

位置：  
`中间结果/<base>/生成dag图/functions_full.json`

内容：  
以函数名为 key 的 dict。  
每个函数包含：  
- `mycalls`：节点序列（含内部调用点，含 pthread_create/join 节点）。  
- `myinfo`：辅助映射（例如 join_node -> tid_var；tid_var -> entry_fn）。  
- 其他 debug/辅助字段。  

关键约定（重要）：  
在 `mycalls` 中，pthread_createX 节点后面紧跟线程入口函数节点。  
例如：  
`c3_fn/pthread_create8` 后面紧跟 `c4_fn`。  
这个约定被 Stage-1 用于构建 create 边。  

#### 2.2.2 debug/mycalls_meta_internal.json

位置：  
`中间结果/<base>/生成dag图/debug/mycalls_meta_internal.json`

内容：  
只包含 `extern==0` 的内部调用点元信息。  
结构：  
`{ fn_name: { node_name: {file,line,col,extern,...} } }`  

用途：  
Stage-1 需要知道 pthread_create/join 在源文件的行号。  
因此必须依赖这里的 `line` 字段。  

#### 2.2.3 functions_ranges.json

位置：  
`中间结果/<base>/生成dag图/functions_ranges.json`

生成条件：  
legacy 运行时提供 `--source-file <.c>`。  

生成实现：  
调用 `mycallyplus_v1/core/func_ranges.py`。  
这是一个纯文本解析器：  
先去掉注释/字符串，再定位函数定义，配对 `{}`。  

字段解释（每个函数一条）：  
- start_line：函数签名处行号（函数名出现位置）。  
- body_start_line：函数体 `{` 所在行号。  
- first_stmt_line：函数体内第一条“语句样”行号（尽力扫描）。  
- end_line：函数体 `}` 所在行号。  
- last_stmt_line：函数体内最后一条“语句样”行号（尽力扫描）。  
- last_return_line：最后一次出现 `return` 的行号。  
- level1_start_line：优先 first_stmt_line，否则 body_start_line。  
- level1_end_line：优先 last_stmt_line，否则 end_line。  

重要修复（本周关键）：  
早期 `last_stmt_line` 会把 `}` 当作最后语句之一（通过 `[;} ]` 正则），  
导致 `level1_end_line` 可能等于 `}` 行。  
当 compute 段包含 `return;` 以及 `}` 时：  
SEG_END 插到 `}` 前，但位于 `return` 后不可达。  
结果：该段只有 SEG_BEGIN 没有 SEG_END，trace 不完整。  

修复策略：  
last_stmt_line 优先取最后一个 `;`。  
如果没有 `;`，再回退到“最后非空非 brace 行”。  
这样 `level1_end_line` 更接近真实语句末尾。  

验证方法：  
以 `c3_fn` 为例：  
修复后其 `level1_end_line` 应落在 `return` 行而非 `}` 行。  
Stage-1 生成的最后 compute 段应为单行 return。  

### 2.3 运行命令（示例）

```bash
python3 -m mycallyplus_v1.generation.legacy \
  mycallyplus_v1/配置文件/cpu4_thread10_fifo/cpu4_thread10_fifo.c.233r.expand \
  --threads-only \
  --source-file mycallyplus_v1/源文件/cpu4_thread10_fifo/cpu4_thread10_fifo.c \
  --output-base mycallyplus_v1 \
  --force \
  --level1-stage1
```

## 3. Step-1：Stage-1 段切割（segments_stage1.json）

本步骤由 `mycallyplus_v1/level1/segment_dag.py` 完成。  
目标是把“函数范围 + create/join 行号”映射成“段列表”。  

### 3.1 输入

来自标准 DAG 目录：  
- `functions_full.json`  
- `functions_ranges.json`  
- `debug/mycalls_meta_internal.json`  

### 3.2 输出

位置：  
`中间结果/<base>/level1/stage1/segments_stage1.json`

内容：  
- cut_points：create/join 的列表（含 function、kind、node、line、entry_fn、tid_var）。  
- segments：段列表（seg_id、function、kind、start_line、end_line、cut_node）。  

### 3.3 seg_id 命名规范（非常重要）

compute 段：  
`THR:<func>#<idx>@<start>-<end>`  
例：`THR:c3_fn#001@103-114`  

create 段（单行）：  
`CRT:<func>#<idx>@L<line>`  
例：`CRT:c3_fn#002@L115`  

join 段（单行）：  
`JON:<func>#<idx>@L<line>`  
例：`JON:main#015@L409`  

说明：  
idx 按函数内段序从 1 递增。  
compute/create/join 混排计数。  
这个编号用于稳定定位“某个函数内第几个段”。  

### 3.4 CutPoint 提取逻辑（实现细节）

#### 3.4.1 create 的 entry_fn 推断

来源：`functions_full[fn].mycalls`。  
遍历每个函数的 mycalls 序列。  
若发现节点匹配 `pthread_create(\d+)?`：  
将该 node 的“下一个 mycalls 元素”作为 entry_fn。  
条件：entry_fn 必须是一个函数名且在 functions_full 中存在。  

该推断依赖 legacy 的“create 后紧跟入口函数”约定。  
如果未来 legacy 改变顺序，这里需要同步调整。  

#### 3.4.2 join 的 entry_fn 推断（链式创建支持）

join 映射更复杂，因为 join 只给线程句柄变量。  
实现分两层：  
- 优先用 join 所在函数的 myinfo：`join_node -> tid_var`，再 `tid_var -> entry_fn`。  
- 若 join 所在函数缺少 `tid_var -> entry_fn`（链式创建时可能出现在其它函数），  
  则全局扫描所有函数 myinfo，建立 `tid_var -> entry_fn` 的全局映射。  

这样支持：  
main join tc0，但 tc0 的创建可能在 main。  
而 tc1/ tc2 的创建可能在 c0_fn/c1_fn。  
join 的 entry_fn 仍然能推回去。  

### 3.5 切段算法（实现细节）

对每个函数 fn：  
读取其 `[level1_start_line, level1_end_line]`。  
收集其切点行：所有落在该区间内的 create/join 行号。  
将切点按行号排序。  

切段规则：  
对每个切点行 L：  
1) 若当前 cur <= L-1：生成 compute 段 `[cur, L-1]`。  
2) 生成 create/join 段 `[L, L]`。  
3) cur = L+1。  
最后：若 cur <= end：生成 compute 段 `[cur, end]`。  

这保证：  
create/join 行总是独立成段。  
compute 段不会跨越 create/join 行。  

### 3.6 示例（以 c3_fn 为例）

源代码结构：  
- 103..114：打印 + busy_wait + done print  
- 115：pthread_create(tc4, c4_fn)  
- 116：return NULL;  
- 117：}  

若 level1_end_line 错误包含 117：  
最后 compute 段是 116-117，包含 return + }。  
SEG_END 会插在 117 前，位于 return 后不可达。  
trace 缺失。  

修复 last_stmt_line 后：  
level1_end_line=116。  
最后 compute 段变成 116-116。  
SEG_END 插在 return 行之后（或插在 return 行之后的 after），可达。

## 4. Step-2：Stage-1 段级 DAG（dag_stage1_seg.json）

本步骤也由 `segment_dag.py` 生成。  
目标是把段列表提升为 DAG，使后续测时/LPF/插桩统一以 seg_id 为键。  

### 4.1 输出文件

位置：  
`中间结果/<base>/level1/stage1/dag_stage1_seg.json`

结构：  
- nodes：seg_id 列表（可包含孤立节点）。  
- edges：`{src,dst,kind}` 列表，kind ∈ {intra,create,join}。  

### 4.2 边构建逻辑

#### 4.2.1 intra 边

对每个函数 fn 的段序：  
按 start_line 排序。  
依次连接：seg[i] -> seg[i+1]，kind="intra"。  

意义：  
描述同一线程内、同一函数内段的执行顺序。  
这是最基础的“顺序控制流”。  

#### 4.2.2 create 边

对每个 create CutPoint c：  
找到 create 行所在的段 seg_create（一般就是对应的 CRT 段）。  
若 c.entry_fn 存在：  
取 entry_fn 的第一段 seg_entry_first。  
添加边：seg_create -> seg_entry_first，kind="create"。  

意义：  
描述线程创建后，入口函数的执行依赖于 create 调用发生。  

#### 4.2.3 join 边

对每个 join CutPoint c：  
找到 join 行所在段 seg_join（对应 JON 段）。  
若 c.entry_fn 存在：  
取 entry_fn 的最后一段 seg_entry_last。  
添加边：seg_entry_last -> seg_join，kind="join"。  

意义：  
描述 join 等待线程结束，必须在线程入口函数末段结束后才可发生。  

### 4.3 active segments（后续测时/LPF 使用）

观察：  
nodes 列表可能包含一些“孤立段”。  
原因：  
有些段没有在边上出现（没有 intra/create/join 关联）。  
或者由于 range/filter 导致某些函数段缺失。  

我们采用策略：  
active_seg_ids = edges 中所有 src/dst 的并集。  
后续测时与 LPF 只对 active_seg_ids 进行处理。  

实现位置：  
- `time_analysis_level1.py`：读取 dag_stage1_seg.json 的 edges，过滤 segments。  
- `lpf_segment.py`：只会对 segments 列表中的 compute 分配（但输入 segments 通常已与 active 对齐）。  

验证：  
`time_analysis_level1.log` 中会记录：  
active_seg_ids 数量、segments_total 数量、segments_instrumented 数量。

## 5. Step-3：段级测时（time_result_seg.json）

本步骤由 `mycallyplus_v1/level1/time_analysis_level1.py` 完成。  
目标：给每个段一个 total_ns（以及 count/min/max）。  

### 5.1 输入

必需：  
- `segments_stage1.json`  
- `dag_stage1_seg.json`（用于过滤 active segments）  
- 源 C 文件路径（用于复制工程）  

### 5.2 输出

主要输出：  
- `level1/timing/<project>/time_result_seg.json`  
- `level1/timing/<project>/trace/trace.<tid>.csv`  
- `level1/timing/<project>/time_analysis_level1.log`  

### 5.3 “不修改原始源文件”的实现方法

策略：  
永远不在 `mycallyplus_v1/源文件/...` 下改写。  
而是在中间结果目录创建工程副本：  
`level1/timing/<project>/<src_root_name>/`  

流程：  
1) `shutil.copytree(src_root, dest_project)`  
2) 在 dest_project 根写入 `segtrace.h/c`（运行时库）。  
3) 在 dest_project 内找到目标源文件（按 basename 匹配）。  
4) 对该源文件原地插入 `#include "segtrace.h"` 和段边界宏。  
5) 在 dest_project 内 gcc 编译运行。  

这样：  
原始源文件不变。  
所有插桩都在副本中发生。  

### 5.4 插桩规则（实现细节）

每个 segment 都尝试插：  
- begin：在 start_line 之前插入 `SEG_BEGIN("<seg_id>");`  
- end：在 end_line 之后插入 `SEG_END("<seg_id>");`  

include 插入位置：  
为了兼容 `_GNU_SOURCE` 等 feature-test macros：  
include 插入在这些宏之后。  

安全性检查（当前约束）：  
- 若 start_line 或 end_line 超出文件行数：skip。  
- 若 start_line > end_line：skip。  
- 若 start/end 行是控制语句头（if/for/while/switch）：skip + warning。  
- 多行语句暂不处理：文档记录为 TODO（当前靠“段边界在语句行”的假设）。  

关于 end 插入位置（避免跑出函数作用域）：  
若 end 行是 `}` 或以 `}` 开头：  
将 `SEG_END` 插到 end 行之前（before）。  
否则：  
插到 end 行之后（after）。  

### 5.5 运行时库 segtrace（实现细节）

文件：  
- `level1/segtrace.h`  
- `level1/segtrace.c`  

关键设计：  
- 使用 TLS 单槽（__thread）记录 `t0_ns` 和 seg_id。  
- 假设段不嵌套（Stage-1 成立）。  
- 每线程一个输出文件 `trace.<tid>.csv`，避免锁争用。  
- 时间使用 `clock_gettime(CLOCK_MONOTONIC)`。  

CSV 格式：  
`tid,"seg_id",begin_ns,end_ns,dur_ns`  

### 5.6 汇总 time_result_seg.json（实现细节）

读取每个 trace 文件，按 seg_id 聚合：  
- total_ns = sum(dur)  
- count = 记录条数  
- avg_ns = total/count  
- min_ns / max_ns  

注意：  
如果某段 begin/end 不匹配或 end 不可达，就不会产生记录。  
这会导致该段在 time_result 中缺失。  
因此我们修复了 func_ranges 以减少缺失。  

### 5.7 编译注意点与修复

我们遇到一个实际坑：  
若 source 指向 experiments 目录下的 baseline/prio 副本，  
其目录里可能含 `wrap_main.c` 与 `prog_timer.c`。  
time_analysis_level1 的 `_compile()` 若用 `rglob("*.c")` 全编译：  
会把 wrap_main 也编进去。  
但没有 `-Wl,--wrap=main` 时，`__real_main` 未定义。  
导致链接失败。  

修复：  
time_analysis_level1 编译时排除 `wrap_main.c` 与 `prog_timer.c`。  

### 5.8 验证方法（推荐）

看 log：  
`time_analysis_level1.log`  
检查：  
- active_seg_ids 是否合理  
- segments_instrumented 是否合理  
- 是否有大量 skip/warn  

看 time_result：  
随机抽几个 THR 段是否有 total_ns。  
并确认 create/join 段通常也会有很小的耗时（可留可忽略）。

## 6. Step-4：LPF 段优先级（schedule_seg.json）

本步骤由 `mycallyplus_v1/level1/lpf_segment.py` 完成。  
目标：为每个 compute 段分配整数优先级（1..prio_max）。  

### 6.1 输入

必需：  
- `dag_stage1_seg.json`（段级 DAG）  
- `segments_stage1.json`（节点元信息：kind、function、范围）  
- `time_result_seg.json`（compute 段权重）  

可配：  
- prio_max（默认 80）  
- only_entry_functions（当前需求：关闭，分配所有 compute）  

### 6.2 权重定义

create/join：  
权重固定为 0。  
原因：它们本质是同步/创建开销，且不应影响关键链计算。  

compute：  
权重 = `time_result_seg.json[seg_id].total_ns`。  
若缺失则当作 0（不建议长期如此，需要回到测时阶段补齐）。  

### 6.3 sink 选择

sink = main 最后一个段。  
实现：把 segments 按 function 分组，main 的段按 start_line 排序，取最后一段。  

原因：  
我们希望最长路径代表“程序完成前必须发生的关键链”。  
以 main 的最后段作为汇点最直观。  

### 6.4 DAG 校验与拓扑排序

LPF 需要 DAG 无环。  
实现：  
对所有节点做拓扑排序。  
若存在环，抛错。  

注意：  
理论上段级 DAG 不应有环。  
若出现环，往往是 create/join 映射错误或段顺序边错误。  

### 6.5 到 sink 的 crit 值（最长路径）计算

定义：  
crit[u] = 从 u 出发到 sink 的最大路径权重和（包含 u 的权重）。  

算法：  
1) 先计算可达性：只对能到达 sink 的节点计算 crit。  
2) 按拓扑逆序遍历：  
   - sink：crit[sink] = w(sink)  
   - 其他 u：crit[u] = w(u) + max(crit[v]) for v in succ(u)  

实现细节：  
为了后续“路径发现顺序”分配，我们额外记录：  
choice[u] = 使 crit 最大的那个后继 v。  
如果多个 v 具有相同 crit，则按 seg_id 字典序选择（稳定性）。  

### 6.6 本周定制策略：路径发现顺序分层分配

用户期望：  
按“路径长度”来分配优先级。  
最长路径拿最高优先级一段连续区间。  
第二长路径拿下一段连续区间。  
区间大小匹配路径节点数。  
同样长度则按“路径发现顺序”。  
每层用掉多少，下一层起点继续递减。  

实现策略（贪心）：  
current_prio = prio_max  
available = 所有未分配的 compute 段（可选再过滤 only_entry_functions）。  
循环：  
1) start = argmax_{u in available} crit[u]  
2) path = 从 start 开始沿 choice[] 一直走，直到：  
   - 到达 sink 后继缺失，或  
   - 遇到非 available 节点，或  
   - successor 缺失。  
3) 对 path 中每个 seg_id：  
   assigned[seg_id] = current_prio  
   current_prio -= 1  
   从 available 移除  
4) 直到 current_prio < 1 或 available 空。  

解释：  
这不是“枚举 K 条互不相交最长路径”的严格算法。  
它是“按当前 crit 最大的未分配节点”逐条发现关键链。  
它符合“发现顺序 + 连续区间”的需求，并且实现简单稳定。  

输出：  
`level1/schedule/lpf_segment/schedule_seg.json`  
其中 priorities 只包含 compute 且 weight>0 的段。  

验证：  
对 `cpu4_thread10_fifo`，应看到 c0/c1/c2/c3/c4 关键链段拿到 80..76。  
其它 compute 段拿到更低优先级。

## 7. Step-5：优先级插桩对照实验（baseline vs prio）

本步骤由 `mycallyplus_v1/level1/instrument_prio_level1.py` 完成。  
目标：自动产出两份工程副本并测总时，生成 compare.json 与可复现实验脚本。  

### 7.1 输入

必需：  
- 源 C 文件路径 `--source`  
- base_name（用于定位 stage1/timing/schedule）  
- schedule 文件（默认 `schedule/lpf_segment/schedule_seg.json`）  

### 7.2 输出结构

输出根：  
`level1/experiments/lpf_segment_<timestamp>/<project>/`  

其中：  
- baseline/project/<src_root_name>/*  
- prio/project/<src_root_name>/*  
- compare.json  
- （自动脚本）<project>/run_experiments.sh  

### 7.3 baseline/prio 副本生成（不改原始源）

实现：  
1) `src_root = source_c.parent`  
2) `copytree(src_root, baseline_proj)`  
3) `copytree(src_root, prio_proj)`  

保证：  
你永远可以回到原始源目录复现。  
任何插桩与改写都只发生在副本。  

### 7.4 prio 源文件重命名（区分副本）

需求：  
prio 副本的主源文件名加 `_prio` 后缀，避免和 baseline 混淆。  

实现：  
- prio_src_orig = prio_proj / source_c.name  
- prio_src_new = prio_proj / f"{stem}_prio.c"  
- rename 后在 prio_src_new 上做插桩。  

效果：  
在 prio 工程中可以一眼区分插桩版本。  
例如：`experiment1_prio.c`。  

### 7.5 prio 插桩规则（实现细节）

插桩目标：  
只插入 `l1_set_thread_prio_fifo(prio)`。  
不插入段测时代码。  
总时测量由 wrap_main 或脚本外层负责。  

插入位置：  
以 `segments_stage1.json` 为蓝图：  
- 只对 kind="compute" 的段。  
- 取 start_line。  
- 若该段在 schedule 中有优先级：在 start_line 对应位置插入一行调用。  

去重规则：  
同一行可能是多个段的 start_line（极端情况）。  
用 dict line_no -> max(prio) 去重。  

缩进规则：  
插入时取该行的前导空白，保持代码风格一致。  

include 规则：  
在 feature-test macros 后插入：  
`#include "prio_runtime.h"`  

### 7.6 prio_runtime.h（权限与失败标记）

`l1_set_thread_prio_fifo(int prio)` 的行为：  
调用 `pthread_setschedparam(pthread_self(), SCHED_FIFO, &sp)`。  

若失败：  
stderr 输出：`L1_PRIO_SET_FAILED rc=... errno=... (...)`。  

用途：  
GUI 或 compare.json 可据此提示“缺少 root/CAP_SYS_NICE”。  

### 7.7 compare.json 的总时测量（wrap_main）

compare.json 的 baseline_total_ns/prio_total_ns 来源：  
编译时加入 `-Wl,--wrap=main`。  
并在工程内加入：  
- `wrap_main.c`：实现 `__wrap_main`，内部调用 `__real_main`。  
- `prog_timer.c/h`：记录 begin/end，atexit 打印 `PROGRAM_TOTAL_NS=<ns>`。  

instrument_prio_level1 会运行 baseline 和 prio 二进制各一次：  
解析 stderr 中 `PROGRAM_TOTAL_NS`。  
写入 compare.json。  

注意：  
这是一种“无需改源文件 main”的总时测量方式。  
它不会污染源代码。  

### 7.8 run_experiments.sh（外层计时与 run_results）

为何还需要脚本：  
compare.json 只跑“一次”并且只抓 stderr 的 PROGRAM_TOTAL_NS。  
但我们需要一个“可重复、可调 WORK_SCALE、可保存日志”的工具。  

脚本功能：  
1) 编译 baseline/prio（跳过 wrap_main/prog_timer，避免 __real_main 链接问题）。  
2) 外层 `date +%s%N` 计时，得到 wall-time。  
3) 将 baseline/prio 的运行日志与 runtime 行写入 `experiment/run_results_*.txt`。  
4) 文件名防覆盖：若同名存在，自动追加 `_1/_2/...`。  

脚本路径：  
放在当前实验目录 `<...>/<project>/run_experiments.sh`。  
这样不会跨目录误指向。  

目录名兼容：  
工程副本目录名实际为 `src_root.name`。  
例如 `实验组`。  
脚本必须用该名字构造 `baseline/project/<src_root.name>`。  
本周修复了之前错误使用 `<project>` 的问题。  

### 7.9 sudo 与非交互环境注意

你在终端手动运行可用：  
`sudo bash run_experiments.sh`。  

在某些非交互环境（无 tty）运行 sudo 会报：  
`sudo: a terminal is required ...`。  
GUI 里默认不走 sudo。  
因此：  
GUI 自动执行脚本时可能无法获得 FIFO 权限。  
此时仍能运行，但 prio 设置可能失败（stderr 会有 L1_PRIO_SET_FAILED）。  

建议：  
真正做最终对比时，手动在终端以 sudo 跑脚本。

## 10. 常见报错与定位指南（按发生阶段）

### 10.1 legacy 阶段

现象：functions_ranges.json 未生成。  
原因：未传 `--source-file` 或源文件不存在。  
解决：确认 `--source-file` 是真实 `.c`。  

现象：stage1 生成失败。  
原因：输入 expand 错误或解析失败。  
解决：确认 `.233r.expand` 路径正确；必要时打开 debug 输出。  

### 10.2 测时阶段

现象：time_result_seg.json 缺失大量 THR 段。  
可能原因 1：段 end 在 `}` 或 return 后不可达（已通过 func_ranges 修复大部分）。  
可能原因 2：段边界落在控制语句行，被 skip。  
定位：看 `time_analysis_level1.log` 的 warnings/skipped。  

现象：编译失败 `__real_main` 未定义。  
原因：误编译了 wrap_main.c 但没有 `-Wl,--wrap=main`。  
解决：测时编译已排除 wrap_main/prog_timer；脚本也会排除。  

### 10.3 LPF 阶段

现象：分配数量很少。  
原因：time_result 缺失导致权重为 0，compute 段被过滤。  
解决：先保证测时覆盖。  

现象：报 DAG cycle。  
原因：段级 DAG 出现环（create/join 映射错误）。  
解决：检查 dag_stage1_seg.json 的边，确认 create/join 映射。  

### 10.4 实验与脚本阶段

现象：run_experiments.sh 报 Missing baseline/prio。  
原因：脚本使用了错误的 project 目录名（例如应为 实验组）。  
解决：模板已修复使用 `src_root.name`；旧脚本需重新生成或手工改 PROJECT_NAME。  

现象：prio_set_failed。  
原因：非 root/CAP_SYS_NICE。  
解决：sudo 运行，或给进程 CAP_SYS_NICE。  

现象：sudo 需要 tty。  
原因：在无交互环境运行 sudo。  
解决：在终端手动 sudo；GUI 内默认不 sudo。
