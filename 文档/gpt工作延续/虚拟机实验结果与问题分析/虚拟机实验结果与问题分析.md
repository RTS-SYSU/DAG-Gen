# 虚拟机实验结果与问题分析

## 1. 本次实验的背景

本次实验的目标是：

- 不使用 `rk3588` 历史结果
- 直接在当前会话所在虚拟机平台上，重新执行 `zhang1 / zhang2 / zhang3 × 5算法` 的粗略测试
- 只基于本轮新生成的结果分析各算法在虚拟机上的提升率
- 同时排查虚拟机平台上可能影响“数据真实性”的因素

本次测试对应文档中的“粗略对比实验方案（zhang1/2/3 × 5算法）”，但实际执行与汇总工作是本轮新完成的，不是从旧结果复制。

## 2. 运行平台确认

为避免把当前虚拟机数据与其他平台混淆，先对平台进行了确认。

执行命令：

```bash

```

得到结果：

```text

```

因此本轮实验平台可明确认定为：

- 虚拟化环境：`vmware`
- 架构：`x86_64`
- 内核：`5.15.96-rt61`

这说明本次实验结果属于“当前虚拟机平台数据”，不能与先前 `rk3588` 跑出的结果混为一谈。

## 3. 本次粗略测试的实验配置

本轮采用如下固定参数：

- 测试用例：`zhang1`、`zhang2`、`zhang3`
- 算法：`cpf`、`heft`、`zhao2020`、`wcet_first`、`t_level`
- `work_scale = 10`
- `repeats = 10`
- `cpu_set = [0, 1]`
- `cores_per_task = 2`
- `use_sudo = false`
- 执行模式：`queue_mode = true`

总任务数：

- `3 × 5 = 15` 组
- 每组包含 `baseline` 与 `prio`
- 每个版本各运行 `10` 次

## 4. 为什么这样配置可以用于“粗略测试”

本轮是“粗略测试”，不是最终论文级实验，因此重点是尽快得到：

- 每个样例上五个算法的大致收益方向
- 各算法在虚拟机平台上的横向对比
- 哪些样例明显受平台噪声影响

选择 `work_scale = 10` 的原因：

- `WORK_SCALE` 只对所有 busy-wait 工作量做统一缩放
- 不改变节点之间相对权重关系
- 不改变优先级分配逻辑
- 因此不改变“提升率的趋势判断”
- 但能明显缩短测试时间

## 5. 为保证数据真实性所做的控制

本轮不是简单“跑一下就记结果”，而是针对真实性做了几项控制。

### 5.1 只使用本轮新结果

本轮分析只使用当前虚拟机上新生成的 `summary.json`。

不使用：

- `rk3588` 历史结果
- 旧目录中的截图或人工摘录
- 以前不同 `work_scale` / `repeats` / 平台条件下的产物

### 5.2 固定 CPU 集合

运行时固定使用：

```json
"cpu_list": [0, 1]
```

这样做的目的是减少：

- 进程在不同 CPU 间迁移
- 调度器随机分配核带来的额外抖动
- 不同任务之间对更多核的争抢

### 5.3 使用串行队列模式

本轮启用了：

```json
"queue_mode": true
```

这样所有实验按顺序执行，而不是并发执行。

原因：

- 如果 15 组任务并行运行，会互相抢占 CPU
- 会破坏“同一参数、同一平台、同一 CPU 集合”下的可比性
- 串行执行虽然慢一些，但更适合当前“粗略测试 + 排除显著干扰”的目标

### 5.4 重复运行 10 次

每个 `baseline` / `prio` 版本各运行 10 次，而不是单次采样。

这样至少可以：

- 避免偶发单次异常主导结论
- 计算均值
- 进一步估计波动程度

### 5.5 对缺失结果做一致性检查与补跑

在汇总结果时，没有直接相信“目录里出现的文件数量”，而是检查了：

- 任务总数是否应为 `15`
- 实际生成的 `summary.json` 是否也为 `15`
- 每个 `summary.json` 反向解析出的 `base/algo` 是否完整

这一步发现了一个真实问题：

- 工具结果目录采用秒级时间戳
- 极快任务可能在同一秒内完成
- 导致不同任务写入同一时间戳目录
- 后写入的结果覆盖先写入的结果

这不是统计误差，而是结果组织层面的缺陷。

发现问题后，针对缺失项执行了单独补跑，避免把脏数据写进最终结论。

## 8. 结果解读

### 8.1 zhang2：结论最可靠

`zhang2` 是本轮虚拟机平台上最稳定的一组。

表现特征：

- 五个算法全部正收益
- `baseline` 和 `prio` 的 `CV` 都相对较低
- 平均提升率大约分布在 `7% ~ 13%`

其中：

- `zhao2020` 的均值提升最高：`+12.822%`
- `t_level` 次之：`+11.375%`

因此，如果只从这轮虚拟机粗测里挑一组最可信的横向比较，优先看 `zhang2`。

### 8.2 zhang3：均值普遍为正，但噪声重

`zhang3` 的均值结果看上去也不错：

- 五个算法均为正收益
- `cpf`、`t_level` 提升较明显

但问题也很明显：

- 多个 `baseline_CV` 超过 `15%`
- 有的接近或超过 `20%`

这说明：

- 虚拟机平台对 `zhang3` 的 baseline 版本干扰较大
- 当前 `repeats = 10` 只能支持“粗略判断趋势”
- 不能据此直接给出强结论

### 8.3 zhang1：短程序最容易受虚拟机噪声影响

`zhang1` 的运行时间非常短，多个均值只有 `20ms` 左右。

这种短程序在虚拟机上最容易受到以下因素影响：

- 宿主机调度
- 虚拟化开销
- 系统后台活动
- 进程唤醒与时间片抖动

结果表现为：

- `heft`、`t_level`、`zhao2020` 为正收益
- `cpf` 与 `wcet_first` 为负收益
- 且 `cpf` baseline 的 `CV` 超过 `10%`

因此，`zhang1` 的本轮数据不能简单理解为“算法绝对优劣”，更合理的说法是：

- 在当前虚拟机平台上，`zhang1` 的粗测稳定性不足
- 对于极短程序，虚拟机噪声足以影响收益判断

## 9. 本轮发现的关键问题

### 9.1 runtime_compare 结果目录存在覆盖风险

本轮排查中发现，当前工具在“极短任务 + 批量队列模式”下存在结果目录覆盖问题。

具体现象：

- 目录名采用秒级时间戳
- 多个任务如果在同一秒内完成
- 它们可能落到同一结果目录
- 导致某些 `summary.json` 被覆盖

实际后果：

- 理论任务数 15
- 首次汇总时只看到 13 个结果文件
- 必须人工核对并补跑

这说明当前工具在“快任务批量实验”场景下不够稳健。

### 9.2 工具输出中的 `stats.std_s` 不足以直接反映波动

在读取原始 `summary.json` 时，发现某些工具统计字段并不可靠地反映波动，因此本轮最终使用：

- `times_s`
- 手动重算均值
- 手动重算 `pstdev`
- 手动换算 `CV`

因此本轮表格中的 `CV` 是后处理得到的，更适合用于判断波动。

## 10. 结论

本轮在当前虚拟机平台上完成了真实的 `zhang1 / zhang2 / zhang3 × 5算法` 粗略测试，结论如下：

- `zhang2`：五算法均为正收益，且稳定性最好，是本轮最可信的一组
- `zhang3`：五算法均值也都为正，但 baseline 噪声明显，只能支持趋势判断
- `zhang1`：运行时间太短，虚拟机噪声影响明显，出现部分负收益，不适合作为强结论样例

同时，本轮确认了一个工具层面的真实问题：

- `runtime_compare` 的结果目录命名策略会在快任务上发生同秒覆盖

这个问题如果不修复，会直接损害批量实验的数据完整性。

## 11. 建议的下一步

如果后续要继续在虚拟机平台上做更可靠的实验，建议：

1. 对 `zhang1`、`zhang3` 提高 `repeats` 到 `30` 或 `50`
2. 保持 `cpu_set=[0,1]` 与串行队列模式
3. 修复 `runtime_compare` 的结果目录命名，至少加入毫秒或任务 ID
4. 汇总时始终用 `times_s` 重算波动，不直接信任已有统计字段
5. 最终论文级结论优先依赖更稳定的平台，虚拟机结果主要用于快速筛查与趋势验证
