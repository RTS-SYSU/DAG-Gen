## 7. 为什么 ws100 / r10 下 zhao2020 没有稳定优于 baseline

### 7.1 prio 实际是生效的

这次不是“优先级根本没设上”的问题。

已经检查：

- `/home/chove/Desktop/ScratchDAG/level1/prio_runtime.h`

并用：

- `/home/chove/Desktop/ScratchDAG/中间结果/zhang22/pipeline/instrument/level2/effective_line_merge/zhao2020/source_priority_trace_test.c`

做了真实追踪测试。

追踪结果表明：

- `main` 从 `policy=OTHER prio=0` 变为 `policy=FIFO prio=99`
- `worker_c0` 进入 `FIFO prio=91`
- `worker_c1` 进入 `FIFO prio=90`
- `worker_c2` 进入 `FIFO prio=88`

所以在当前机器上：

- `SCHED_FIFO` 是真的生效了

### 7.2 真正的问题是程序结构本身弱化了优先级优势

当前 `zhang22` 的关键执行结构是：

1. `main` 自己拿到最高优先级
2. `main` 连续执行 `C7 -> C8 -> C9`
3. `main` 再做 `join(thread_c0) + C10`
4. 然后 `C11`
5. 再做 `join(thread_c1) + C12`
6. 然后 `C13`
7. 再做 `join(thread_c2) + C14`

这意味着：

- makespan 的主导者其实是 `main` 自己
- worker 线程优先级变化，很多时候只是改变“谁先等到门打开”
- 而不是改变真正的关键门点释放顺序

所以即使 `prio` 真的生效，`zhao2020` 也未必能显著缩短总时间。

### 7.3 另一个问题：当前不是严格两核实验

当前 `source_instrumented.c` 里仍然是：

```c
CPU_SET(0, &cpu_set);
CPU_SET(1, &cpu_set);
CPU_SET(2, &cpu_set);
CPU_SET(3, &cpu_set);
```

见：

- `/home/chove/Desktop/ScratchDAG/中间结果/zhang22/pipeline/instrument/level2/effective_line_merge/zhao2020/source_instrumented.c`

而 runtime compare 的结果里也记录了：

- `affinity_rewritten_in_source = false`

也就是说：

- 虽然任务配置写了 `cpu_list: [0,1]`
- 但源码内 affinity 没有被重写成功
- 实际程序还是在 `0,1,2,3` 上跑

这会进一步稀释“2核下 FIFO 更差”的实验假设。


## 8. 当前阶段最重要的判断

本轮排查后的判断是：

- 当前 `zhang22` 的问题，不是简单继续调权重就能稳定解决
- 也不是 `prio` 完全没生效
- 核心矛盾是：程序结构 + affinity 条件 与“2核下关键路径优先显著优于 FIFO”的理想模型不够一致

换句话说：

- 你想构造的是“关键门点释放被错误调度明显拖慢”的程序
- 但当前 `zhang22` 更接近“main 自己串行主导，worker 辅助”

## 12. 本次续接会话新增排查：块边界动态降优先级是否会触发抢占

### 12.1 本次新增想回答的问题

这次又单独验证了一个机制问题：

- 当前方案虽然“分析调度单位”是代码块
- 但 Linux 真正调度的对象仍然是线程

因此需要确认：

- 如果线程 A 正在运行
- 它在进入下一个块时把自己的实时优先级降低
- 而此时线程 B 已 ready，且优先级高于 A

那么 B 会不会立即抢占 A。

这个问题很关键，因为它决定了“块边界动态设优先级”到底只是图上的标签，还是会在真实运行中形成有效的调度效果。


### 12.2 本次实验结论

结论是：

- 会抢占

本次最小化实验已经真实验证：

- A 先以 `FIFO 90` 运行
- A 在块边界把自己降到 `FIFO 70`
- 随后 A 唤醒 `FIFO 80` 的 B
- B 在 A 继续执行前立即获得 CPU
- A 暂停，直到 B 运行结束后才恢复

因此可以确认：

- 当前方案虽然不是“内核原生块调度”
- 但如果在块边界动态修改线程优先级，确实能形成接近块级优先级调度的效果

### 12.4 实验设计

本次设计成单核、两线程、信号量唤醒的最小模型：

1. 所有线程绑到 `CPU0`
2. `A` 启动后设置为 `SCHED_FIFO 90`
3. `B` 启动后设置为 `SCHED_FIFO 80`，先阻塞在 `sem_wait`
4. `main` 设置为 `SCHED_FIFO 60`
5. `A` 先执行第一段工作
6. `A` 在进入下一段前，把自己降到 `SCHED_FIFO 70`
7. `A` 调用 `sem_post()` 唤醒 B
8. 观察此时是谁先继续执行

这个设计的优点是：

- 抢占条件简单明确
- 单核下不会被“并行运行”掩盖
- 可以直接通过日志先后顺序判断是否发生抢占


### 12.5 关键运行结果

本次实际运行得到的核心日志如下：

```text
[   2004495 ns] thread=A     policy=FIFO   prio=70 phase=drop     after prio set, about to wake B
[   2007585 ns] thread=B     policy=FIFO   prio=80 phase=ready    woken and runnable
[   2008188 ns] thread=B     policy=FIFO   prio=80 phase=run      start block B1
[   4808587 ns] thread=B     policy=FIFO   prio=80 phase=run      end block B1
[   4868083 ns] thread=A     policy=FIFO   prio=70 phase=drop     returned from sem_post
[   4870114 ns] thread=A     policy=FIFO   prio=70 phase=block_A2 start
```

这里最关键的是：

- `B start block B1` 发生在 `A returned from sem_post` 之前

这说明：

- A 降级并唤醒 B 之后
- 调度器先让优先级更高的 B 运行
- A 没有继续往下执行，而是被抢占


### 12.6 这个结果对当前 zhang22 / zhao2020 的意义

这个实验验证的是“机制成立”，不是说明 `zhang22` 当前结构一定会显著提速。

更准确地说，它说明：

1. 当前运行时真正被 Linux 调度的是线程
2. 但如果在代码块边界调用 `pthread_setschedparam(SCHED_FIFO)` 改线程优先级
3. 那么线程在不同块上的调度地位确实会变化
4. 当某块把当前线程降到比其他 runnable 线程更低时，抢占会真实发生

因此，对当前方案最准确的描述是：

- “分析调度单位”是代码块
- “执行调度单位”是线程
- “块优先级”的运行时效果，是通过块边界动态改变线程优先级实现的


### 12.7 与前面 zhang22 结果的关系

此前对 `source_instrumented.c` 的检查表明：

- 当前插桩版本不是“每线程只设一次优先级”
- 而是每个块前都插入了 `l1_set_thread_prio_fifo(...)`

这意味着：

- `zhang22 / zhao2020` 当前的插桩运行时，已经具备“块边界触发抢占”的能力

但是还要区分两件事：

1. 机制是否成立
   - 本次实验已经确认成立
2. 在 `zhang22` 当前结构下，这种机制能否稳定转化为总时长收益
   - 目前还不能直接由该实验推出

原因仍然是：

- `zhang22` 当前总体结构偏向 `main` 串行主导
- 真实总时长是否改善，还取决于关键门点释放、同步关系和 affinity 条件


### 12.8 这次新增实验带来的判断更新

这次实验之后，可以更明确地排除一种怀疑：

- 问题不是“块优先级根本不会在运行时产生作用”

因为现在已经有直接证据表明：

- 块边界降优先级
- 会导致更高优先级线程在运行时抢占当前线程

所以如果后续 `zhang22 / zhao2020` 仍然不能稳定优于 baseline，更可能的原因是：

- 程序结构本身不够适合放大这种优先级优势

### 21.1 单位说明

- 秒：`s`
- 毫秒：`ms = 10^-3 s`
- 微秒：`us = 10^-6 s`

如果说“单次插桩开销”，指的是：

- 某个变体相对 baseline 的总时间增量
- 再除以该变体新增的插桩点数

即：

- `per_insert_overhead = (mean_time_variant - mean_time_baseline) / insert_count`


### 21.2 单独 C 程序的插桩开销量级

- `mean = 0.159194 s`

- `mean = 0.159845 s`
- 总增量 `delta = 0.000651 s = 0.651 ms = 651 us`
- 因为只插了 1 次，所以单次插桩开销约为：
- `0.000651 s / 次 = 0.651 ms / 次 = 651 us / 次`

单独 C 程序插 4 次：

- 这批结果均值反而比 baseline 略低
- 说明这个短程序噪声偏大
- 因此它更适合给出“量级参考”，不适合拿来精确估算每次插桩的固定成本

所以单独 C 程序这边，只能保守地说：

- 单次插桩开销大致在“亚毫秒到 1 毫秒内”的量级

- 平均到每次插桩：
- `0.000470 s / 次 = 0.470 ms / 次 = 470 us / 次`


### 21.4 当前最可用的结论

如果问“插桩一次的时间开销是多大”，当前最稳妥的回答是：

- 在这次 `probe` 实验里，单次优先级插桩开销大致是 `0.1 ms ~ 0.8 ms / 次`
- 更保守地按 `zhang22` 全量 14 点结果估计，可记为：
- `约 0.47 ms / 次 = 470 us / 次`

如果要给一个偏上界的说法：

- 在某些位置上，单次成本可以接近 `2.4 ms / 次`
- 但这个值明显受插桩位置、线程上下文和测量波动影响，不应直接当成固定常数

因此更推荐后续引用下面这句话：

- `当前测得的优先级插桩单次时间开销，大致为几百微秒/次，保守记为约 0.47 ms/次；在不同插桩位置上可能波动到 0.1~2.4 ms/次。`


### 21.5 这组结果说明什么

这组实验说明：

- 优先级插桩本身确实有成本
- 但在 `zhang22` 这个量级上，它不是几十毫秒/次那种压倒性大开销
- 更像是“几百微秒级”的附加成本

因此如果后续看到：

- 提升率很高
- 或退化很明显

那主因通常不太可能只是“多插了几个优先级调用”本身，更可能是：

- 真实优先级修改带来的调度变化
- 分块位置不同
- DAG 结构与权重设置把执行顺序带偏


### 21.6 这组结果的边界

需要明确：

- 这里测的是 `probe` 模式下的“插桩调用路径开销”
- 不是 `real` 模式下真正切换到目标优先级后的净效果

所以本节能回答的是：

- “插桩本身大约多花多少时间”

但还不能单独回答：

- “真实优先级生效后，最终程序到底净赚了还是净亏了多少”

如果后续要继续补完整，应再做一组：

- `real` 模式
- 与本节 `probe` 模式直接对比

这样才能把：

- 插桩固定成本

和

- 调度收益 / 调度副作用

彻底拆开。


### 21.7 单独微基准：自己写的单文件 C 程序里，单次插桩调用到底多长时间

上面的 standalone 整程序结果，受程序本身执行波动影响较大，只适合看量级。

为了更直接回答：

- “如果是我自己写的单独 C 程序，插桩一次到底要多久？”

又补了一组更合适的微基准。

微基准文件：

- `test实验/2026-03-17_优先级插桩开销实验/microbench_prio_call_overhead.c`

配套 `probe` 版运行时头：

- `test实验/2026-03-17_优先级插桩开销实验/prio_runtime_probe.h`

做法是：

1. baseline 版本循环 `200000` 次，只做一个极轻的累加
2. probe 版本循环 `200000` 次，每次先执行一次 `l1_set_thread_prio_fifo(99)`，再做同样的累加
3. 两个版本都用 `PROGRAM_TOTAL_NS` 统计总时间
4. 用总增量除以 `200000`，反推出“单次调用开销”

测得均值：

- baseline 平均总时间：`395761.6 ns`
- probe 平均总时间：`45831088.75 ns`
- 总增量：`45435327.15 ns`

折算到单次调用：

- `45435327.15 / 200000 = 227.18 ns / 次`
- 即：
- `约 0.227 us / 次`
- 也就是：
- `约 0.000227 ms / 次`

所以，如果问：

- “在自己写的一个单独 C 微基准程序里，插桩代码本身一次调用要多久？”

当前最直接的回答是：

- `约 227 ns / 次`
- `约 0.227 us / 次`
- `约 0.000227 ms / 次`


### 21.8 这里的“插桩开销”到底指什么

这里必须区分两种含义。

第一种，是“插进去这一行代码本身的执行成本”。

例如插入：

- `l1_set_thread_prio_fifo(99);`

那么这一行并不只是一个空语句，它包含了完整的函数调用路径。

在本次 `probe` 微基准里，这一行实际做了：

1. 普通 C 函数调用进入 `l1_set_thread_prio_fifo`
2. `memset(&sp, 0, sizeof(sp))`
3. `pthread_self()`
4. `pthread_getschedparam(...)`
5. `pthread_setschedparam(...)`
6. 返回调用点

所以这里测到的 `227 ns / 次`，不是“插入一行文本”的成本，而是：

- 这整条函数调用路径在 `probe` 模式下的平均执行时间

第二种，是“插桩后整程序总运行时间增加了多少”。

这时开销就不只是上面那个函数调用时间了，还会叠加：

1. 插桩位置本身对缓存/流水线的扰动
2. 多线程程序里线程切换时机的变化
3. 如果是真实优先级设置，还会改变调度行为
4. 同步点前后被插桩后，关键路径可能被放大或缩短

所以：

- 微基准的 `227 ns / 次`

回答的是：

- “插桩调用本身要多久”

而前面 `zhang22` 的：

- `约 0.47 ms / 次`

回答的是：

- “把这些插桩点放进真实程序后，平均摊到每个点上的整程序净增量是多少”

两者都叫“插桩开销”，但不是同一个层面的量。


### 21.9 现在应该怎样理解这两个数

当前可以这样理解：

1. 纯调用路径成本

- 约 `227 ns / 次`
- 这是函数调用 + `pthread_*sched*` 相关路径本身的成本

2. 真实程序中的摊销成本

- 在 `zhang22` 上大致是几百微秒/次
- 这是“调用本身 + 插桩位置扰动 + 多线程结构影响”合在一起后的结果

因此如果后续你问：

- “这条优先级插桩语句本身重不重？”

更合适引用的是：

- `约 227 ns / 次`

如果你问：

- “把这些插桩放到真实程序里后，平均每个点会让整程序多花多少时间？”

更合适引用的是：

- `约 0.47 ms / 次`

这两个数字并不矛盾，它们描述的是两个不同层次的开销。


## 22. 下一步计划：基于 `zhang22` 拆分结构开销与计算开销，重建块权重

当前下一步的核心目标，不再是继续讨论“插桩有没有效果”，而是：

- 重新估计 `zhang22` 各个分块的真实代价
- 让调度算法看到的块权重，更接近程序真实执行代价

为此，计划把每个块的时间拆成两部分：

- 固定结构开销
- 计算开销

即：

- `块总耗时 = 结构固定开销 + 计算开销`

这里的含义是：

1. 结构固定开销

- 线程创建与退出
- `pthread_mutex_lock/unlock`
- `sem_wait/post`
- `pthread_join`
- 调度和同步导致的时序扰动
- 插桩本身带来的附加扰动

2. 计算开销

- 块内 `busy_wait_seconds(Cx)` 真正贡献的时间
- 也就是希望作为“计算节点重量”的那部分时间


### 22.1 基本思路

目标不是直接继续手调权重，而是先建立一套更可信的块级代价模型。

计划分三步：

1. 先测“计算为 0”时每个块的基础耗时
2. 再单独标定 `busy_wait_seconds(Cx)` 的真实时间成本
3. 最后把两部分组合成新的块权重，再重新调度

这样可以回答三个关键问题：

1. 当前每个块的时间里，有多少是结构成本，有多少是 `busy` 成本
2. 哪些块其实不该被视为“重计算块”
3. 调度算法到底应该优化计算顺序，还是当前主要被结构同步限制


### 22.2 第一步：测 `busy = 0` 时每个块的基础耗时

第一步计划做一个“去计算负载”版本的 `zhang22`。

核心做法：

- 让所有 `busy_wait_seconds(Cx)` 不再执行实际计算
- 或者等价地让其工作量为 0
- 但保留程序原有：
  - 线程结构
  - 锁
  - 信号量
  - `join`
  - affinity
  - 分块边界
  - 插桩框架

这样测出来的结果代表：

- 在没有真实计算负载时，每个块最少仍然要付出的结构成本

这一组结果将作为各块的“基础底噪”。

这一步要特别注意：

- 不能把同步原语一起删掉
- 否则测到的就不是“结构开销”，而是另一套程序


### 22.3 第二步：单独标定 `busy_wait_seconds(Cx)` 的真实开销

第二步不放在完整 `zhang22` 里做，而是单独做 `busy` 标定实验。

目标是建立：

- `Cx` 或 `busy_wait_seconds(Cx)` 参数

到

- 真实运行时间

之间的映射关系。

建议测的内容：

1. 不同 `Cx` 下，单次 `busy_wait_seconds(Cx)` 的真实耗时
2. 同一 `Cx` 在虚拟机与开发板上的差异
3. `Cx -> 时间` 是否近似线性
4. 在当前 `WORK_SCALE` 下，单位 `Cx` 大致对应多少时间

最终产物应是一张映射表，例如：

- `C1 -> t1`
- `C2 -> t2`
- ...
- 或者更进一步给出一个拟合关系：
- `time_busy ≈ a * Cx + b`

这一步的目的，是把“计算节点重量”从主观设置，变成带测量依据的数值。


### 22.4 第三步：把两部分组合成新的块权重

有了前两步之后，就可以重新估计每个块的权重。

对任意块，新的权重思路为：

- `weight(block) ≈ base_cost(block) + compute_cost(block)`

其中：

1. `base_cost(block)`

- 来自 `busy = 0` 实验
- 代表该块在没有计算时的结构开销

2. `compute_cost(block)`

- 来自 `busy` 标定实验
- 代表块内各个 `busy_wait_seconds(Cx)` 累加后的真实计算时间

如果一个块几乎全由 `busy` 组成：

- 那么权重主要由 `compute_cost` 决定

如果一个块主要是同步和等待：

- 那么它的权重不应只看 `Cx`
- 而应更多体现 `base_cost`


### 22.5 为什么这一步对 `zhang22` 很关键

当前 `zhang22` 的核心问题，很可能不是“插桩完全无效”，而是：

1. 块权重没有准确反映真实执行代价
2. 某些块的主要耗时其实来自结构同步，而不是 `busy`
3. 调度算法拿到的是失真的权重，因此优先级分配不一定对应真实瓶颈

所以这一步的真正意义是：

- 把块权重从“人工大致设置”

变成

- “结构成本 + 真实计算成本”的组合

只有这样，后续调度结果才更有机会和真实收益对齐。


### 22.6 拟执行实验

计划至少补三类实验：

1. `zhang22_busy0`

- 把所有 `busy_wait_seconds(Cx)` 置空或置 0
- 测整程序与各块的基础耗时

2. `busy_unit_bench`

- 单独测 `busy_wait_seconds(Cx)` 在不同 `Cx` 下的真实耗时
- 形成 `Cx -> time` 映射

3. `zhang22_reweight`

- 用 `base_cost + compute_cost` 生成新的块权重
- 重新跑 `schedule -> instrument -> runtime_compare`
- 看收益是否比当前权重更稳定、更合理


### 22.7 预期结果

如果这套思路成立，预期应该能得到：

1. 一张更可信的块级权重表
2. 对每个块“结构成本/计算成本占比”的解释
3. 对 `zhang22` 为什么原来收益不稳定的更直接解释
4. 一组基于新权重的重新调度结果

如果重新加权后收益明显改善，可以支持：

- 当前主要问题确实在块权重建模，而不是插桩机制本身

如果重新加权后仍然改善有限，则更可能说明：

- `zhang22` 的程序结构本身就不利于当前调度策略发挥


### 22.8 一句话计划总结

下一步不再直接“猜哪个块该更大或更小”，而是：

- 先测掉 `zhang22` 每个块的结构底噪
- 再标定 `busy` 的真实计算时间
- 再把两者组合成新的块权重
- 最后用这个新权重重新调度并验证效果

### 24.4 这意味着什么

这说明对当前 `zhang22` 的 DAG 和 `zhao2020` 算法而言：

- 第一轮重加权虽然改变了数值权重
- 但没有改变算法最终的优先级排序

换句话说：

- 当前 `zhao2020` 在这个 DAG 上的优先级分配，对这轮权重变化并不敏感

因此本轮实验不能支持：

- “新权重已经成功改变了调度，并带来了更好性能”

它真正支持的是：

- “在当前 `zhang22` + 当前 `zhao2020` 下，第一轮重加权还不足以改变最终优先级决策”


### 24.5 为什么会出现这种情况

从算法角度看，这种现象是合理的。

因为 `zhao2020` 并不是简单按权重大小排序，而是：

1. 先基于拓扑结构确定 critical path / provider / consumer 集合
2. 再按 EA 规则分配优先级

如果新权重没有改变：

- 关键路径识别
- provider 分组关系
- 组内相对优先级顺序

那么即使具体 `avg_ns` 数值变了，最后优先级也可能完全不变。


### 24.6 当前可得出的结论

本轮实验的实际结论不是“重加权成功”，而是：

1. 当前 `busy_wait_seconds` 已经能被标定
2. 当前 `zhang22` 的计算时间占主要部分
3. 但把第一轮新权重直接喂给 `zhao2020` 后，优先级顺序没有变化

所以当前真正的瓶颈已经转成：

- 不是“能不能估计出更合理的块权重”

而是：

- “这些权重变化是否足以让当前调度算法作出不同决策”


### 24.7 下一步应如何推进

基于这轮结果，后续更值得做的是：

1. 检查 `zhao2020` 在 `zhang22` 上到底对什么敏感

- 是关键路径结构主导
- 还是某些 provider/consumer 集合主导

2. 设计更激进的权重对照组

- 不是只做“按标定值替换”
- 而是故意放大关键块/非关键块差异
- 看优先级是否会发生跳变

3. 同时尝试别的调度算法

- 如 `heft` / `t_level` / `cpf`
- 看这些算法是否比 `zhao2020` 对新权重更敏感


### 24.8 一句话结论

第一轮重加权实验已经说明：

- 新权重表本身是能构造出来的

但在当前 `zhang22` 上：

- `zhao2020` 的最终优先级顺序并没有因此发生变化

所以当前问题已经不是“权重有没有测出来”，而是：

- “当前调度算法在这个 DAG 上，是否真的会因为这些权重变化而改变决策”


## 25. 2026-03-17 实测：当前 `zhang22` 的块时间计算流程还不能直接用于验证

### 25.1 实验结果

这轮结果不是“块时间偏大或偏小”，而是更前置的问题：

- 当前版本并没有成功产出新的 `timing.json`

### 25.2 失败位置

核心编译错误发生在 timing 插桩后的源码中：

- `SEG_END("MU:worker_c2#001@98-100");`
- `SEG_BEGIN("MU:worker_c2#002@101-104");`

被插入到了当前源码结构下不合法的位置，导致编译器报错：

- `expected declaration specifiers or '...' before '(' token`

这说明：

- 当前块级 timing 的插桩方式

和

- 当前更新后的 `zhang22.c`

之间已经不兼容。


### 25.3 这意味着什么

这轮实验的结论非常明确：

1. 现在还不能直接回答“块时间算得对不对”

因为当前流程连新的块时间都算不出来。

2. 当前 `zhang22` 的块时间计算问题，已经先退化成了“timing instrumentation 是否还能正确插进去”

也就是说，当前首先要验证的不是：

- `avg_ns` 数值准不准

而是：

- 当前分块 timing 插桩方法，对这版源码是否仍然合法


### 25.4 当前阶段可得出的实际结论

所以到这一步，最准确的结论不是：

- “块时间方法是对的”

也不是：

- “块时间方法是错的”

而是：

- “当前块时间计算流程在更新后的 `zhang22` 上尚未稳定工作，因此其输出还不能被视为可信调度输入”


### 25.5 后续真正应该先做什么

基于这轮结果，下一步优先级应该调整为：

1. 先修当前 `timing stage` 的插桩合法性

- 让 `SEG_BEGIN / SEG_END` 能在新的 `zhang22.c` 上正确插入并编译通过

2. 再重新生成新的 `timing.json`

3. 之后才能进入真正的验证问题：

- 这些块时间和 `busy` 标定时间是否一致
- 哪些块混入了同步等待
- 哪些块时间可以当调度权重，哪些不行


### 25.6 一句话结论

当前这版 `zhang22` 上，块时间计算方法还没有进入“数值是否正确”的验证阶段；

它现在首先暴露出来的问题是：

- timing 插桩已经无法稳定产出合法的块时间结果
