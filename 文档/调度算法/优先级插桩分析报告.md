# 优先级插桩分析报告（CPC 模式）

## 1. 优先级插桩是如何做的
- 入口数据：`schedule.json.priorities` 给出每个节点（或线程前缀）的目标优先级；`mycalls_meta_internal.json` 给出每个调用点位置。
- 插桩点选择：遍历调用点，按线程前缀判定“首次出现”。仅在每个线程前缀第一次遇到的调用点前插入 `ta_set_priority(prio)`，其余调用点只做计时，不再设置优先级，避免频繁系统调用。
- 插桩代码形态：
  ```c
  // TA_BEGIN ...
  ta_set_priority(<prio>);    // 仅线程前缀首次出现时插入，使用 SCHED_FIFO
  uint64_t t0 = now_ns();
  <原始调用>
  uint64_t dur = now_ns() - t0;
  time_account("key", dur);
  time_trace("key", t0, dur);
  ```
- 运行时库扩展（`time_stat.c/h`）：
  - 增加 `ta_set_priority(int prio)` 调用 `pthread_setschedparam(SCHED_FIFO)`。
  - 记录诊断：调用次数、成功/EPERM/其他错误、调用耗时、最后的 policy/prio/errno，预期写出 `sched_diag.json`。
- 产物：基线 `time_result.json`/`metrics.json` 与 CPC 版 `time_result_prio.json`/`metrics_prio.json`；对比图生成到 `中间结果/<base>/调度算法/compare/<timestamp>/`。

## 2. 这种插桩对性能的影响
- 系统调用开销：每个线程前缀至少一次 `pthread_setschedparam`，即使失败（无权限）也会增加开销。
- 权限限制：未以 root/CAP_SYS_NICE 运行时，`setschedparam` 返回 EPERM，调度不变但多了系统调用开销。
- 时机滞后：优先级在首次计时点才设置，不是在线程入口，关键线程可能已运行一段时间才提升，收益受限。
- 调度副作用：SCHED_FIFO 高优先级线程可能占用 CPU，降低并行度，导致 wall-clock 或节点总和变大。
- 计时口径：`program_total_ns` 是节点耗时总和，额外系统调用直接放大此值；短基准更易被放大。

## 3. 数据与诊断位置
- 插桩工程与结果：`中间结果/<base>/时间分析_cpc/<project>/`（含插桩源码、`time_result_prio.json`、`metrics_prio.json`、可选 `sched_diag.json`）。
- 对比图：`中间结果/<base>/调度算法/compare/<timestamp>/metrics_compare_{program,threads}.png`。
- 基线对应目录：`中间结果/<base>/时间分析/<project>/`。

## 4. 结论（当前实现）
- 若无 root/CAP_SYS_NICE，优先级设置大概率失败，只增加系统调用开销，可能使总耗时上升。
- 即便权限满足，设置时机滞后、SCHED_FIFO 抢占导致并行度下降，都可能使短基准耗时不降反升。

## 5. 改进建议
1) **权限**：以 root 运行或授予 `CAP_SYS_NICE`，并在 `sched_diag.json` 中确认成功率/errno。
2) **时机**：将优先级设置移动到线程入口（threadtaskX/main 开头）且每线程只设一次，避免每线程前缀首次调用的系统调用分布不均。
3) **策略**：调节 prio 映射，防止长任务占用最高优先级造成吞没；可分级（关键高、次关键中、非关键低）。
4) **测量**：多次运行取平均，记录 wall-clock 与 `program_total_ns`，结合 `sched_diag.json` 分析 EPERM/开销。
5) **诊断完善**：确保 `sched_diag.json` 恒写出；若未生成，优先检查 ta_set_priority 是否执行（线程前缀是否命中）。***
