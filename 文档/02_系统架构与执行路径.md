# 系统架构与执行路径

## 1. 总体架构

当前仓库可以看成四条互相复用的执行路径：

```text
路径 A: legacy 生成链路
输入 .expand / .c
-> generation/legacy.py
-> DOT / circle.txt / debug JSON / 函数范围

路径 B: viewer 可视化链路
输入 DOT + circle.txt
-> visualization/viewer.py
-> 原始图 / 互斥锁图 / 信号量图 / Tarjan / 线程图

路径 C: 实验链路
输入 DAG 及元数据
-> level1/* / level2/* / time_analysis.py / scheduler.py
-> 分块 / 测时 / 调度 / 插桩

路径 D: pipeline 模块化链路
collect
-> blocks
-> timing
-> schedule
-> instrument
```

## 2. 路径 A: legacy 生成链路

入口：

- `cli.py` 中的 `generate` 子命令
- `generation/legacy.py:main()`

主流程：

```text
.expand
-> 解析函数/调用/符号引用
-> 构造 functions 字典
-> 识别条件前缀
-> 识别 pthread_create / pthread_join
-> 源码兜底补绑定
-> 导出 threads/full DOT
-> 导出 circle.txt
-> 导出 functions_full.json / functions_ranges.json / debug/*
```

这条路径产生了后续几乎所有阶段所需的基础输入。

## 3. 路径 B: viewer 可视化链路

入口：

- `cli.py` 中的 `describe` 子命令
- `visualization/viewer.py`

主流程：

```text
DOT + circle.txt
-> 读取图结构
-> 叠加 mutex / semaphore 信息
-> Tarjan 强连通分量分析
-> 线程分组着色
-> 生成 PNG 与文本信息
```

这条路径本身不生产新分析元数据，它更像“消费生成产物的解释器”。

## 4. 路径 C: 实验链路

这一层并不是一个单一入口，而是多个脚本拼出来的研究链路：

```text
legacy 生成产物
-> level1/segment_dag.py
-> level2/segment_dag_level2.py
-> level1/time_analysis_level1.py 或 time_analysis.py
-> scheduler.py / pipeline/algo/*
-> instrument_prio_level1.py 或 pipeline/instrument.py
```

这里有两种“测时对象”：

- 调用点级：`time_analysis.py`
- 分段级：`level1/time_analysis_level1.py`、`pipeline/timing.py`

也有两种“调度对象”：

- 函数节点 / 调用点 DAG：`scheduler.py`
- 分段 DAG：`pipeline/algo/*`

## 5. 路径 D: pipeline 模块化链路

`pipeline/cli.py` 把实验链路重新组织成显式 stage：

```text
collect
-> 读取 legacy 产物，生成 block_info.json

blocks
-> 调用 rule 插件生成 segments.json / dag_seg.json

timing
-> 对 segments 插桩、编译、运行、汇总 timing.json

schedule
-> 调用 algo 插件生成 schedule.json

instrument
-> 把优先级回写到源码，生成 instrumented source
```

其目录结构统一写到：

```text
中间结果/<base_name>/pipeline/
```

## 6. 当前架构中的复用关系

`pipeline` 并没有重写核心算法，而是复用了旧代码：

- `pipeline.rules.level1_stage1_rule` 直接调用 `level1.segment_dag.build_stage1_segments_and_dag`
- `pipeline.rules.level2_effective_line_rule` 直接调用 `level2.segment_dag_level2.build_level2_segments_and_dag`
- `pipeline.timing` 复用 `level1.time_analysis_level1.instrument_source`
- `pipeline.instrument` 复用 `level1.instrument_prio_level1.instrument_prio_program_timing_and_segment_priorities`

因此，理解 `pipeline` 的前提依然是先理解 `level1`、`level2` 和 `legacy` 的产物格式。

## 7. 架构上的关键依赖关系

当前项目有一个非常清晰的“上游依赖锚点”：

```text
generation/legacy.py
-> 生成 dag.dot
-> 生成 functions_full.json
-> 生成 functions_ranges.json
-> 生成 debug/mycalls_meta_internal.json
-> 生成 circle.txt
```

后续模块对这些文件的依赖如下：

- `level1/segment_dag.py`：依赖 `functions_full.json`、`functions_ranges.json`、`mycalls_meta_internal.json`
- `level2/segment_dag_level2.py`：在 Level-1 依赖基础上再依赖 `circle.txt` 与源码文件
- `pipeline/collector.py`：统一验证上述文件是否存在
- `visualization/viewer.py`：依赖 DOT 与 `circle.txt`
- `time_analysis.py`：依赖 `mycalls_meta_internal.json`
