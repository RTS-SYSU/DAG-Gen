# 论文版技术实现详解

本文档面向论文写作，不再以“如何上手项目”为主，而是以“系统如何实现、各阶段输入输出是什么、算法规则如何落地、实验结果为何可信”为主。内容基于当前仓库源码直接整理，可作为论文第三章至第五章的技术支撑材料或附录草稿。

## 1. 研究目标与系统问题定义

ScratchDAG 的目标不是仅从源码得到一张静态调用图，而是从多线程 C 程序中恢复一个可用于性能分析与调度实验的执行 DAG，并在该 DAG 上逐步完成：

```text
程序解析
-> 线程依赖恢复
-> 执行 DAG 生成
-> 分块
-> 时间测量
-> 带权 DAG 构建
-> 调度优先级生成
-> 优先级插桩与实验验证
```

从问题建模角度，可以把系统输入与输出定义为：

- 输入：
  - GCC RTL `.expand` 文件
  - 对应 C 源文件
  - 可选的已有 DOT/配置文件
- 中间表示：
  - 函数级调用关系
  - 线程创建/汇合关系
  - 调用点级元数据
  - 分段集合与段间依赖图
  - 段级时间权重
- 输出：
  - 执行 DAG、分段 DAG、带权 DAG
  - 调度优先级
  - 插桩源码与实验结果

在论文中，这个系统可以被描述为一个“面向多线程程序的静态-动态结合 DAG 构建与调度实验平台”。

## 2. 整体技术路线

从源码看，当前实现实际上由两个层次叠加而成：

1. `generation/legacy.py` 为核心的上游生成层。  
   它负责从 `.expand` 和源码中构建函数调用、线程关系和基础 DAG，并输出所有后续阶段都依赖的基础文件。

2. `level1`、`level2`、`time_analysis.py`、`scheduler.py`、`pipeline/*` 构成的分析实验层。  
   它们在上游基础上继续做分块、测时、调度和优先级插桩。

因此，论文中的系统架构图建议不要画成“单一步骤脚本调用”，而应画成“基础图生成层 + 分析实验层”的两层结构。

可以用下面的流程描述：

```text
RTL(.expand) + C source
-> 调用点与函数范围提取
-> 线程 create/join 绑定
-> 基础执行 DAG
-> 同步原语配置抽取
-> Level-1 分块
-> Level-2 分块
-> 调用点级 / 分段级测时
-> 带权 DAG
-> LPF / CPF / HEFT / Zhao2020 调度
-> 优先级插桩
-> 运行时对比实验
```

## 3. 基础程序表示与执行 DAG 生成

### 3.1 函数级表示

项目在解析阶段维护了一个以函数名为键的字典结构 `functions`。尽管仓库中存在 `Function` dataclass，但当前主流程最核心的数据仍是该字典。每个函数条目至少包含：

- `calls`：直接调用关系
- `refs`：直接符号引用
- `mycalls`：按源内顺序记录的调用节点序列
- `myinfo`：线程相关信息、尾节点信息、绑定信息
- `mycalls_meta` / `mycalls_meta_internal`：调用点源码定位信息

其中 `mycalls` 和 `mycalls_meta_internal` 最重要，因为它们把“图节点顺序”和“源码行号”连接了起来。后续的分块规则、测时插桩和同步原语定位都依赖这两者。

### 3.2 `.expand` 解析

解析器对 RTL `.expand` 文件执行正则扫描，识别：

- 函数头
- `(call ...)`
- `(symbol_ref ...)`

解析结果首先形成函数级调用关系，再叠加两类额外信息：

1. 条件控制前缀，如 `if/`、`while/`、`switch`。  
   这使得图中的节点不只是“函数名”，而是“带局部控制流上下文的调用点”。

2. 同步原语调用点。  
   例如 `pthread_create`、`pthread_join`、`pthread_mutex_lock`、`pthread_mutex_unlock`、`sem_post`、`sem_wait` 等。

### 3.3 线程边恢复

线程关系恢复是本系统区别于普通调用图工具的关键。系统采用两层策略：

- 第一层：利用解析时写入 `myinfo` 的线程句柄到任务函数映射。
- 第二层：当 RTL 中的 create/join 配对不稳定时，用 `generation/source_binder.py` 从对应 C 源函数中重新扫描 `pthread_create` / `pthread_join` 调用，并对线程句柄表达式进行归一化。

句柄归一化支持：

- `&thread`
- `threads[i]`
- `ctx->thr` / `ctx.thr`
- `*p`

这样做的核心目的是恢复两类语义边：

- `create` 段到线程入口函数首段
- 线程尾节点到对应 `join` 节点

在论文中，这部分可以表述为“静态调用关系与轻量源码绑定相结合的线程依赖恢复机制”。

### 3.4 基础输出文件

执行 DAG 生成完成后，系统会输出一组基础文件：

- `dag.dot`
- `functions_full.json`
- `functions_ranges.json`
- `debug/mycalls_meta_internal.json`
- `circle.txt`

这组文件构成后续分析阶段的统一输入接口。

## 4. 同步原语抽取与配置文件构建

### 4.1 `circle.txt` 的作用

`circle.txt` 是本项目里一个非常关键的桥接文件。它不只是可视化配置，而是同步语义在后续阶段中的显式载体。文件按两段组织：

- `互斥量`
- `信号量`

记录内容包括：

- 原始图节点名
- 原语类型
- 编号
- 可选源码行号
- 可选源文件名

### 4.2 互斥量与信号量的恢复逻辑

从实现角度，`generation/exporters.py` 会扫描 `mycalls` 序列，把同步调用点提取出来。其核心任务有两个：

1. 为每个同步对象生成稳定编号。
2. 将源码位置信息和图节点名称对应起来。

`circle.txt` 之后会被两个阶段直接消费：

- viewer：用于图展示、lock/unlock 和 post/wait 成对高亮。
- Level-2 与 collector：用于恢复 `sem_post -> sem_wait` 跨线程依赖。

在论文中可以将它描述为“静态同步事件的外部化表示”，作用类似于一个由前端分析阶段导出的同步标注文件。

## 5. Level-1 分块模型

### 5.1 目标

Level-1 的目标是从函数级执行图过渡到第一层段级图。它只关注线程生命周期相关的控制边界，因此只把下列两类语句当作切点：

- `pthread_create`
- `pthread_join`

### 5.2 段定义

对每个函数的可执行区间 `[start_line, end_line]`，把切点按源码行排序后，生成若干闭区间段：

- 普通计算段 `compute`
- 创建段 `create`
- 汇合段 `join`

代码中采用的段 ID 设计是：

- `THR:<func>#<idx>@<start>-<end>`
- `CRT:<func>#<idx>@L<line>`
- `JON:<func>#<idx>@L<line>`

这种设计有两个优点：

- 人工阅读结果时可以立即分辨段语义。
- 后续调度、插桩和实验日志可以直接以段 ID 为主键。

### 5.3 Level-1 构图规则

设函数 `f` 的段序列为 `s1, s2, ..., sk`，则首先建立函数内顺序边：

```text
s1 -> s2 -> ... -> sk
```

然后根据 `create/join` 的线程绑定信息增加跨函数边：

- `create` 段 -> 线程入口函数的首段
- 线程入口函数的尾段 -> `join` 段

因此 Level-1 图中的边类型可定义为：

- `intra`
- `create`
- `join`

### 5.4 Level-1 的意义

从论文结构上看，Level-1 可以被视为“把线程生命周期边界显式化”的第一层粗粒度分块。它解决的是：

- 线程创建和线程回收在段图中如何表示
- 多线程并发执行关系如何从函数调用级过渡到段级

## 6. Level-2 分块模型

### 6.1 目标

Level-2 的目标是在 Level-1 的基础上进一步刻画同步原语对执行段边界的影响，使段图更接近真实的并发调度单元。它引入三类额外信息：

- `sem_post` / `sem_wait`
- `pthread_mutex_lock` / `pthread_mutex_unlock`
- “有效代码行相邻”合并规则

### 6.2 函数有效区间的确定

Level-2 并不直接使用函数定义的完整闭区间，而是优先使用：

- `level1_start_line`
- `first_stmt_line`
- `last_stmt_line`
- `last_return_line`

其目标是尽量避免把：

- 函数头
- 尾部 `return`
- 纯闭括号 `}`

纳入分块区间，从而让每个段更贴近实际可执行语句。

### 6.3 基本切线规则

根据源码实现，Level-2 对同步事件采用如下切线规则：

- `create`：在该行之后切
- `sem_post`：在该行之后切
- `join`：在该行之前切
- `sem_wait`：在该行之前切
- `lock`：在该行之前切
- `unlock`：在该行之后切

如果用 `cut_after(line)` 表示“在 `line` 后形成边界”，则：

- `create`、`sem_post`、`unlock` 直接产生 `cut_after(line)`
- `join`、`sem_wait`、`lock` 产生 `cut_after(line-1)`

### 6.4 互斥临界区保护

系统会先在 `mycalls_meta_internal.json` 的有序节点序列中，用栈式匹配方法恢复每个函数内的 `lock/unlock` 区间。  
随后删除所有位于区间内部的切线：

```text
若 lock_line <= k < unlock_line，则删除 cut_after(k)
```

这样做保证了一个互斥临界区不会被错误地切成多个段。  
因此 Level-2 中新增了一类段标签：

- `mutex_cs`

它表示“含有互斥临界区语义的执行段”。

### 6.5 有效代码行相邻合并

这是当前 Level-2 的关键技术点。系统不是按物理相邻行判断，而是先构建“上一条有效代码行”和“下一条有效代码行”的映射。  
有效代码行的判定会跳过：

- 空白行
- `//` 注释
- `/* ... */` 注释

然后应用两个合并规则：

1. `create/sem_post` 合并  
   若其前一条有效代码为 `unlock`，则删除这个 `unlock` 对应的切线。

2. `join/sem_wait` 合并  
   若其后一条有效代码为 `lock`，则删除这个 `lock` 之前的切线。

这一规则的本质是：避免把“同步原语紧邻的锁释放/锁获取”切成过碎的段，从而提高段图对真实执行逻辑的拟合度。

### 6.6 线程边界规则

对 `main` 和所有线程入口函数，系统还根据 `internal_meta` 的首尾节点顺序增加边界规则：

- 如果首个调用不是 `lock/wait`，则记录入口切线。
- 如果最后调用不是 `unlock/post/create`，则记录出口切线。

当前实现不会因此生成空段，而是把这一规则体现在切线集合和元数据记录中。

### 6.7 信号量依赖恢复

Level-2 还会把 `sem_post -> sem_wait` 关系显式转成图边。恢复流程是：

1. 从 `circle.txt` 中读取成对的 `post/wait` 节点。
2. 通过 `internal_meta` 把节点映射回所属函数和源码行。
3. 再通过段覆盖关系把节点映射到段 ID。
4. 增加 `sem_dep` 类型的段间边。

最终 Level-2 段图中可能出现的边类型包括：

- `intra`
- `create`
- `join`
- `sem_dep`

## 7. 调用点级时间分析

### 7.1 目标

调用点级测时的目标是为原始 DAG 节点提供运行时间权重。该阶段由 `time_analysis.py` 实现，读取 `mycalls_meta_internal.json` 后，直接对对应调用点插入时间戳采样代码。

### 7.2 插桩流程

核心流程如下：

1. 复制源代码目录到实验目录。
2. 写入 `time_stat.c/h` 运行时库。
3. 读取并展开 `mycalls_meta_internal.json`。
4. 将调用点按源文件分组。
5. 在调用语句前后插入 `TA_BEGIN` / `TA_END` 标记。
6. 编译整个工程并运行。
7. 读取 `time_result.json`。
8. 生成 `metrics.json`、`thread_time_summary.json`、`dag_weighted.dot`。

### 7.3 关键工程保护

为保证插桩尽可能稳定，代码中加入了多项约束：

- 当前只支持 `.c` 文件。
- 对编译器内部函数如 `__stack_chk*`、`__builtin_*` 跳过插桩。
- 避免对已含 `TA_BEGIN` 标记的位置重复插桩。
- 对复杂表达式、控制语句、三目表达式等风险场景做保守跳过。

在论文中应明确说明：该调用点级插桩是“轻量静态文本插桩”，不是基于完整 AST 的语义保真插桩，因此其适用范围主要是普通 C 调用语句。

## 8. 分段级时间分析

### 8.1 目标

分段级测时服务于段 DAG 调度。其目标是获得每个 `seg_id` 的总执行时间、平均时间、最值等统计量。

### 8.2 插桩与运行流程

段级测时由 `level1/time_analysis_level1.py` 与 `pipeline/timing.py` 共同实现。其思路比调用点级更直接：

1. 读取 `segments.json`。
2. 从 `dag_seg.json` 中提取 active segments。
3. 复制源码目录。
4. 注入 `segtrace.h/c`、`prog_timer.h/c`、`wrap_main.c`。
5. 在段起止边界插入 `SEG_BEGIN/SEG_END`。
6. 编译运行。
7. 从 `trace/trace.*.csv` 中读取每次段执行时长。
8. 聚合得到 `timing.json`。

### 8.3 聚合指标

对每个段 `v`，系统统计：

- `total_ns(v)`
- `count(v)`
- `avg_ns(v)`
- `min_ns(v)`
- `max_ns(v)`

其中：

```text
avg_ns(v) = total_ns(v) / count(v)
```

这些值随后作为段级带权 DAG 的节点权重输入调度算法。

## 9. 带权 DAG 与调度算法

### 9.1 权重的来源

当前代码中，节点或段的权重不是静态估计值，而是由实际运行测得：

- 调用点级：来自 `time_result.json`
- 分段级：来自 `timing.json`

这使论文中的权重模型可以明确写成“实测执行时间驱动的带权 DAG”，而不是理论 WCET 分析。

### 9.2 最长路径与简化 CPC

`scheduler.py` 在函数/调用点级图上实现了：

- DAG 拓扑排序
- 最长路径求解
- 简化 CPC 优先级分配

其简化 CPC 过程大致是：

1. 先在最长路径上按唯一前驱关系切成 provider 段。
2. 为 provider 段依次赋予最高优先级。
3. 对剩余节点反复抽取子图内局部最长链，再依次赋予递减优先级。

这不是文献级完整 CPC 复现，而是一个面向当前带权 DAG 的工程化简化实现。论文中应明确说明该点，避免与严格文献算法混淆。

### 9.3 分段级 LPF

`pipeline/algo/lpf.py` 对段级 DAG 实现了 Longest Path First 思路：

1. 在 DAG 上拓扑排序。
2. 选择一个汇点，优先以 `main` 的最后一个段为 sink。
3. 逆拓扑计算每个节点到汇点的关键路径长度。
4. 按关键路径长度降序映射到优先级 99..1。

该算法强调“距离关键终点越重要的段优先级越高”。

### 9.4 分段级 CPF

`pipeline/algo/cpf.py` 的逻辑是：

1. 在当前未分配节点集合中抽取一条最长路径。
2. 将该路径作为一个 critical path layer。
3. 重复直到节点分配完毕。
4. 按抽取顺序对路径上的节点依次赋予递减优先级。

因此它不是单条关键路径，而是关键路径层的迭代分解。

### 9.5 分段级 HEFT

`pipeline/algo/heft.py` 实现的是“零通信成本版本的 HEFT”：

- 权重默认优先使用 `avg_ns`
- 处理器数量使用“函数个数”作为稳定代理
- 先计算 upward rank
- 再按 Earliest Finish Time 选择处理器

这一实现更适合做对比实验与顺序推导，而不是严格模拟真实异构多处理器平台。

### 9.6 Zhao2020 CPC + EA 规则

`pipeline/algo/zhao2020.py` 是当前实现里最接近论文级算法表达的一部分。其核心步骤为：

1. 在完整 DAG 上计算一条带虚拟源汇点的最长关键路径。
2. 把关键路径划分为多个 provider。
   - 若相邻关键节点满足“后者的前驱集合恰为前者”，则归为同一 provider。
3. 对每个 provider 计算消费者集合 `F` 与相关集合 `G`。
4. 按 EA 规则赋优先级：
   - 关键路径优先
   - provider 对应的消费者组随后分配
   - 若消费者子图内部再次出现多前驱关键路径，则递归进入嵌套 CPC

从工程实现看，它输出的仍是固定优先级字典：

```text
priorities: {seg_id -> [1, 99]}
```

因此论文中可以把这一部分写成“基于 Zhao2020 的段级 CPC-风格优先级分配实现”，并说明实现保留了 provider / consumer / nested CPC 的核心思想。

## 10. 优先级插桩机制

### 10.1 目标

优先级插桩的目的是把调度算法的离线优先级结果回写到程序源码中，从而通过操作系统实时调度机制验证优先级对运行结果的影响。

### 10.2 实现方式

当前实现存在两类插桩器：

- Level-1 专用插桩器 `instrument_prio_level1.py`
- pipeline 通用插桩器 `instrument_levelx.py`

它们的共同策略是：

- 注入 `prio_runtime.h`
- 在段起始行插入 `l1_set_thread_prio_fifo(prio);`

其中 Level-1 专用路径只对 `compute` 段插桩，通用路径则按段起始行回写。

### 10.3 操作系统约束

论文中必须明确写出的工程约束是：

- 优先级的实际生效依赖 `SCHED_FIFO` 或类似实时调度策略。
- 没有 `root` 权限或 `CAP_SYS_NICE` 时，优先级设置可能失败。
- 在这种情况下，优先级插桩可能只增加额外函数调用开销，而不改变线程调度顺序。

因此实验评价应区分：

- 算法输出的优先级是否合理
- 系统运行时是否成功应用该优先级

## 11. pipeline 模块化工作流

为了支持更清晰的实验流程，代码在 `pipeline/*` 中把分析链路重构为五个阶段：

### 11.1 collector

输入：

- `dag.dot`
- `functions_full.json`
- `functions_ranges.json`
- `mycalls_meta_internal.json`

## 13. 工程假设与有效性边界

这是论文里必须主动说明的部分。

### 13.1 当前明确假设

- 以 C 源文件为主要插桩对象，当前不完整支持 C++。
- `mycalls_meta_internal.json` 的键顺序可作为调用顺序使用。
- 同步原语识别基于原生 API 名称，不覆盖宏封装变体。
- Level-2 当前不处理“同一物理行命中多个同步原语”的冲突场景。

### 13.2 可能影响精度的因素

- RTL 到源码的绑定依赖正则与行号，复杂语法可能导致定位保守跳过。
- 调用点级插桩不是 AST 级精确重写，因此对复杂语句的覆盖有限。
- `HEFT` 当前使用零通信成本模型。
- `scheduler.py` 中的 CPC 是简化版工程实现，不等同于完整理论模型。

### 13.3 运行时实验限制

- 操作系统实时优先级权限会影响实验结果。
- 编译优化、平台差异、CPU 频率波动会影响测时统计。
- 段级权重来自实际运行均值或总时间，不是严格 WCET 上界。

这些都属于论文实验部分应纳入“威胁有效性”小节的内容。
