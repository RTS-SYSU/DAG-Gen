# 当前问题与重构建议

## 1. 包名与导入路径不一致

这是当前最显著的问题。

现状：

- 仓库目录名是 `ScratchDAG`
- `import ScratchDAG` 可以成功
- 但 `ui`、`pipeline`、`level2` 等模块大量硬编码 `mycallyplus_v1`

影响：

- GUI 和 pipeline 在当前目录名下无法直接运行
- README 命令与当前仓库名称不一致
- 新开发者容易误判“功能坏了还是命令写错了”

建议：

- 统一把内部绝对导入从 `mycallyplus_v1` 改为当前包名
- 或在重构前显式引入兼容层，但不要长期双名并存

## 2. `core/*` 与 `generation/*` 存在重复抽象

现状：

- `core/model.py` 与 `generation/model.py` 基本同构
- `core/parser.py` 与 `generation/parser.py` 也高度相似

影响：

- 源码阅读成本上升
- 开发者不容易判断“真实主线”在哪里
- 修 bug 时容易出现一处修了、另一处没修

建议：

- 明确一套为唯一数据模型实现
- 另一套只保留兼容导出，或者直接删除

## 3. legacy 是事实上的上游单点

现状：

- `level1`、`level2`、`pipeline.collector` 都依赖 legacy 产物
- 但项目文档容易让人误以为 `pipeline` 已经完全自给自足

影响：

- 新开发者若直接从 `pipeline` 入手，会忽略上游输入前提
- 出现缺文件时不容易快速定位

建议：

- 在代码和文档里明确写出 `pipeline` 的前置输入契约
- 长期看把上游 DAG 生成也纳入 stage 化流程

## 4. GUI 逻辑过重

`ui/gui.py` 不仅负责界面，还直接承担：

- 文件状态管理
- 子进程调度
- 分块流程启动
- 调度算法调用
- 运行时 Web UI 管理

影响：

- GUI 文件体量过大
- 测试与维护困难
- 命令行与 GUI 的流程一致性更难保证

建议：

- 把 GUI 只保留为状态展示与按钮分发层
- 把实际动作都下沉到可复用的 service 或 runner

## 5. Stage 命名已统一，但视图语义尚未真正分离

`RuleOutput` 已经区分：

- `struct_segments` / `struct_dag`
- `sched_segments` / `sched_dag`

但当前 Level-1 / Level-2 rule 仍然直接复用同一份内容。

建议：

- 若未来要支持“结构分块”和“调度分块”不同视图，这是正确方向。
- 若短期没有此需求，应避免接口过度超前，至少在文档里说明当前两者相同。

## 6. 文档和代码曾出现迁移痕迹

从 `git status` 和目录现状看，原 `文档/` 中的大量旧文档已经被移动到 `文档（old）/` 或处于删除状态。

这说明：

- 仓库正在经历一次文档整理
- 新文档必须以源码为准，不能简单恢复旧文件名或旧结论

本次新文档集的定位就是：

- 作为当前源码状态的“重新基线化说明”
- 为后续继续重构 `pipeline`、统一包名、整理 GUI 提供公共上下文
