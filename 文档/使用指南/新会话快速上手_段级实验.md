## 1. 现在的目标是什么（本阶段的研究闭环）

对一个 C 程序完成 Level‑1 段级链路，并用实验验证“prio 插桩是否带来整体耗时变化”：

1) 标准 DAG（函数调用级）  
2) Stage‑1 切段（只按 `pthread_create*` / `pthread_join*`）  
3) 段级 DAG（segment‑DAG）  
4) 段级测时（得到每段 `total_ns`）  
5) 段级 LPF（Longest Path First）计算每段优先级（prio 上界 80）  
6) 生成实验：baseline vs prio（只在副本里插桩）  
7) 反复采集实验数据（不同程序 / 不同 workscale / 多次运行）

## 2. 绝对规则（必须遵守）

1) 不能改写 `mycallyplus_v1/源文件/**`（插桩/编译/运行都在副本工程内完成）。  
2) `<base>` 规则（决定中间结果目录名）：  
   - 优先使用源 `.c` 文件名 stem；  
   - 若缺失源文件，则用 `.233r.expand` 去掉后缀后的前缀作为 `<base>`。  
3) Level‑1/Stage‑1 只切 create/join（条件节点/热点段暂不做，只在文档记录）。  
4) 段级 DAG 里 create/join 段允许存在，但后续 LPF/插桩忽略（权重 0）。  
5) 段级测时：只看 `start_line/end_line` 是否“安全可插”；多行语句暂不处理（遇到跳过并记录日志）。  

## 3. 核心文件与“它们是怎么来的”

### 3.1 Stage‑1 切段与段级 DAG

输入（都在 `mycallyplus_v1/中间结果/<base>/生成dag图/`）：
- `functions_full.json`：标准 DAG（含 mycalls/myinfo 等）
- `functions_ranges.json`：函数行号范围（level1_start_line / level1_end_line 等）
- `debug/mycalls_meta_internal.json`：内部元信息

输出（固定在 `mycallyplus_v1/中间结果/<base>/level1/stage1/`）：
- `segments_stage1.json`：段定义（seg_id、start/end 行号、type=compute/create/join）
- `dag_stage1_seg.json`：段级 DAG（nodes/edges）
- `dag_stage1_seg.dot`：便于渲染

对应实现：
- `mycallyplus_v1/level1/segment_dag.py`
- 入口汇总在 legacy：`mycallyplus_v1/generation/legacy.py` 的 `--level1-stage1`

### 3.2 段级测时（每段 total_ns）

做法：在“副本工程源码”里，对符合规则的 compute 段边界插入 `SEG_BEGIN/SEG_END`，运行后按 trace 汇总得到每段 total_ns。

输出（固定在 `mycallyplus_v1/中间结果/<base>/level1/timing/<project>/`）：
- `time_result_seg.json`：`seg_id -> total_ns`
- `time_analysis_level1.log`：插桩/跳过原因/运行信息
- `.../trace/trace.<tid>.csv`：每线程 trace

对应实现：
- `mycallyplus_v1/level1/time_analysis_level1.py`
- `mycallyplus_v1/level1/segtrace.{h,c}`

### 3.3 段级 LPF 优先级

输入：
- 段级 DAG：`level1/stage1/dag_stage1_seg.json`
- 段级耗时：`level1/timing/<project>/time_result_seg.json`

规则：
- create/join 段权重=0（忽略不分配）
- compute 段权重=该段 total_ns
- 汇点：main 的最后一个段
- prio 上界：80（从高到低分配）

输出：
- `mycallyplus_v1/中间结果/<base>/level1/schedule/lpf_segment/schedule_seg.json`

对应实现：
- `mycallyplus_v1/level1/lpf_segment.py`

### 3.4 实验生成：baseline vs prio

输出目录：
`mycallyplus_v1/中间结果/<base>/level1/experiments/lpf_segment_<timestamp>/<project>/`

目录结构：
- `baseline/project/...`：副本工程，**不插入优先级**
- `prio/project/...`：副本工程，**插入优先级**
  - prio 源文件命名会加后缀：`*_prio.c`（用于避免与 baseline 同名文件混淆）
- `run_experiments.sh`：实验脚本（用于整体耗时采集）
- `experiment/run_results_*.txt`：脚本输出（不覆盖旧文件）
- `compare.json`：历史遗留（wrap_main 方案测 total_ns，和脚本 wall‑time 可能不一致，后续计划弱化/移除）

对应实现：
- `mycallyplus_v1/level1/instrument_prio_level1.py`

## 4. 整体耗时到底怎么测（你现在用哪套口径）

当前存在两套“整体耗时”来源，**优先使用 run_experiments.sh 的结果**：

### 4.1 推荐口径：run_experiments.sh（wall‑time）

脚本做法（已升级）：
- 用 `date +%s%N` 在每次运行前后取时间戳
- `dur = end - start` 作为一次运行的 wall‑time（程序跑完一次的耗时）
- 支持 `WORK_SCALE` 和 `REPEATS`，并输出：
  - baseline/prio 的 mean/min/max
  - baseline/prio 每一次的耗时列表
  - 每一次运行的完整程序输出（便于排查 CPU 执行过程等）
- 输出文件不覆盖：`experiment/run_results_<ts>_ws<ws>_r<rep>[_N].txt`

这套测时符合“测量程序运行完的耗时”的需求。

### 4.2 可能不一致的口径：compare.json（wrap_main）

`compare.json` 的 `baseline_total_ns/prio_total_ns` 来自链接期 wrap_main + prog_timer 的“程序计时打印”，并不是脚本 wall‑time。

由于两者口径不同（以及程序内部打印、stdout/stderr、权限、调度等因素），可能出现“compare.json 与 run_experiments 输出不一致”。

当前策略：以 `run_experiments.sh` 输出为主；后续计划考虑“去除 compare.json total_ns 作为主要结果”。

## 5. run_experiments.sh 怎么用（你采集数据的主入口）

你会在某个实验目录看到它，例如：
`mycallyplus_v1/中间结果/cpu4_thread10_fifo_1/level1/experiments/lpf_segment_20260126_044809/cpu4_thread10_fifo_1/run_experiments.sh`

常用运行方式：
- `sudo bash run_experiments.sh`
- `sudo WORK_SCALE=10000 REPEATS=5 bash run_experiments.sh`

注意点：
- 脚本会自动用 `/tmp` 做临时编译/日志目录，减少权限问题
- 若报 `Missing baseline/prio ...`，说明你不在正确的实验目录，或者该目录生成不完整

## 6. GUI 测试工具是什么（工具链第二阶段）

文件：`mycallyplus_v1/tools/c_runtime_compare_gui.py`

它的定位是：不用手动进实验目录改脚本，直接在 UI 里选两份 C 文件（baseline/prio），后台跑并归档结果到 `mycallyplus_v1/experiment/`。

它的关键行为（已经实现）：
- 编译：`gcc -O2 -g -std=c11 -pthread -lm`（并支持从 UI 填 workscale）
- 后台队列：可以连续选择多组实验，自动排队运行
- 核心隔离：每个任务独占一组 CPU 核（核不够会提示）
- 线程亲和：会把源码中的 `CPU_SET(...)` 重写为“分配到的核集合”，保证所有线程限制在该核集合
- 输出归档：
  - `mycallyplus_v1/experiment/<baseline_stem>/compare_<...>/<timestamp>_ws<ws>_r<rep>_c<cores>/`
  - `summary.json`（统计结果）
  - `runs.csv`（每次耗时，便于画图）
  - `run.log`（编译/运行日志）

你接下来要做的是：把“基于 run.sh 的 workscale 传递”和“数据采集格式”进一步统一，让 UI 工具与 run_experiments 输出口径一致。

## 7. 常见问题（直接按这里排查）

### 7.1 WORK_SCALE 改了但耗时几乎不变

最常见原因：busy_wait 循环被 `-O2` 优化掉，导致不同 WORK_SCALE 下耗时差异不明显。

建议后续改法（任务之一）：busy_wait 内引入 `volatile` sink（例如累加到 volatile 变量或读写 volatile），确保编译器无法消除循环。

### 7.2 “Missing baseline/prio …”

原因：脚本找不到 `baseline/project/...` 和 `prio/project/...`。通常是“运行目录不对”或“实验目录没生成全”。

### 7.3 sudo/权限导致写入失败

历史上某些输出目录被 root 创建，普通用户写不了。当前脚本已把临时目录放在 `/tmp`，但最终输出仍落在实验目录下。

处理方式：
- 尽量用新 timestamp 的实验目录；或
- 明确用 sudo 跑（但会让输出变 root-owned）
