## 1. 本次会话解决了什么问题

### 1.1 统一总耗时测量口径：改为“程序内部计时”

结论：后续实验总耗时统一以“程序内部计时”为准，而不是脚本 wall‑time。

实现方式（不改业务源文件）：
- 链接期包裹 `main`：编译时加入 `-Wl,--wrap=main`
- 工程内附带 `wrap_main.c` + `prog_timer.{h,c}`：
  - `__wrap_main()` 中调用 `PROG_BEGIN()`，再进入 `__real_main()`
  - `atexit(PROG_END)` 输出 `PROGRAM_TOTAL_NS=<ns>` 到 stderr
- 运行脚本/工具从日志中解析最后一次 `PROGRAM_TOTAL_NS` 作为一次运行的耗时（秒=ns/1e9）

为什么这样做：
- `wall-time` 会受启动/收尾、stdout flush、系统负载、调度抖动影响
- “程序内部计时”可以把测量区间稳定定义为“main 入口到退出”

### 1.2 WORK_SCALE 看似不生效的根因与修复策略

现象：在某些程序上，`WORK_SCALE` 调大，运行时间几乎不变。

根因：`-O2` 优化会消除无副作用的 busy‑wait 循环（矩阵乘结果未被可见使用时，循环被优化掉）。

最终策略（按用户要求）：**不改源代码**，在编译命令层解决：
- 将实验编译从 `-O2` 改为 `-O0`（保留 `-g -std=c11 -pthread` 等），避免优化器消除 busy‑wait

注意：
- 历史上曾在某些实验副本中临时加过 `volatile sink` 防优化，但已按要求撤销（后续不再依赖源代码改动）。

## 2. 已实现的脚本与 GUI 能力（你可以直接用）

### 2.1 新版 run_experiments.sh 的“统一输出格式”

目标格式（txt 三段式）：
1) **配对表**（条目数=REPEATS）：每次 run 的 baseline/prio 耗时 + delta
2) **统计表**：baseline 1 张、prio 1 张，包含 times 列表、mean/min/max、rcs
3) **原始日志**：每次运行完整 stdout/stderr，baseline/prio 分开，便于排查

同时要求：
- 支持两个默认变量，并允许环境变量覆盖：
  - `WORK_SCALE_DEFAULT`（可用 `WORK_SCALE=...` 覆盖）
  - `REPEATS_DEFAULT`（可用 `REPEATS=...` 覆盖）
- 文件名记录参数：`run_results_<ts>_ws<ws>_r<repeats>.txt`

### 2.2 c_runtime_compare_gui.py（GUI）已对齐 run.sh 的核心逻辑（不再调用 run.sh）

文件：`mycallyplus_v1/tools/c_runtime_compare_gui.py`

关键升级点：
- 编译：
  - `GCC_FLAGS` 改为 `-O0 -g -std=c11 -pthread -Wl,--wrap=main -lm`
  - 编译不再只编译单个 `.c`，而是把所选 C 文件所在目录下所有 `*.c` 一并编译（以便自动包含 wrap_main/prog_timer 等辅助文件）
  - compile.log 记录实际 gcc 命令
- 计时：
  - 优先解析 `PROGRAM_TOTAL_NS=...`；兼容旧式 “Program total time: ...s”
  - 解析失败会标记并回退到 wall‑time（同时在日志中告警）
- 结果归档（每个任务 out_dir）：
  - `summary.json`（统计与元信息）
  - `runs.csv`（每次耗时表）
  - `run.log`（完整输出）
  - **新增**：`run_results_<ts>_ws<ws>_r<rep>.txt`（与 run.sh 同格式的三段式 txt）
- CPU 亲和与隔离：
  - 工具会给每个任务分配一组“互不重叠”的 CPU 核集合
  - 会在“拷贝后的源码副本”里尝试改写 `sched_setaffinity` 的 CPU_SET，让源码中写死的 0~3 映射到分配到的核集合
  - 若改写失败或未命中（未找到可改写模式），会在 txt 中输出 `[warn] ...`，summary.json 也记录 `affinity_patch_error`
- 新增“排队模式”（单并发）：
  - UI 增加勾选项：**单并发排队模式**
  - 勾选后：一次只跑 1 个任务；其他任务可继续加入队列，自动顺序执行
  - 不勾选：维持原有“多任务并行 + CPU 组分配”的模式

已修复的 bug：
- 排队模式上线后，曾出现 `TypeError: __init__() got an unexpected keyword argument 'serial_sem'`，原因是 `TaskRunner.__init__` 未同步参数；已修复（TaskRunner 接收 `serial_sem` 与 `queue_mode_fn`）。

## 3. 常见坑与排查

### 3.1 输出目录权限（root-owned）导致写失败

现象：脚本或 GUI 写 `experiment/` 目录时提示权限不够。

处理：
- GUI：会尝试用 sudo 修复权限（若启用 sudo 且 sudo -n 可用），否则抛出明确错误提示。
- 脚本：需要确保实验目录非 root-owned，或让脚本回退到可写路径（具体脚本版本可能不同）。

### 3.2 为什么不同 WORK_SCALE 下时间没变化

优先检查是否开启了 `-O2`；本会话最终策略是统一用 `-O0`。

## 7. RK3588S 上跑实验的注意事项（强烈建议先按此自检）

### 7.1 环境依赖

- 架构：ARM64（gcc/python3 通常没问题）
- 需要的软件包（按需安装）：
  - `build-essential`（gcc/make）
  - `python3`
  - 若要跑 GUI：`python3-tk`（无显示环境则建议用 run.sh/脚本跑）

### 7.2 性能与抖动来源（为什么 RK 会显著慢于 VM）

- RK3588S 为 big.LITTLE，单核性能与频率通常低于桌面 CPU；且可能存在温控降频
- 本会话为保证 WORK_SCALE 生效，编译改为 `-O0`，会进一步放大 ARM vs x86 的性能差距（属预期）
- 若同时跑桌面环境/图形渲染，可能导致更多系统负载与温控；建议用纯命令行跑批量实验

### 7.3 建议的运行策略

- **优先使用排队模式**：一次只跑一个任务（最稳、最可复现）
- “每任务核数”尽量选择同类核集合（例如只用大核），减少 big.LITTLE 混用带来的抖动
- 先用小 `WORK_SCALE` 试跑，确认单次耗时，再扩大规模

### 7.4 防止“息屏/睡眠”影响

注意：**屏幕息屏通常不影响计算**，但“系统睡眠/挂起”会直接停掉实验。

- 在板子系统里关闭 suspend/sleep（不同发行版方式不同）
- 若用 GUI/远程桌面，确保远程断开不会触发 suspend
