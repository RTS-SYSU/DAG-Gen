# 程序模块化设计（pipeline）

目标：把除“分块规则”和“调度算法”以外的步骤全部模块化、固定化；新增规则/算法时只需要新增一个模块并在 GUI 增加一个按钮即可集成。

扩展点（必须独立）：
- 分块规则：`level1 / level2 / level3` 互相独立，且每个 level 内允许多个规则实现（用 `rule_name` 区分）。
- 调度算法：互相独立（用 `algo_name` 区分）。

非目标：
- 本文档不定义“实验工具”的实现细节（实验由外部工具完成）。
- 本文档不强制你必须保存每次运行的历史版本（默认覆盖写入最新产物）。

---

## 0. 总体流水线（固定骨架）

前置：用户已点击“生成 dag 图”，产生标准输入（`dag.dot`、`functions_full.json`、`functions_ranges.json`、`mycalls_meta_internal.json`、可选 `circle.txt`）。

pipeline 依次提供按钮（每一步都只读上一阶段输出，不重复解析散落文件）：
1. 生成分块信息（collector）
2. 分块（level1）
3. 分块（level2）
4. 分块（level3）
5. 分块测时（timing）
6. 调度算法（schedule）
7. 优先级插装（instrument）
8. 实验（外部工具）

说明：
- 分块阶段强制产出两种视图：`struct`（结构验证）与 `sched`（用于调度/插装）。
- 所有路径在 `中间结果/<base>/pipeline/` 下固定组织。
- 不使用 `run_id`，默认每一步覆盖写入“最新结果”。

---

## 1. 目录结构（固定）

根目录：`中间结果/<base>/pipeline/`

```
pipeline/
  block_info.json
  block_info_meta.json
  derived/
    sem_pairs.json            # 可选：由 circle.txt 提取的 post->wait 配对
    mutex_intervals.json      # 可选：由 meta 提取的 lock/unlock 区间

  blocks/
    level1/<rule_name>/
      struct/segments.json
      struct/dag_seg.json
      struct/dag_seg.dot
      struct/dag_seg.png
      sched/segments.json
      sched/dag_seg.json
      sched/dag_seg.dot
      sched/dag_seg.png
      rule_meta.json

    level2/<rule_name>/...    # 同 level1 结构
    level3/<rule_name>/...    # 同 level1 结构

  timing/
    levelX/<rule_name>/<view>/timing.json
    levelX/<rule_name>/<view>/timing_meta.json
    levelX/<rule_name>/<view>/logs/...

  schedule/
    levelX/<rule_name>/<view>/<algo_name>/schedule.json
    levelX/<rule_name>/<view>/<algo_name>/schedule_meta.json
    levelX/<rule_name>/<view>/<algo_name>/dag_prio.dot
    levelX/<rule_name>/<view>/<algo_name>/dag_prio.png

  instrument/
    levelX/<rule_name>/<view>/<algo_name>/
      source_original.c
      source_instrumented.c
      instrument_meta.json
```

约定：
- `levelX` 取值：`level1 | level2 | level3`
- `view` 取值固定：`struct | sched`
- `rule_name`：规则实现名（例如 `stage1_create_join`、`effective_line_merge`、`level3_xxx`）
- `algo_name`：算法名（例如 `lpf`、`helf`、`wcet`）

覆盖策略（默认）：
- 同一路径重复运行直接覆盖旧文件。
- `*_meta.json` 必须记录生成时间、输入文件路径与关键参数，保证可追溯。

## 2. 按钮 1：生成分块信息（collector）

### 输入（标准输入，不再散读）
来自 `中间结果/<base>/生成dag图/`：
- `dag.dot`
- `functions_full.json`
- `functions_ranges.json`
- `debug/mycalls_meta_internal.json`

来自 `中间结果/<base>/配置文件/`（可选）：
- `circle.txt`

以及源文件路径（GUI 状态区的 “源文件”）。

### 输出
写入 `中间结果/<base>/pipeline/`：
- `block_info.json`
- `block_info_meta.json`
- `derived/` 目录（可选派生索引）

### 功能边界
- 只做“收集路径 + 校验存在性 + 生成派生索引（可选）”。
- 不做分块、不做测时、不做调度、不做插装。

### `block_info.json`（最小字段契约）
```json
{
  "schema_version": "1.0",
  "base_name": "<base>",
  "source_file": "<path/to/source.c>",
  "inputs": {
    "dag_dot": ".../中间结果/<base>/生成dag图/dag.dot",
    "functions_full": ".../functions_full.json",
    "functions_ranges": ".../functions_ranges.json",
    "mycalls_meta_internal": ".../debug/mycalls_meta_internal.json",
    "circle_txt": ".../配置文件/circle.txt"
  },
  "capabilities": {                        
    "has_circle_txt": true
  }
}
```

## 3. 按钮 2/3/4：分块（level1/level2/level3）

### 输入
- `pipeline/block_info.json`
- `pipeline/derived/*`（若该规则需要信号量/互斥锁信息）

### 输出（每个规则独立目录）
- `pipeline/blocks/<levelX>/<rule_name>/struct/*`
- `pipeline/blocks/<levelX>/<rule_name>/sched/*`
- `pipeline/blocks/<levelX>/<rule_name>/rule_meta.json`

### 统一段/图契约（两视图都必须满足）
#### `segments.json`
```json
{
  "schema_version": "1.0",
  "base_name": "<base>",
  "level": "level2",
  "rule_name": "<rule_name>",
  "view": "sched",
  "segments": [
    {"seg_id": "...", "function": "...", "kind": "...", "start_line": 1, "end_line": 2}
  ]
}
```

#### `dag_seg.json`
```json
{
  "schema_version": "1.0",
  "base_name": "<base>",
  "nodes": ["seg_id1", "seg_id2"],
  "edges": [
    {"src": "seg_id1", "dst": "seg_id2", "kind": "intra"}
  ]
}
```

约束：
- `seg_id` 必须唯一且稳定（后续 timing/schedule/instrument 都以 `seg_id` 为 key）。
- `dag_seg.json` 中所有边端点必须存在于 `nodes`。

---

## 4. 按钮 5：分块测时（timing）

### 输入
- `pipeline/block_info.json`
- `pipeline/blocks/<levelX>/<rule_name>/<view>/segments.json`

### 输出
- `pipeline/timing/<levelX>/<rule_name>/<view>/timing.json`
- `pipeline/timing/<levelX>/<rule_name>/<view>/timing_meta.json`
- `pipeline/timing/<levelX>/<rule_name>/<view>/logs/*`

### `timing.json`（最小字段）
```json
{
  "schema_version": "1.0",
  "base_name": "<base>",
  "level": "level2",
  "rule_name": "<rule_name>",
  "view": "sched",
  "weights": {
    "seg_id": {"total_ns": 123, "count": 7}
  }
}
```

计时口径：
- 主口径固定为程序内部计时（`PROGRAM_TOTAL_NS`）。
- `timing_meta.json` 必须记录是否成功解析 `PROGRAM_TOTAL_NS`、gcc 参数等。

---

## 5. 按钮 6：调度算法（schedule）

### 输入
- `pipeline/blocks/<levelX>/<rule_name>/<view>/dag_seg.json`
- `pipeline/timing/<levelX>/<rule_name>/<view>/timing.json`

### 输出
- `pipeline/schedule/<levelX>/<rule_name>/<view>/<algo_name>/schedule.json`
- `pipeline/schedule/<levelX>/<rule_name>/<view>/<algo_name>/schedule_meta.json`
- （可选）`dag_prio.dot/png`（把优先级标回段图便于检查）

### `schedule.json`（最小字段）
```json
{
  "schema_version": "1.0",
  "base_name": "<base>",
  "algo_name": "<algo_name>",
  "priorities": {
    "seg_id": 80
  }
}
```

---

## 6. 按钮 7：优先级插装（instrument）

目标：产出两份可以运行的 C 代码文件（一份原始，一份插装后），用于后续实验工具直接对比。

### 输入
- `pipeline/block_info.json`（取源文件路径）
- `pipeline/blocks/<levelX>/<rule_name>/<view>/segments.json`（用于定位段边界/插装点）
- `pipeline/schedule/<levelX>/<rule_name>/<view>/<algo_name>/schedule.json`

### 输出
- `pipeline/instrument/<levelX>/<rule_name>/<view>/<algo_name>/source_original.c`
- `pipeline/instrument/<levelX>/<rule_name>/<view>/<algo_name>/source_instrumented.c`
- `pipeline/instrument/<levelX>/<rule_name>/<view>/<algo_name>/instrument_meta.json`

约束：
- `source_original.c` 为源文件的直接拷贝（或等价展开）。
- `source_instrumented.c` 只在“允许的位置”插入优先级设置调用（插装点需可解释并落日志）。
- `instrument_meta.json` 必须记录插装点数量、跳过原因（如定位失败/控制语句行/多行语句等）。

## 7. 需要你后续补充/确认的两件小事（写进文档即可）

### 7.1 `rule_name` / `algo_name` 命名规范（强制）
为了保证跨平台与脚本处理稳定，建议强制以下规范（否则按钮展示可用中文，但落盘目录必须稳定）：
- `rule_name`、`algo_name` 仅允许：英文小写字母、数字、下划线（正则：`[a-z0-9_]+`）。
- GUI 展示名称可以是中文，但落盘使用规范化后的 `rule_name` / `algo_name`。

### 7.2 多文件工程策略（当前默认 + 未来扩展）
当前默认（优先保证落地速度）：
- pipeline 以“单个 `.c` 文件”为分析与插装对象。
- `instrument/` 仅输出两份 `.c` 文件：`source_original.c` 与 `source_instrumented.c`。

未来扩展（当你需要支持多文件工程时再做）：
- `instrument/` 除两份主 `.c` 外，额外输出一个可编译目录：
  - `pipeline/instrument/<...>/project_original/`
  - `pipeline/instrument/<...>/project_instrumented/`
- 两个目录都包含完整工程源码；仅在插装版本中改写目标源文件，其余文件原样拷贝。
  - 这样既满足“保留两份单文件对比”的习惯，也满足“工程可直接编译运行”的实验需求。
