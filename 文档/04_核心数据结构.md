# 核心数据结构

## 1. 调用图数据模型

定义位置：

- `core/model.py`
- `generation/model.py`

### 1.1 `Function`

| 字段 | 含义 |
| --- | --- |
| `name` | 函数名 |
| `files` | 来源 RTL 文件集合 |
| `calls` | 直接调用的函数集合 |
| `refs` | 直接引用的符号集合 |
| `call_sequence` | 调用在函数体中的出现顺序 |
| `callee_calls` | 反向调用索引 |
| `callee_refs` | 反向符号引用索引 |
| `meta` | 预留扩展字段 |

生命周期：

- 由解析器在扫描 RTL 时创建。
- 由 builder 填充反向索引。
- 被导出器、渲染器、线程补边逻辑消费。

### 1.2 `ThreadInfo`

| 字段 | 含义 |
| --- | --- |
| `thread_id` | 线程句柄标识 |
| `task_function` | 线程入口函数 |
| `create_site` | 创建位置 |
| `join_site` | 汇合位置 |
| `tail_node` | 线程任务的尾节点 |

### 1.3 `CallGraph`

| 字段 | 含义 |
| --- | --- |
| `functions` | 全部函数节点 |
| `thread_infos` | 线程信息表 |
| `thread_edges` | 线程补边缓存 |
| `thread_create_queue` | 线程创建兜底队列 |

## 2. legacy 函数字典

虽然有 dataclass，实际主流程最常用的数据结构仍然是 `generation/legacy.py` 的 `functions: dict`。

典型条目包含：

- `files`
- `calls`
- `refs`
- `callee_calls`
- `callee_refs`
- `mycalls`
- `myinfo`
- `mycalls_meta`
- `call_src`
- `call_src_full`

其中最关键的是：

- `mycalls`：保留顺序的调用节点序列。
- `myinfo`：保存线程绑定、tail、join 关联等信息。
- `mycalls_meta` / `mycalls_meta_internal`：保存源码 `(file, line, col)` 等定位信息。

## 3. 函数范围数据

定义位置：

- `core/func_ranges.py`

关键结构：`FuncRange`

| 字段 | 含义 |
| --- | --- |
| `name` | 原始函数名 |
| `base_name` | 归一化函数名 |
| `start_line` | 函数定义起始行 |
| `body_start_line` | 函数体 `{` 所在行 |
| `first_stmt_line` | 第一条有效语句行 |
| `end_line` | 函数闭括号所在行 |
| `last_return_line` | 最后一个 `return` 所在行 |
| `last_stmt_line` | 最后一条有效语句所在行 |

这个结构直接服务于 Level-1、Level-2 分块边界计算。

## 4. 调用点数据

定义位置：

- `time_analysis.py`

### 4.1 `CallSite`

| 字段 | 含义 |
| --- | --- |
| `file` | 所在源文件 |
| `line` | 行号 |
| `col` | 列号，可选 |
| `func` | 被推断出的函数名 |
| `raw_key` | 原始内部节点键 |

### 4.2 `InstrumentResult`

描述一次调用点级测时运行的产物位置：

- 插桩目录
- 可执行文件
- `time_result.json`
- `metrics.json`
- 日志路径
- 已插桩文件列表
- warning / skipped 列表

## 5. 分块数据

### 5.1 Level-1

定义位置：

- `level1/segment_dag.py`

`CutPoint`

| 字段 | 含义 |
| --- | --- |
| `function` | 所属函数 |
| `kind` | `create` / `join` |
| `node` | 原始 DAG 节点名 |
| `line` | 切点行号 |
| `entry_fn` | 关联线程入口函数 |
| `tid_var` | 线程句柄变量 |

`Segment`

| 字段 | 含义 |
| --- | --- |
| `seg_id` | 段 ID |
| `function` | 所属函数 |
| `kind` | `compute` / `create` / `join` |
| `start_line` | 起始行 |
| `end_line` | 结束行 |
| `cut_node` | 触发该段的切点节点，可选 |

### 5.2 Level-2

定义位置：

- `level2/segment_dag_level2.py`

`Segment` 字段与 Level-1 接近，但 `kind` 扩展为：

- `compute`
- `mutex_cs`

在 pipeline 的标准化结果中，未来还允许出现：

- `create`
- `join`
- `sem_wait`
- `sem_post`

## 6. pipeline 插件数据

定义位置：

- `pipeline/rules/base.py`

`RuleOutput`

| 字段 | 含义 |
| --- | --- |
| `struct_segments` | 结构视图 segments |
| `struct_dag` | 结构视图 DAG |
| `sched_segments` | 调度视图 segments |
| `sched_dag` | 调度视图 DAG |
| `meta` | 规则元数据 |

虽然当前 `struct_*` 和 `sched_*` 基本相同，但接口已经为未来的“双视图”预留了空间。

## 7. 运行结果 JSON 结构

### 7.1 `segments.json`

核心字段：

- `schema_version`
- `base_name`
- `level`
- `rule_name`
- `view`
- `segments[]`

### 7.2 `dag_seg.json`

核心字段：

- `schema_version`
- `base_name`
- `nodes[]`
- `edges[]`

每条边通常含：

- `src`
- `dst`
- `kind`

### 7.3 `timing.json`

核心字段：

- `weights[seg_id] = {total_ns, count, avg_ns, min_ns, max_ns}`

### 7.4 `schedule.json`

核心字段：

- `algo_name`
- `priorities`
- 可选 `meta`
- 对 HEFT 还会附加 `order`、`assignments`
