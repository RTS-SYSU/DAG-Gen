我明白你的意思，而且你的直觉是**对的、而且是可行的**，但需要**把“编号”的语义想清楚**，否则很容易把 DAG 建成“长链函数调用图”，而不是你真正想要的**并发/调度分析 DAG**。

我分层次把这件事讲清楚。

---

## 一、你现在遇到的问题本质是什么

你现在用 ScratchDAG 做的是：

* **函数级 DAG 建模**
* 但工程代码里存在大量 **被反复调用的工具函数**，例如

  * `since_prog_start`
  * `elapsed_seconds`
  * `busy_wait_seconds`

这些函数在：

* 循环里
* 多个线程里
* 多次出现

结果就是你现在看到的这张图：

> 一个巨大、纵向拉得很长、重复节点极多的“调用轨迹图”

这张图 **在程序语义上是正确的**，但：

* ❌ **对调度分析没有价值**
* ❌ **关键路径被重复噪声淹没**
* ❌ **无法回答“哪个并发结构决定了端到端时间”**

---

## 二、你提出的“给反复出现的函数编号”——是否可行？

### 结论先给：

> **可行，但前提是：编号的不是“函数”，而是“函数的一次执行实例”**

这是一个非常关键的区分。

---

## 三、两种“编号”方式的本质区别（非常重要）

### ❌ 错误但直观的想法（不要这样做）

> 给 `busy_wait_seconds` 这个函数统一编号一个节点

这会导致：

* 多次调用被错误合并
* 时间被叠加或覆盖
* 依赖关系丢失

**这等价于把程序“压扁”成静态调用图（call graph）**
👉 不再是 DAG，而是 CFG / CG

---

### ✅ 正确、学术界通用的做法

> **对“同一个函数的不同执行实例”进行编号**

也就是说：

* `busy_wait_seconds@T3#1`
* `busy_wait_seconds@T3#2`
* `busy_wait_seconds@T7#1`

这里至少包含三个维度中的一部分：

1. **线程上下文**
2. **调用顺序（instance id）**
3. **所处并发阶段**

👉 这在并行分析里通常叫：

* *dynamic instance*
* *execution instance*
* *node instance*

---

## 四、这样做之后，你得到的 DAG 是什么样的？

你最终得到的不是：

> “函数 DAG”

而是一个更重要的东西：

> **并发执行 DAG（Execution DAG）**

### 节点含义变成：

> 一次具体的、可测量的执行片段

例如：

```
Node A: T_SRC_A.main_compute_phase
Node B: T_A1.worker_loop#1
Node C: T_A2.worker_loop#1
Node D: T_M1.merge_phase
```

而不是：

```
busy_wait_seconds
elapsed_seconds
since_prog_start
```

这一步，**是你这个工具从“代码分析”走向“调度分析”的分水岭**。

---

## 五、你现在的想法可以怎么落地（一步一步来）

### Step 1：先保留函数级 DAG（你说得对）

你说：

> 我可以先生成完整的函数级 dag，再对节点进行合并

这是**非常合理的工程路径**，而且非常适合写论文。

原因是：

* ✔ 保证语义完整
* ✔ 可回溯
* ✔ 可解释
* ✔ 可复现

---

### Step 2：引入“实例化规则”

对反复出现的函数，引入一个规则：

> **同一线程 + 同一循环层级 + 连续调用 = 同一“阶段实例”**

例如：

```c
for (...) {
    busy_wait_seconds();
}
```

你可以在 ScratchDAG 里定义：

* 不为每一次循环生成一个节点
* 而是生成一个：

```
busy_wait_seconds@T3#loop1
```

并把**总时间累加到这个节点**

👉 这是**工程可行、分析合理、论文可解释**的做法

---

### Step 3：节点合并不是“拍脑袋”，而是基于语义

你合并节点的依据不是：

* “名字一样”

而是：

* 同一线程
* 同一控制结构
* 同一并发语义阶段
* 不影响调度依赖判断

你可以在论文中明确说：

> We merge repetitive utility-function invocations within the same execution phase into a single DAG node to avoid over-fragmentation.

这句话**审稿人是完全能接受的**。

---

## 六、从调度分析角度看，你真正该建的 DAG 是什么？

我直接告诉你一个**非常关键的判断**：

> **调度分析关心的不是“函数”，而是“可被调度的执行单元”**

在你这个程序里，可被调度的执行单元其实是：

* 线程
* 或线程内的大计算阶段
* 或并发阶段之间的依赖

因此你最终应该收敛到：

### 一个“线程/阶段级 DAG”

例如：

```
SRC_A  ─┐
        ├─>  A1/A2/A3  ─┐
SRC_B  ─┘                ├─>  MERGE
        └─>  B1/B2/B3  ─┘
```

而不是：

```
since_prog_start -> busy_wait_seconds -> elapsed_seconds -> ...
```

---

## 七、总结一句非常重要的话（你可以直接写进论文）

> 函数级 DAG 是中间表示，不是最终分析对象。
> 真正用于调度分析的，是在函数级 DAG 之上，通过实例化与语义合并构建的执行级 DAG。
