# 代码段切割与时间戳插桩方法（方案 1）

> 目标：确定“时间戳插在哪些位置”与“代码段怎么切”，保证测得的耗时可解释、可复现、可用于调度（LPF/优先级插桩）。

---

## 1. 问题拆解

你这个问题可以拆成两件事：
1. **时间戳（timestamp）插在哪些位置**，才能保证测到的是“可解释、可复现、可调度”的耗时；
2. **代码段（Segment）怎么切**，才能保证段的语义稳定，且不会被循环/工具函数/条件分支搞乱。

下面给出一套**规则化、可写进论文、实现成本低**的方案：先给通用规则，再给 create/join 的示例切分。

---

## 2. 时间戳边界识别：用「并发语义切点」定义段边界

### 2.1 核心原则

每个 Segment 的边界必须落在**并发语义事件**上，而不是落在“函数边界/任意行号”上。

### 2.2 并发语义事件（Cut Points）清单

必须识别并作为段边界的调用点（建议从粗到细逐步纳入）：

- **线程结构**：`pthread_create*`、`pthread_join*`、线程入口函数、线程返回（`return`）
- **同步语义**：
  - `pthread_mutex_lock/unlock`
  - `pthread_cond_wait/signal/broadcast`
  - `pthread_barrier_wait`
- **阻塞点**：任何可能导致线程阻塞的调用（wait/join/barrier 等）

### 2.3 为什么用 Cut Points 做边界

- 这些点会改变 *happens-before* 关系
- 这些点决定关键路径与等待时间
- 这些点前后的代码段语义更稳定（跨版本/跨编译更稳）

---

## 3. 代码段划分：三层粒度（从粗到细逐步增强）

你不需要一步到位切得很细，建议按下面三层逐步做，闭环验证非常好跑。

### 3.1 Level-0：线程级段（最简单，先跑通）

每个线程只切两段：
- `ThreadStart → ThreadEnd`

用途：
- 快速做 thread-level LPF（按线程总耗时给优先级）
- 快速验证“是否能跑通测时与调度闭环”

### 3.2 Level-1：同步切分段（推荐作为论文主版本）

规则：**在线程内按 Cut Point 切分**。Cut Point 每出现一次，就切一刀。

例如，一个线程里按顺序出现：
- `barrier_wait`
- `lock`
- `unlock`
- `cond_wait`
- `return`

自然得到段序列：
- `entry → barrier`
- `barrier → lock`
- `lock → unlock`
- `unlock → cond_wait`
- `cond_wait → return`

每个 Segment 都是“连续顺序执行代码”，可直接插桩测时。

### 3.3 Level-2：热点切分段（解决“大循环很重但测不到”）

Level-1 保证并发语义正确，但遇到“大循环”你希望更细。

规则：在某个 Level-1 段内，如果存在明显计算热点（例如大 for 循环），再按“热点边界”细分：
- 循环前准备段
- 循环计算段
- 循环后收尾段

注意：热点边界必须满足：
- **不跨越并发语义切点**
- **能稳定定位**（源代码行号稳定，或 AST/expand 定位稳定）

## 4. 时间戳插桩规则：保证不会“测错/测不稳”

### 4.1 最小插桩形式（每段两处）

每段只插两处：
- `SEG_BEGIN(id)`：放在段**第一条语句前**
- `SEG_END(id)`：放在段**最后一条语句后**

并记录（写 CSV/trace 均可）：
- `seg_id`
- `thread_id`
- `timestamp_begin/end`
- `duration`

### 4.2 两个常见坑与规避策略

**坑 A：把阻塞调用算进“计算段时间”，导致含义混乱**
- 例如 `pthread_join` / `pthread_cond_wait` 会把“等待别人”的时间算进去
- 解决：把阻塞调用**单独做一个 Segment**（甚至只包含这一行）
- 这样你能区分：
  - 计算时间（compute）
  - 等待时间（wait/join）

**坑 B：条件分支导致段耗时路径不一致**
- 若段内有 `if/else`，运行时走不同路径，耗时差异大
- 解决（验证阶段够用的做法）：
  - 仍按 cut point 切分
  - 分支内部不强行切细，先做多次运行统计均值/中位数
  - 论文里明确“路径敏感切分是未来工作/可扩展点”

## 5. 用 create/join 示例演示：如何切、如何插桩

你的 `main` 里大致是：

```c
pthread_create(... f0_fn ...);
...
pthread_create(... f11_fn ...);
pthread_create(... c0_fn ...);

pthread_join(tc0, NULL);
...
pthread_join(tf11, NULL);
```

### 5.1 main 线程的 Segment 划分（建议）

- M0 初始化段：main 的变量/结构初始化
- M1 Create 段：从**第一条** `pthread_create` 到**最后一条** `pthread_create`
- M2 Join 段：从**第一条** `pthread_join` 到**最后一条** `pthread_join`
- M3 收尾段：打印/退出

插桩测量关注点：
- M1 的 create 时间（通常很小）
- M2 的 join 时间（通常很大，反映“被动等待”的证据）

### 5.2 worker 线程的 Segment 划分（推荐 Level-1 + Level-2）

假设线程函数内部结构是：
- barrier 对齐
- 两段大循环
- return

切成：
- Ti_0：`entry → barrier_wait`
- Ti_1：`barrier_wait → loop1_end`（或 loop1 单独成段）
- Ti_2：loop2（最重的 loop2 单独成段）
- Ti_3：exit

这样能得到你真正想要的：
- 每个线程的“重计算段时间”（LPF 输入）
- 哪些线程 bottom-level 最大（关键链识别）
- main 在 join 上等待了多少（验证调度是否减少等待）

## 6. 自动化切分算法（论文可写伪码）

### 6.1 输入/输出

输入：
- 源代码 + expand（用于稳定定位）
- 线程入口函数集合（从 `pthread_create` 第三个参数得到）
- 在每个线程函数中识别的 cut points 列表（含行号/节点名）

输出：
- Segment 列表：`(seg_id, thread/function, start_loc, end_loc, kind)`
- 插桩点：`start_loc` 前插 BEGIN，`end_loc` 后插 END

### 6.2 切分逻辑（描述性伪码）

```text
for each thread_entry_fn:
  scan statements in source order
  when see cut_point:
    cut one segment
  for each segment:
    if contains huge_hot_loop:
      split into (pre, loop, post)  // Level-2
  ensure blocking calls are isolated segments
```

## 7. 做验证时的推荐选择

为了最快跑出“段级 DAG 能指导 LPF 并带来性能差异”的结果：

1. 先用 **Level-1（同步切分）** 跑通：
   - DAG → 段 → 测时 → schedule → 插桩 → 对照
2. 如果“重循环被淹没”，再加 **Level-2（热点切分）**：
   - 只对最重的循环切一次就够了（成本低、收益高）
